# Application-definition schema migration

Definitions support schema versions 1 and 2. Version 2 adds a required page `description` string (up to 10,000 characters); an empty string means no description. The explicit `migrateDraft(expectedRevision, 2)` operation transforms a version 1 draft by adding empty descriptions and incrementing its revision. `POST /draft/migrate` accepts `{ "expectedRevision": 0, "targetVersion": 2 }` on the token-protected local control plane. A stale revision or unsupported migration is rejected. SQLite commits the draft update atomically. Existing publications are not modified, and migration does not publish or change business data.

After migration, use the `setPageDescription` patch to edit a description. The development agent accepts both schema versions and can propose version 2 page descriptions, subject to the same separate approval. New version 2 pages must include a description; version 1 pages must not. Publishing, rollback and environment promotion continue to validate definitions and apply the host publication guard. A rollback to an earlier version creates a new publication with that earlier schema; it does not downgrade the draft. Hosts must verify the target runtime supports the chosen schema before publishing, promoting or rolling back.

The host may explicitly call `migrateDraft(expectedRevision, 1)` on a version 2 draft, or send target version 1 to the same Control Plane endpoint. The downgrade succeeds only when every page description is exactly empty; otherwise it rejects the entire operation with a conflict and preserves the draft. A host may deliberately clear descriptions first, but should retain any needed content elsewhere. A successful downgrade removes the version-2-only fields, increments the draft revision and leaves all existing publications intact. SQLite applies the version check and update atomically, so concurrent edits require a fresh revision. Downgrading the draft does not publish or migrate business data.

The generated workspace renders descriptions for schema 2. Its local data-plane integration defaults to version 1; set `PUBLICATION_SCHEMA_VERSION=2` and restart the app when switching to a version 2 publication. Configure offline-publication host scope with the matching version. A schema mismatch fails closed rather than rendering the wrong cached definition. Switch the configured version back if rolling back to version 1, and coordinate all readers and caches before cutover. Immutable historical versions and old clients are not automatically migrated.

The migration paths are intentionally limited to 1 to 2 and the lossless 2-to-1 case; they are not a general registry for arbitrary schemas or a business-data migration. There is no automatic downgrade, production identity, cross-process cutover coordination, or rollback of business data. Rehearse migrations and deploy compatible readers before publication.

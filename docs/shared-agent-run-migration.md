# Shared agent run storage: migration design

Status: design, not an implemented production backend. This plan supports P2-07, P2-08, P2-09 and P3-08. The current `SqliteAgentRuns` and `DurableAgentWorker` remain the only supported lifecycle registry and worker pairing. `PostgresAgentRunSlots` coordinates quotas; it does not store run state or make SQLite state shared.

## Current transaction boundary

The local database is more than a run table. `durable-runs.ts` changes lifecycle state, lease tokens, approval and delegation waits, wakeups, terminal timestamps and control evidence in SQLite transactions. `agent-triggers.ts` and `agent-schedules.ts` couple trigger identity to run creation or wakeup. `action-journal.ts`, `agent-approvals.ts`, `agent-delegations.ts`, `agent-token-budget.ts` and `sqlite-checkpointer.ts` read run state and leases inside their own transactions. Notice delivery, retention, metrics and recovery discovery also query run state directly. Worker, capability and recovery constructors frequently require the concrete SQLite class. Replacing only `get`, `claim` and `settle`, or putting separate SQLite files behind shared quota slots, would split these fences and is not a shared run registry.

## Target and invariants

The target is one authoritative PostgreSQL primary for a migrated run and its coupled state, with independently hosted workers and authenticated, host-authorized control and recovery operations. A run belongs to one tenant and agent; its run ID, definition version, request or trigger identity and stable action keys must retain their existing meanings. Run state, dependent evidence and any decision that requires the current state must commit atomically on the same primary. A lease must use database time, an unguessable token and conditional updates; stale workers must be unable to commit checkpoints, action transitions, approvals, budget changes or results. Expired or interrupted work with an external effect stays uncertain until separately authorized verification, rather than being automatically repeated. Database failure or ambiguous commit must fail closed and leave the caller able to inspect durable state. A successful database check cannot revoke an already dispatched external effect; downstream idempotency and reconciliation remain mandatory.

## Implemented foundation

An internal `PostgresAgentTriggerFoundation`, not exported from the package entry point, creates one queued shared run and its trigger receipt in a single PostgreSQL transaction. Per-agent row locking serializes deduplication and backlog checks across connections; duplicate identity conflicts, tenant isolation and rollback on receipt failure are exercised against PostgreSQL. It uses database time and snapshots its input before asynchronous work. It is not connected to ingress, schedulers, capabilities or workers, and is not a production backend. An internal `PostgresAgentRunLifecycleFoundation` can claim and renew a queued run using database time and revision- and token-fenced leases, enforce per-agent concurrent and daily limits, and move an expired lease to uncertain without automatic retry. Its PostgreSQL tests exercise competing connections, tenant isolation, stale leases and transaction rollback. Expired-lease recovery can optionally atomically record an actor, reference, prior state and lease time; a bounded, run-scoped history read is available to trusted host code. Database triggers reject ordinary updates, deletes and truncation of that history; privileged database administrators can bypass these controls. A local process-termination test checks that recovery and its evidence either both commit or both roll back when a process dies around commit; it does not simulate node or database failover. The host must authenticate and separately authorize recovery and history reads. Shared wakeup identity, redaction, other lifecycle transitions, action and budget fences, checkpoints, migration and production authorization are not implemented. Later operations that change active run counts must use the same scope lock as claims. Do not route production traffic to these tables.

## Implementation sequence

1. Define asynchronous, scoped storage contracts around whole transactional operations, including cancellation and ambiguous outcomes. Inventory every direct SQL consumer above and specify supported behavior for each. Keep the SQLite implementation and its existing tests as the behavioral baseline; do not expose a generic transaction or connection to untrusted extensions.
2. Implement PostgreSQL lifecycle, request deduplication, triggers and wakeups, lease and revision transitions, terminal evidence and authorized controls on one transaction boundary. Test races between two independent connections, tenant isolation, clock and deadline edges, duplicate identities and commit failures against a real PostgreSQL server.
3. Port the action journal, approvals, delegation waits, token budget, notices and checkpoint fences before allowing configured agents to execute with the shared registry. Each write that relies on a lease must verify it in the same transaction as the write. Preserve unresolved external outcomes and stable idempotency keys across process loss.
4. Port recovery, retention, audit, discovery, metrics and capability integrations; keep their authorization and evidence semantics. Adapt workers and dispatchers to the asynchronous operations, rechecking authority and lease after pending callbacks and fencing late results. Do not enable a shared execution path that silently falls back to local state.
5. Run common behavior tests for both backends, then process and pod termination tests with two worker nodes and the same PostgreSQL primary. Exercise concurrent claim and control, primary unavailability, cancellation, uncertain external outcomes, replay and tenant isolation. Test migration, monitoring, backup restoration and reconciliation with representative volumes before production use.

## Cutover and recovery

Start with newly created, explicitly selected scopes; keep each run and its dependent records on exactly one authority. Existing SQLite scopes remain local until a separately implemented and rehearsed offline migration can quiesce ingress and schedulers, drain or reconcile running and uncertain work, copy all coupled state and evidence, and compare counts and content digests before switching the authority. No live dual writes are proposed. Capture an immutable source backup and a migration manifest without credentials or payloads; protect both according to the data they describe. A partial copy, mismatch, active lease or unresolved ownership stops cutover.

After PostgreSQL accepts writes, routing back to an old SQLite snapshot would discard valid new state and may repeat external actions. Stop writers and reconcile or replay every post-cutover change before any reverse migration; otherwise forward repair on the PostgreSQL authority is required. A backup alone is not a rollback protocol. Define actual outage budgets, retention, operator ownership, primary failover behavior and recovery evidence in the target deployment; these have not been established by the current local tests.

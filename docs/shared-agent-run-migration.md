# Shared agent run storage: migration design

Status: design, not an implemented production backend. This plan supports P2-07, P2-08, P2-09 and P3-08. The current `SqliteAgentRuns` and `DurableAgentWorker` remain the only supported lifecycle registry and worker pairing. `PostgresAgentRunSlots` coordinates quotas; it does not store run state or make SQLite state shared.

## Current transaction boundary

The local database is more than a run table. `durable-runs.ts` changes lifecycle state, lease tokens, approval and delegation waits, wakeups, terminal timestamps and control evidence in SQLite transactions. `agent-triggers.ts` and `agent-schedules.ts` couple trigger identity to run creation or wakeup. `action-journal.ts`, `agent-approvals.ts`, `agent-delegations.ts`, `agent-token-budget.ts` and `sqlite-checkpointer.ts` read run state and leases inside their own transactions. Notice delivery, retention, metrics and recovery discovery also query run state directly. Worker, capability and recovery constructors frequently require the concrete SQLite class. Replacing only `get`, `claim` and `settle`, or putting separate SQLite files behind shared quota slots, would split these fences and is not a shared run registry.

## Target and invariants

The target is one authoritative PostgreSQL primary for a migrated run and its coupled state, with independently hosted workers and authenticated, host-authorized control and recovery operations. A run belongs to one tenant and agent; its run ID, definition version, request or trigger identity and stable action keys must retain their existing meanings. Run state, dependent evidence and any decision that requires the current state must commit atomically on the same primary. A lease must use database time, an unguessable token and conditional updates; stale workers must be unable to commit checkpoints, action transitions, approvals, budget changes or results. Expired or interrupted work with an external effect stays uncertain until separately authorized verification, rather than being automatically repeated. Database failure or ambiguous commit must fail closed and leave the caller able to inspect durable state. A successful database check cannot revoke an already dispatched external effect; downstream idempotency and reconciliation remain mandatory.

## Checked-in foundation

At the checked-in baseline, an internal `PostgresAgentTriggerFoundation`, not exported from the package entry point, creates one queued shared run and its trigger receipt in a single PostgreSQL transaction. Per-agent row locking serializes deduplication and backlog checks across connections; duplicate identity conflicts, tenant isolation and rollback on receipt failure are exercised against PostgreSQL. It uses database time and snapshots its input before asynchronous work. It is not connected to ingress, schedulers, capabilities or workers, and is not a production backend. An internal `PostgresAgentRunLifecycleFoundation` can claim and renew a queued run using database time and revision- and token-fenced leases, enforce per-agent concurrent and daily limits, and move an expired lease to uncertain without automatic retry. Its PostgreSQL tests exercise competing connections, tenant isolation, stale leases and transaction rollback. The foundation also supports revision-checked pause and resume for manually paused queued runs, cancellation of queued or manually paused runs, and pause or cancel requests for running runs, with optional atomic actor-attributed control evidence and scoped history. It refuses to resume or cancel an unimplemented approval or delegation wait. Expired-lease recovery can optionally atomically record an actor, reference, prior state and lease time; a bounded, run-scoped history read is available to trusted host code. Database triggers reject ordinary updates, deletes and truncation of that history; privileged database administrators can bypass these controls. A local process-termination test checks that recovery and its evidence either both commit or both roll back when a process dies around commit; it does not simulate node or database failover. The host must authenticate and separately authorize recovery and history reads. At that baseline, shared wakeup identity, redaction, other lifecycle transitions, action and budget fences, checkpoints, migration and production authorization are not implemented. The workspace prototype below adds some of these pieces. Later operations that change active run counts must use the same scope lock as claims. Do not route production traffic to these tables.

## Work in progress in the current workspace

The internal shared execution prototype now couples a PostgreSQL action journal, token budget, approvals and LangGraph checkpoints to run leases, and connects an internal worker and dispatcher, authenticated event ingress, shared schedule polling, manual controls and lease recovery. Stopping the dispatcher signals its active worker and prevents an interrupted, still-pending claim from committing when the database adapter honors transaction rollback; ambiguous commits still require inspection and lease recovery. Shared schedules serialize occurrence creation, receipt insertion and schedule advancement in one database transaction, with revision checks and database time. The existing action recovery worker can verify shared uncertain effects with actor-attributed evidence, and the fixed-run budget recovery service can verify shared token and cost usage, including reconciliation with a separately shared cost ledger. Scope-authorized discovery and existing coordinators can find and recover shared uncertain actions and reservations; a separately authorized fixed-run capability can reconcile the run after unresolved effects and token usage are cleared, recording its operator and reference atomically. Event identity and payload are retained in the same transaction as the run; the worker host can read the scoped payload after authorizing access. A separately authorized shared trigger-retention worker can redact terminal-run payloads while preserving their deduplication fingerprints and immutable evidence. Authenticated ingress can resume a host-selected shared paused run with a deduplicated wakeup receipt and approval checks. Shared schedules can also wake a host-selected paused run in the same transaction as the occurrence and receipt. Separately authorized retention workers can redact terminal-run trigger and wakeup payloads while retaining replay fingerprints and immutable redaction evidence. An opt-in local kind test removes an executing pod after an external-effect barrier, waits for its database lease to expire, verifies and reconciles that effect, and resumes from the retained checkpoint on a replacement pod without dispatching the effect again. It has also passed with the two pods pinned to different worker nodes. A separate opt-in test stops the first disposable kind worker node, reconciles its recorded effect after lease expiry, and resumes on the second worker node without repeating that effect. A separate disposable synchronous PostgreSQL primary/standby test stops the primary, promotes the standby and recovers the run after lease expiry. Neither local test establishes target-cluster behavior, automatic database failover or backup recovery. Overdue queued or paused shared runs can be expired by the existing host-authorized expiry worker using database time, with atomic scope-local audit evidence and separately authorized history reads. Expiry fails closed when effects or token usage remain unresolved; cancellation during a database transaction rolls the transition and evidence back. These changes are exposed only through an explicitly experimental package subpath and are not a production-ready deployment. Shared delegated execution now verifies a scope-bound grant using database time and pauses on expiry until a newer live grant is supplied. Shared approval and delegation notices are recorded atomically and accessible through the authenticated review inbox; shared external notice delivery has an experimental outbox and host-operated worker; deployment-specific delivery, schedule history access and retention, production authorization, and target-environment failover validation remain incomplete. Hosts must bound database statements and transactions, authorize every operation, and reconcile ambiguous outcomes; downstream effects require idempotency or independent verification.

## Experimental host entry point

A host testing new shared scopes can import `@app-mixer/agent/dist/shared-run-experimental.js`. Run `initializeExperimentalSharedAgentStorage({query, transaction})` once during controlled provisioning, before workers start; use a single provisioner because concurrent schema migrations are not coordinated. The transaction adapter must run the supplied callback on one connection, commit only on success, and roll back on errors. Configure connection, statement, and transaction timeouts, and make commit outcomes inspectable after connection loss. The initializer creates schema objects and no runs, grants, or authorization policy.

The entry point returns trigger, run and schedule stores and exports lease-bound journals, budgets, checkpoints, approvals, worker, dispatcher and recovery helpers. A host must supply its own authentication, authorization, worker execution callback, model, provider verification, database operations and lifecycle controls. Shared execution rejects mixed local and shared stores and requires the same database adapter for its coupled stores. The experimental PostgreSQL notice outbox can be used with the existing notice delivery worker and HTTPS transport. The host selects and authorizes destinations, queues notices, operates the worker, and verifies or reconciles uncertain outcomes. A sender may still be running in another process; an operator must ensure it has stopped before recovering a sending delivery. Receiver idempotency or independent verification is required. The local integration test covers a shared approval, competing senders, an uncertain outcome, reconciliation and worker delivery; target-deployment delivery and failover remain unverified. Do not route production traffic to this experimental interface until its missing capabilities, monitoring, deployment-specific identity and failover exercises are complete.

For the destructive node-stop exercise, set `APP_MIXER_TEST_KIND_NODE_FAILURE=1` in addition to the shared pod test's PostgreSQL URLs and worker-node settings. The test only accepts the dedicated `kind-app-mixer-shared-recovery` context and its `app-mixer-shared-recovery-worker` and `app-mixer-shared-recovery-worker2` containers. It stops the first container and restarts it during cleanup. Use only a disposable cluster; this exercise does not simulate a storage failure.

From the repository root, after building the agent package, `pwsh -NoProfile -File packages/agent/test/run-postgres-failover.ps1` creates a disposable PostgreSQL primary and standby with synchronous `remote_apply` replication, stops the primary after the worker's effect barrier, promotes the standby, and recovers the run after its lease expires. It refuses pre-existing test container or network names and removes the resources it creates. The test effect is represented in the test database, not a real external provider. This exercise does not test automatic endpoint routing, split-brain fencing, an asynchronous replica, backup restoration, or a production deployment.

## Implementation sequence

1. Define asynchronous, scoped storage contracts around whole transactional operations, including cancellation and ambiguous outcomes. Inventory every direct SQL consumer above and specify supported behavior for each. Keep the SQLite implementation and its existing tests as the behavioral baseline; do not expose a generic transaction or connection to untrusted extensions.
2. Implement PostgreSQL lifecycle, request deduplication, triggers and wakeups, lease and revision transitions, terminal evidence and authorized controls on one transaction boundary. Test races between two independent connections, tenant isolation, clock and deadline edges, duplicate identities and commit failures against a real PostgreSQL server.
3. Port the action journal, approvals, delegation waits, token budget, notices and checkpoint fences before allowing configured agents to execute with the shared registry. Each write that relies on a lease must verify it in the same transaction as the write. Preserve unresolved external outcomes and stable idempotency keys across process loss.
4. Port recovery, retention, audit, discovery, metrics and capability integrations; keep their authorization and evidence semantics. Adapt workers and dispatchers to the asynchronous operations, rechecking authority and lease after pending callbacks and fencing late results. Do not enable a shared execution path that silently falls back to local state.
5. Run common behavior tests for both backends, then process and pod termination tests with two worker nodes and the same PostgreSQL primary. Exercise concurrent claim and control, primary unavailability, cancellation, uncertain external outcomes, replay and tenant isolation. Test migration, monitoring, backup restoration and reconciliation with representative volumes before production use.

## Cutover and recovery

Start with newly created, explicitly selected scopes; keep each run and its dependent records on exactly one authority. Existing SQLite scopes remain local until a separately implemented and rehearsed offline migration can quiesce ingress and schedulers, drain or reconcile running and uncertain work, copy all coupled state and evidence, and compare counts and content digests before switching the authority. No live dual writes are proposed. Capture an immutable source backup and a migration manifest without credentials or payloads; protect both according to the data they describe. A partial copy, mismatch, active lease or unresolved ownership stops cutover.

After PostgreSQL accepts writes, routing back to an old SQLite snapshot would discard valid new state and may repeat external actions. Stop writers and reconcile or replay every post-cutover change before any reverse migration; otherwise forward repair on the PostgreSQL authority is required. A backup alone is not a rollback protocol. Define actual outage budgets, retention, operator ownership, primary failover behavior and recovery evidence in the target deployment; these have not been established by the current local tests.

# Offline operation queue: local foundation

`SqliteOfflineQueue` is an explicitly enabled, durable local queue separate from `SqliteStagedOperations`. Construct it with `{enabled: true, maxAttempts, retryDelayMs}`; attempts are limited to 1–20 and delay to at most one day. The host can call `processOne` for an authenticated tenant and principal, or explicitly start the polling worker described below. No worker starts automatically.

`enqueue(scope, principalId, operationId, requestKey, payload)` persists a JSON object and generates a stable external idempotency key. Retrying the same request key, operation and payload for the same tenant, application and principal returns the existing operation; a different operation or payload conflicts. Each principal's queue is limited to 1,000 retained operations. This foundation retains terminal entries to preserve deduplication; retention and archival policy remain open.

A worker atomically claims a due intent and invokes the registered capability with `{idempotencyKey, payload}` and the supplied actor. Capability authorization, validation and audit run again for every attempt. The remote implementation must honor the idempotency key; the local queue cannot guarantee an external service's behavior. The worker must establish the actor's current identity and authority before each pass. Direct queue methods do not authenticate or authorize callers.

A host-owned synchronous failure classifier may return `retry` only when it can establish that a replay is safe, `conflict` for a known conflict, or `uncertain` otherwise. Unknown classifications and classifier errors become uncertain. Retries use the same idempotency key, a fixed delay and a durable attempt limit; exhausted operations stop. Conflicts and uncertain outcomes stop automatically. A host can inspect operations, discard pending, conflicting or exhausted intents, and submit a new intent with a new request key after resolving a conflict. Discard never changes remote data.

A crash can leave an operation `running`. Only after confirming its submitting process is no longer active may an authorized host call `recoverAbandoned`, which marks it uncertain. `reconcile` requires independent evidence that the remote operation was applied or not applied; only the latter returns it to the queue, subject to the attempt limit. Never classify a timeout, a failed outcome audit, or an ambiguous external error as a safe retry without evidence.

The SQLite file is not encrypted by this package. The host must protect it and its backups using platform-appropriate secure storage, manage identity, and avoid placing secrets in queued payloads. This is a local server/host primitive, not yet a browser or mobile offline store, conflict-resolution UI, production multi-device synchronization, or automatic cleanup. P2-04 remains open.

`OfflineSyncWorker` can poll an enabled queue after the host explicitly calls `start()`. Its configuration fixes the tenant, application and principal and supplies `isOnline`, `resolveActor`, a failure classifier, an error handler, a polling interval (100 ms to one hour) and a per-pass limit (1–100). Before each operation it checks connectivity and resolves the current actor; absent or mismatched identity stops the pass. Capability authorization still runs on every dispatch. The worker does not claim staged operations or overlap its own passes. `stop()` prevents new work and waits for the current in-flight operation and callbacks to finish; it cannot undo or cancel an external effect already dispatched. The host must stop the worker before closing its queue and must ensure the connectivity and identity callbacks return promptly. Multiple workers may share a database; SQLite claims prevent them from executing the same intent concurrently.

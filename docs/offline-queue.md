# Offline operation queue: local foundation

`SqliteOfflineQueue` is an explicitly enabled, durable local queue separate from `SqliteStagedOperations`. Construct it with `{enabled: true, maxAttempts, retryDelayMs}`; attempts are limited to 1–20 and delay to at most one day. The host can call `processOne` for an authenticated tenant and principal, or explicitly start the polling worker described below. No worker starts automatically.

`enqueue(scope, principalId, operationId, requestKey, payload)` persists a JSON object and generates a stable external idempotency key. Retrying the same request key, operation and payload for the same tenant, application and principal returns the existing operation; a different operation or payload conflicts. Each principal's queue is limited to 1,000 retained operations. This foundation retains terminal entries to preserve deduplication; retention and archival policy remain open.

A worker atomically claims a due intent and invokes the registered capability with `{idempotencyKey, payload}` and the supplied actor. Capability authorization, validation and audit run again for every attempt. The remote implementation must honor the idempotency key; the local queue cannot guarantee an external service's behavior. The worker must establish the actor's current identity and authority before each pass. Direct queue methods do not authenticate or authorize callers.

## Shared request identity across devices

An optional `PostgresOfflineRequestKeys` store lets a trusted host allocate one idempotency key for a logical request shared across devices. Provision its table with `initialize()` using a migration identity, then provide a query adapter connected to the authoritative PostgreSQL primary. `allocate(scope, principalId, operationId, requestKey, payload)` binds the tenant, application, principal, operation and canonical payload digest to a random UUID. Concurrent matching allocations return the same key; a different operation or payload under the same request key conflicts. The host must authenticate and authorize every allocation and derive the scope and principal independently of client-supplied data. A request key must be deliberately shared for the same intended action; the store does not infer whether independently created requests represent the same intent.

Trusted host code can pass the allocated key as `{idempotencyKey}` to `SqliteOfflineQueue.enqueue`, `EncryptedBrowserQueue.enqueue`, or the generated runtime's `enqueue`. These are explicit optional fourth/final arguments; without them each queue continues to create its own key. The key must be obtained and securely transferred while the device can reach the trusted service, or pre-provisioned with the intended payload before going offline. Reusing an existing local request with a different explicit key fails. By default the generated form creates device/session-local request identities and does not allocate or synchronize shared keys automatically.

Before an effect, the host-controlled capability can call `verify(scope, principalId, operationId, payload, idempotencyKey)` against the authoritative primary and reject false results or store failures. This binds a presented key to the authenticated scope and content; a client-provided key alone is not proof of authorization. Capability authorization and downstream idempotency must still run for every delivery. The allocator is not a transaction with the downstream effect and cannot ensure that an external provider honors the key. A lost database update, database restore, key disclosure, incompatible old clients, a different principal, or a provider with limited idempotency retention can break cross-device deduplication. Host code must coordinate durable storage, recovery, key delivery, rollout and replay windows. Only a digest of the payload is stored, but predictable payloads can be guessed from hashes; request metadata and keys may also be sensitive. Records are retained indefinitely and require host-managed storage and retention.

`registerSharedOfflineAllocation(front, store, options)` and `registerSharedOfflineDispatch(front, external, store, options)` can expose that flow through the authenticated capability server. Register separate host-chosen candidates for allocation and dispatch, with the same fixed `applicationId` and `targetOperationId`. Both require `authorize(actor)`, `authorizePayload(actor, payload)` and `validatePayload(payload)` callbacks. Allocation accepts exactly `{requestKey, payload}` and returns `{idempotencyKey}`; dispatch accepts exactly `{idempotencyKey, payload}`, verifies the stored binding, then invokes the fixed operation through a **separate** capability registry, which performs its own authorization, validation and audit. Tenant and principal come from the authenticated server context, not the request body. A conflicting allocation returns HTTP 409, a valid-format key with a mismatched binding returns 403, malformed input returns 400, and a store failure prevents dispatch.

The generated runtime can enqueue the returned object as its optional key argument, using the dispatch capability as its operation. Configure the host's generated-app allowlist, authentication, origin restrictions, payload policies and transport for both endpoints. The host must authorize the target action at allocation and again at dispatch; allocation alone grants no execution authority. On a new dispatch both registries' audits apply, and failure to record a success after dispatch may leave the outcome uncertain. The target capability or provider still must durably deduplicate the supplied key; a successful verification is not an atomic transaction with that effect. The built-in form can opt into the shared slot integration described below; reconciliation remains host-controlled.

For optional shared dispatch coordination, construct `PostgresOfflineExecutions({query, requestKeys: store})`, call `initialize()` after the key registry is provisioned, and pass it as `executions` to `registerSharedOfflineDispatch`. Use the same authoritative primary for both stores. The journal atomically claims a verified key before forwarding; a concurrent caller receives HTTP 409 `Shared offline operation in progress`. After a successful response is recorded, later authorized calls return the stored JSON result without dispatching again. The host's outer `authorize` and `authorizePayload` policies run on every call, including result replay; the external registry's policy is invoked only for a new dispatch, so the outer policy must independently enforce current access to both the action and stored result. Results must be bounded JSON values and are stored unencrypted; protect them and retain them only under a suitable host policy.

Any dispatch error, invalid result, or failure to record completion makes the outcome uncertain, or leaves it running if the database cannot record uncertainty. Neither state automatically dispatches again. A trusted, authorized operator can use `get(scope, principalId, key)` to inspect the attempt token, call `markUncertain` only after establishing that the old dispatcher has stopped, and then call `reconcile` with that exact token and independently verified `applied` result or `not_applied` outcome. An applied result becomes the replayable result; confirmed non-application permits a new claim. Attempt tokens fence stale local updates, but cannot stop a remote effect already in flight. A client must distinguish an in-progress response from an uncertain result, apply bounded polling where appropriate, and never treat an ambiguous result as proof of non-application. The recovery methods themselves do not authenticate, authorize or audit administrators; the host must provide those controls.

This journal coordinates only callers that use it against the same durable primary. Other code paths or older versions can bypass it. It cannot atomically commit a remote provider's effect with its own record, fence an external worker, survive an unsafe database rollback, or establish what a provider did after a timeout. Downstream idempotency and independent provider reconciliation remain required for external effects. Do not recover while the old dispatcher or provider request may still execute. Records and results are retained indefinitely; production availability, secure storage, retention and independent audit remain host responsibilities.

For operator-attributed recovery, `PostgresOfflineRecovery({query, authorize, clock?})` provides an alternative to direct journal recovery methods. Provision its event table with `initialize()` and use the same authoritative primary. `markUncertain(actor, target, attemptToken, reference)` and `reconcile(actor, target, attemptToken, decision, reference)` require explicit host authorization and a nonempty evidence reference. The target fixes tenant, application, original principal and idempotency key; the operator must belong to the same tenant. The state change and actor-attributed event commit in one PostgreSQL statement, so a failed event insert rolls back the change. Competing or stale attempts cannot both change the same state. `history(actor, target, {after?, limit?})` separately authorizes a bounded page of operator events.

The reference is host-supplied metadata, not proof that a worker stopped or a provider outcome was verified. Authentication, authorization, evidence verification and protection of any sensitive references remain host responsibilities. The event table is not tamper-proof: use separate database roles and restrict updates and deletes, and export audit records to independently protected storage if required. The direct journal recovery methods and direct database access can bypass this audit; do not expose them when audited recovery is required. Automatic uncertainty after a dispatch error is not an operator event. Existing recovery actions are not backfilled, and records are retained indefinitely.

After a capability executes, a failure to persist its successful outcome is never passed to the retry classifier. The queue attempts to mark it uncertain and reports an error; if that write also fails, it remains running and requires host-confirmed abandoned-submitter recovery. A capability outcome-audit failure is also treated as uncertain without consulting the classifier. `CapabilityRegistry` reports this failure as `CapabilityOutcomeUncertainError`; other callers must independently verify the outcome before retrying. These protections do not establish the external outcome.

A host-owned synchronous failure classifier may return `retry` only when it can establish that a replay is safe, `conflict` for a known conflict, or `uncertain` otherwise. Unknown classifications and classifier errors become uncertain. Retries use the same idempotency key, a fixed delay and a durable attempt limit; exhausted operations stop. Conflicts and uncertain outcomes stop automatically. A host can inspect operations, discard pending, conflicting or exhausted intents, and submit a new intent with a new request key after resolving a conflict. Discard never changes remote data.

A crash can leave an operation `running`. Only after confirming its submitting process is no longer active may an authorized host call `recoverAbandoned`, which marks it uncertain. `reconcile` requires independent evidence that the remote operation was applied or not applied; only the latter returns it to the queue, subject to the attempt limit. Never classify a timeout, a failed outcome audit, or an ambiguous external error as a safe retry without evidence.

The SQLite file is not encrypted by this package. The host must protect it and its backups using platform-appropriate secure storage, manage identity, and avoid placing secrets in queued payloads. This is a local server/host primitive, not yet a browser or mobile offline store, conflict-resolution UI, production multi-device synchronization, or automatic cleanup. P2-04 remains open.

`OfflineSyncWorker` can poll an enabled queue after the host explicitly calls `start()`. Its configuration fixes the tenant, application and principal and supplies `isOnline`, `resolveActor`, a failure classifier, an error handler, a polling interval (100 ms to one hour) and a per-pass limit (1–100). Before each operation it checks connectivity and resolves the current actor; absent or mismatched identity stops the pass. Capability authorization still runs on every dispatch. The worker does not claim staged operations or overlap its own passes. `stop()` prevents new work and waits for the current in-flight operation and callbacks to finish; it cannot undo or cancel an external effect already dispatched. The host must stop the worker before closing its queue and must ensure the connectivity and identity callbacks return promptly. Multiple workers may share a database; SQLite claims prevent them from executing the same intent concurrently.

## Encrypted browser intent storage

`@app-mixer/web/offline` exports `EncryptedBrowserQueue`, an explicitly enabled IndexedDB store for browser intents. The host supplies `{enabled: true, databaseName, scope: {tenantId, applicationId, principalId}, key}` where `key` is a non-extractable AES-GCM `CryptoKey` with encrypt and decrypt usage. The host must obtain and protect that key using its own secure unlock and identity lifecycle; this package does not persist, derive, recover or distribute keys. Changing or losing the key makes previously encrypted records unreadable. Use a secure browser context and platform-appropriate protection.

Payload, operation ID, request key, external idempotency key and state are encrypted with a fresh IV and authenticated against their partition, record ID and version. IndexedDB still exposes hashed partition and request identifiers, versions, ciphertext sizes and timing. The store does not protect against compromised same-origin code, an unlocked session, browser extensions, rollback of old database snapshots unless the optional rollback anchor below is configured, or a host that mishandles keys. Do not treat hashing as secrecy for guessable identifiers.

### Rollback anchor

A host can pass `rollbackAnchor: {read, advance}` to `EncryptedBrowserQueue.open` to detect a queue partition restored from an older copy of browser storage. The queue then keeps a monotonic change counter, encrypted and authenticated with the queue key and bound to the partition, and advances it in the same IndexedDB transaction as every enqueue, conflict resolution, transition and key rotation. The current counter also authenticates a digest of the entire encrypted queue partition, detecting selective replacement, insertion, deletion or partition reassignment of its records. Repeated idempotent enqueues and reads do not advance it. `read()` must return the host's stored floor as a nonnegative safe integer, and `advance(counter)` must durably keep the maximum value it has received; tabs can report values out of order. Store the floor outside the browser profile being protected, for example in an authenticated server record or platform secure storage, and scope it to the same tenant, application and principal.

Opening and queue operations fail closed when the anchor cannot be read, returns an invalid value, or exceeds the local counter (`Offline queue rollback detected`), including when the counter record was deleted. A counter that has been changed or cannot be authenticated is rejected. A larger local counter is pushed to the anchor during these checks. If the host anchor is unavailable, subsequent reads and writes can fail until it recovers. Writers in other tabs that advance the counter first cause an internal retry with jittered backoff; a write fails only after 32 attempts. If `advance` fails after a local commit, the change stays committed, `hasPendingRollbackAnchor()` returns true, and later writes or `syncRollbackAnchor()` retry. Until the floor catches up, a rollback to a state at or after the old floor is not detected. Every queue instance for a partition must configure the anchor; an instance without it writes without advancing the counter.

The anchor detects whole-partition restores, counter deletion, and selective queue-record tampering observed during open-session checks. It does not protect a host that loses or resets its floor. Existing v1 counters do not bind individual records until the next anchored mutation upgrades them to v2; older anchored clients cannot read v2 counters, so update every client before relying on the new binding. For bounded resource use, protected partitions are limited to 1,000 records and 64 MiB of encrypted record data. Each check scans and hashes the partition, which may be costly for large queues; unanchored queues keep their existing behavior. The host anchor and browser storage do not share an atomic transaction, so a restore between a check and an operation can still race. Recovery from a detected rollback is a host decision: inspect the server state for queued operations before discarding local storage or resetting the floor.

`enqueue` deduplicates a request key within the identity partition and rejects a changed operation or payload. Enqueue and conflict resolution snapshot their payloads, and enqueue snapshots any supplied shared idempotency key, before asynchronous work; cross-tab retries reuse those snapshots. `get` and `list` authenticate entries before returning them. `transition(id, expectedVersion, action)` uses IndexedDB compare-and-swap to prevent competing tabs from claiming the same version. The host must use `uncertain` after an ambiguous outcome or abandoned running claim, and only use reconciliation after verifying the external result. `requeue` is permitted only when the host has independently established retry safety. The store alone does not dispatch operations or schedule retries; the optional worker below supplies bounded polling. It retains at most 1,000 records per partition; retention and cleanup remain open. It does not submit staged transactions.

`BrowserOfflineWorker` in the same module can explicitly poll an encrypted queue after `start()`. The host supplies connectivity, a current actor resolver, an authenticated `dispatch` function, a safe failure classifier, an error handler, a polling interval and bounded attempts and batch size. It checks the resolved tenant, application and principal against the queue's snapshotted scope before each dispatch, and the remote capability service must independently authenticate and authorize every call. `stop()` prevents new dispatches and waits for any active one. A claim made before stopping or losing connectivity is released without consuming an attempt if no dispatch began. Competing tabs use compare-and-swap; a failed or interrupted dispatch is uncertain unless the host can prove it is safe to retry or is a conflict.

Retries use the same external idempotency key and occur no more than once per polling pass, up to the configured attempt limit. A worker does not automatically recover claims left running by a closed tab; the host must establish the previous dispatcher has stopped and reconcile uncertain external outcomes. Browser timers can be delayed or suspended, so this is not a guaranteed background service. The host still owns key lifecycle and must explicitly enable offline storage. Mobile storage, cross-device conflict presentation, and production identity remain open.

## Rotating a browser queue key

A trusted host may call `await queue.rotateKey(nextKey)` to re-encrypt an existing identity partition with a new non-extractable AES-GCM key. The method authenticates every entry, rejects running operations, prepares replacement ciphertext, then checks the complete partition and writes all replacements in one IndexedDB transaction. A concurrent enqueue or transition aborts rotation without changing any entry. Rotation preserves IDs, payloads, statuses, attempts, idempotency keys and conflict links, and advances every item version so stale operations cannot overwrite the new ciphertext. A retry of an already completed conflict resolution can still use the original expected version when its replacement request and payload match. A successful rotation returns the number of entries and closes the old queue handle; reopen with the new key and refresh displayed versions. An empty partition returns zero and still installs a key marker and closes the old handle. Rotation is limited to 1,000 entries and 64 MiB of ciphertext.

The host must authorize the operation, provision and durably retain the new key, stop dispatchers, and reconcile abandoned running operations before rotating. An authenticated key marker fences other current-version queue instances: their reads and mutations fail after rotation, and reopening requires the new key. Opening the current store upgrades its IndexedDB database to version 3, requests that existing version-1 and version-2 connections close, and prevents App Mixer clients that explicitly open those older versions from reopening it. Both offline stores may use the same database name; their separate object stores and keys remain independent. An uncooperative connection can block the upgrade; close it and retry. Other code that opens the current database version but ignores the marker is not fenced and must be stopped before rotation. Before a partition has been rotated, there is no marker to authenticate its key on open. A crash after commit but before the host records success leaves the outcome unknown, so retain both keys until the host verifies the partition. Rotation does not securely erase prior ciphertext from browser storage or backups. Key distribution, revocation, recovery, retention, and rotation of the separately encrypted publication cache remain host responsibilities.

## Reviewing browser conflicts

`mountOfflineConflictPanel(root, queue, {loadCurrent})` renders conflicts, uncertain results and exhausted operations after the host unlocks the correct queue. The host's `loadCurrent(operationId, payload, scope)` must authenticate and retrieve the current authoritative data. A user can load it, compare it with the queued JSON, edit a resolved object, and explicitly queue the resolution. The panel uses text nodes for data and never automatically retries uncertain operations. Its `refresh()` method reloads the panel; `dispose()` removes it and ignores late results.

`resolveConflict(id, expectedVersion, requestKey, payload)` atomically marks the old conflict discarded and creates a linked pending intent with a new external idempotency key. Repeating the same resolution request returns the existing replacement; different concurrent resolutions cannot both win. A host can also explicitly discard a conflict. Successful replacement may be picked up by an enabled worker, so resolving the conflict is a user-authorized queue action. The user and host remain responsible for choosing a correct merged payload and any remote version precondition. Uncertain outcomes require host verification and reconciliation; the panel does not provide a blind retry. The panel is opt-in and is not automatically mounted in generated apps. Optional read and mutation policy callbacks can prevent actions after a host identity or authorization change.

## Generated local apps

Generated apps include `offline-runtime.mjs` and the browser offline modules, but do not enable or start them by default. Trusted host code can call `createGeneratedOfflineRuntime(config)` after a user unlocks a non-extractable key. The configuration supplies `enabled: true`, database name, tenant/application/principal scope, key, an allowlist of `{id, label}` operations, `canEnqueue`, `canDiscard`, `resolveActor`, `isOnline`, authenticated `dispatch`, `classify`, `onError`, `loadCurrent`, interval, batch size and attempt limit. The runtime checks identity and host policy when queuing or resolving, and the worker rechecks identity before dispatch. Remote services must authenticate and authorize every operation and honor the idempotency key. Never put keys or credentials in browser module source.

Host code can call `mountGeneratedOfflineForm(root, runtime)` for an explicit JSON enqueue form, `runtime.mountConflicts(root)` followed by `refresh()` for conflict review, and `runtime.start()` to enable polling. Before enqueueing, the form saves a request key and a salted digest of the operation and JSON in the tab's session storage. Repeating unchanged input after a reload in the same tab reuses the key; changed input or the explicit new-operation action creates a new one. The stored digest is not encryption and may reveal guessable input; neither the JSON payload nor credentials are stored there. Use one mounted form per storage key and provide a stable, distinct `{storageKey}` option for each form and identity; by default the key uses the root element's ID, or `default` if absent. Storage and secure crypto must be available; errors prevent enqueue rather than silently changing the request key. Session storage can be cleared or lost when a tab closes, and a duplicated tab may inherit its opener's state. This is not cross-device or long-term deduplication. `runtime.close()` stops the worker and disposes conflict panels; the host should dispose the enqueue form and remove sensitive UI immediately when identity changes or the key is locked. Do not allowlist explicit staged submission as an offline operation: staged transactions have a separate user-controlled workflow.

A trusted host can opt the form into shared identity by passing `{storageKey, sharedIdentityStore}` instead of `identityStore`. The store supplies `getOrCreate(slot, operation, payload)`, returning `{requestKey, idempotencyKey}`, and `reset(slot)` and `restore(slot, operation, payload, pair)`. Both returned keys must be lowercase version-4 UUIDs. The host must coordinate the logical request key across devices, obtain the matching idempotency key through the authenticated allocation capability, bind the store to the runtime's current tenant, application and principal, and authorize the payload. The form passes that pair to the encrypted queue; a failed or malformed lookup stops submission and retains the entered data rather than creating a local key. Disposing the form before lookup completes prevents that submission from being queued.

`reset` must deliberately coordinate a new logical operation across devices; an already-started submission cannot be recalled. `restore` receives both keys from a selected queued item and must authorize and verify their binding before sharing them. A host may cache a previously allocated pair securely for offline use, but cannot safely invent a replacement when allocation or coordination is unavailable. The dispatch capability must still verify the key, and the external effect must honor idempotency. The hook itself does not provide remote identity or provider reconciliation; its host-supplied store must do so. Do not use it for unrelated operations that happen to have identical data.

For online cross-device coordination, a host can provide the built-in `createSharedOfflineIdentityStore` as the form's `sharedIdentityStore`. On the server, construct `PostgresOfflineSlots({query, requestKeys})` and initialize it after the request-key registry, using the same authoritative PostgreSQL primary. Register `registerSharedOfflineSlotCapability` on the authenticated capability registry with a fixed `applicationId` and `targetOperationId`, and host policies `authorize`, `authorizeSlot`, `authorizePayload` and `validatePayload`. The slot capability accepts open, allocate, reset and restore actions; tenant and principal come from the authenticated actor. Configure dispatch and the execution journal separately as described above. The host must authorize the slot and content for the same user-confirmed business intent, secure transport and results, and protect database roles, audit records and retention.

```js
import {createSharedOfflineIdentityStore, mountGeneratedOfflineForm} from './offline-runtime.mjs';
const identities = await createSharedOfflineIdentityStore({
  databaseName: 'my-app-shared-slots', scope: {tenantId, applicationId, principalId},
  operations: [{id: 'offline.dispatch', slotCapability: 'offline.slot'}],
  resolveActor, invoke // authenticated invoke(capabilityId, input)
});
const form = mountGeneratedOfflineForm(root, runtime, {storageKey: 'order-form', sharedIdentityStore: identities});
// On lock or sign-out: form.dispose(); identities.close(); await runtime.close();
```

Use a dedicated IndexedDB database and stable, distinct form storage keys. Each device stores the last observed slot generation, so a reset on another device produces a conflict instead of silently using a new request. Opening and allocating a slot require network access. Allocation binds the exact operation and canonical payload to the current generation in the database; changing the payload in that generation conflicts. After reviewing the old operation and resolving any uncertainty, the host may explicitly call `identities.adoptCurrent('app-mixer-offline-form-v1:order-form', 'offline.dispatch')` to accept the current generation for the example form. The form prefixes its configured storage key with `app-mixer-offline-form-v1:` when addressing the slot. New operation and history restore use compare-and-swap; restore additionally verifies the original payload and keys. Reset or restore does not cancel queued requests or effects already in flight. Stop and reconcile old clients before changing generations or adopting a new one; identical data can represent a separate intent.

The local generation database stores a hashed scope and slot plus the random request key, not the payload. Clearing, restoring or rolling back browser storage can lose the device's fencing state, so it is not an anti-rollback guarantee. Hosts needing offline initiation must securely pre-provision an appropriate custom identity store. Stable production identity, durable database recovery, downstream idempotency and provider reconciliation remain host responsibilities.

After reopening the same encrypted queue, the host may call `runtime.mountHistory(root)` and `await panel.refresh()` to show retained operations, their state and queued data. The read-only view helps users check for a previously queued request before creating another; it does not automatically deduplicate requests after session storage is lost or prove a remote outcome. Refresh rechecks the host-resolved identity and clears the old view before reading. Call `panel.dispose()` or `runtime.close()` immediately on identity change or lock; the runtime clears mounted panels before waiting for its worker to stop. The host must ensure the surrounding page is private and provide its own key recovery and access policy. Existing operation payloads remain visible until the view is cleared.

For explicit request recovery, mount a form and pass `{onRecover: id => form.recover(id)}` to `runtime.mountHistory`. Choosing “Use request in form” replaces the form's current data with the selected queued request and restores its request key; submitting unchanged data returns the existing operation, including its current status, instead of creating another. Edited data gets a new request key. The host should warn about unsaved form edits before invoking recovery. Recovery supports UUID request keys used by generated forms and rechecks identity and the entry version; other host-created request keys cannot be restored through this form. It does not dispatch or reconcile an uncertain operation, and it does not recover a request that was never committed to the queue. The host must unlock the same key and scope and dispose the form on identity change or lock.

The generated local capability proxy uses one host-configured actor and is a development profile, not multi-user authentication. The runtime needs host-provided key and identity management; the optional static shell cache below can reopen the app shell, but it does not cache published definitions or business data. Automatic cross-session request deduplication, mobile storage and production multi-device conflict handling remain open.

## Optional generated-app shell cache

Generated apps include `offline-shell.mjs`. Trusted host code can call `enableOfflineShell(revision)` only after the user or host opts in; no service worker is registered by default. A revision is a host-chosen 1–64 character identifier containing letters, digits, dots, underscores or hyphens. The worker caches a fixed allowlist of the generated shell and static JavaScript, then serves those files from that revision's cache. Change the revision whenever any shell asset or trusted extension module changes; normal service-worker lifecycle rules can leave an older version active until existing clients close. `disableOfflineShell()` unregisters this shell worker when it owns the root registration and deletes this app's shell caches. Enabling it uses the origin's root service-worker scope, so a host must coordinate with any existing worker.

Only use this feature when the generated HTML and static modules are safe to retain on the device and contain no secrets or user-specific data. The worker does not cache `/api/application`, `/api/publication`, capability calls, chat, request bodies or arbitrary URLs. It does not cache published pages or business data by itself. A host can separately enable the encrypted published-definition integration described in [published cache](published-cache.md), and must provide authorization and key lifecycle. Browser storage eviction, first installation and private browsing behavior remain platform-dependent.

## Cross-session form request identity

A trusted host may opt a generated form into a persistent request identity store:

```js
import {createPersistentOfflineRequestKeys, mountGeneratedOfflineForm} from './offline-runtime.mjs';
const identities = await createPersistentOfflineRequestKeys({
  databaseName: 'my-app-form-identities', scope: {tenantId, applicationId, principalId}
});
const form = mountGeneratedOfflineForm(root, runtime, {storageKey: 'order-form', identityStore: identities});
// When the user locks or signs out: form.dispose(); identities.close(); await runtime.close();
```

Use a dedicated IndexedDB database name, distinct from the queue and publication databases. The identity scope must exactly match the authenticated runtime scope, and each independent logical form needs a distinct stable `storageKey`. A saved request key survives tab closure and browser restart; identical operation and JSON input in the same slot reuse it, including after an enqueue committed but its response was lost. IndexedDB transactions coordinate concurrent tabs that submit the same unchanged form. Changed serialized input receives a new key, and the explicit New operation button clears the slot so the next submission is a separate intent. Explicit history recovery can also restore a selected request into the slot. Payload property order affects matching.

The identity database stores only a hashed scope/slot identifier, random request key, random salt and salted digest of the operation and JSON; the payload itself remains in the encrypted queue. These hashes are not encryption and guessable inputs may be inferred. The host must protect browser access, authorize the user and retain the queue key; this feature does not provide cross-device deduplication or protect against same-origin code, storage loss or database rollback. Stop other forms and in-flight submissions using the same slot before selecting New operation or restoring history: an already-started submission cannot be undone, and distinct concurrent input changes can intentionally create separate identities. Clearing browser data loses the mapping. Identical data may represent a separate intended business operation, so use New operation when appropriate. Downstream services must still honor idempotency keys and authenticate each request.

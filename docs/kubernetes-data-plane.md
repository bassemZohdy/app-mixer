# Kubernetes Data Plane package

This package deploys a replicated, read-only Data Plane serving one pre-approved immutable publication. It is a component of the production deployment task, not a complete App Mixer production stack: it does not deploy the Control Plane, agent workers, shared data stores, an identity provider.

The image reads a single `{ "version": 1, "definition": { ... } }` publication from a mounted file at startup, validates the definition, and keeps a snapshot in memory. `/application` serves it, `/application/versions/:version` serves that version only, and other versions return 404. Replacing the ConfigMap triggers a rollout; no Control Plane connection is needed at runtime. The bundled publication is a demonstration only. A release pipeline must authenticate, authorize, validate and approve the exact publication and protect the deployment and ConfigMap from unauthorized changes. The sample base explicitly enables unsigned mode and is for local testing only. It does not enforce tenant access or release freshness; rollback of the deployment can serve an older publication.

Build and push `Dockerfile.data-plane` to a trusted registry, pin both base images and the deployment image by approved digest, and use an environment-specific Kustomize overlay to replace the sample publication and image. For a local cluster smoke test only:

```sh
docker build -f Dockerfile.data-plane -t app-mixer-data-plane:test .
kind load docker-image app-mixer-data-plane:test
kubectl apply -n YOUR_NAMESPACE -k deploy/kubernetes/data-plane
kubectl rollout status -n YOUR_NAMESPACE deployment/app-mixer-data-plane
```

The base uses two replicas, a rolling update with zero unavailable replicas, liveness/readiness/startup probes, a disruption budget, resource limits, preferred node spreading, a non-root user, read-only root filesystem, dropped capabilities, runtime-default seccomp, and no service-account token. On SIGTERM the server fails readiness, serves for five seconds, then stops accepting connections; the 30-second termination grace period must be tuned for the ingress, workload and cluster. The disruption budget covers voluntary evictions and does not ensure availability during node failure; use multiple failure domains and test your scheduler, capacity and rollout strategy.

The local base explicitly uses HTTP and allows unauthenticated publication reads. The sample NetworkPolicy allows ingress only from labeled pods in the same namespace and denies egress, but policies require a CNI that enforces them; node-origin probes and service routing vary by platform. Pod labels are not authentication. Restrict who can create or relabel pods, configure namespace isolation, and place a trusted authenticated TLS gateway or service mesh in front of the service before exposing it. Verify all network rules and certificate/identity lifecycle on the target cluster. Only publish data all permitted clients may read; do not put credentials or private data into ConfigMaps. Define limits, monitoring, availability targets, backup and release controls appropriate to the environment.

CI builds the image, starts a disposable kind cluster, tests verified TLS, signed release startup, JWT access and tenant isolation, rejection of an altered release, two-replica readiness, a new publication rollout, and pod replacement. Kind's default network implementation does not validate NetworkPolicy enforcement, and the test does not prove production security, multi-node availability, disaster recovery, release authorization or production load capacity. Old generated ConfigMaps are not automatically removed; use an authorized retention process after confirming no workload needs them.

## Signed publication releases

The Data Plane defaults to signed mode when `APP_MIXER_PUBLICATION_MODE` is absent. The local example base explicitly sets `unsigned`; production deployments must use signed mode and enforce that configuration with their deployment and admission controls. `deploy/kubernetes/signed-example` shows a signed overlay for application `demo` in environment `production`. It requires an independently provisioned ConfigMap named `app-mixer-release-keys` containing `keys.json`, an array of `{keyId, publicKey}` entries where `publicKey` is an Ed25519 SPKI PEM. Configure the correct application and environment in a trusted overlay, secure the ConfigMap and deployment with RBAC, and pin the container image. The service reads at most 20 trusted keys at startup and rejects malformed configuration, unknown keys, altered content, and releases for a different application or environment before opening its listener.

An authorized release pipeline can create an artifact from an already approved publication:

```sh
node deploy/kubernetes/sign-publication.mjs publication.json signed.json private-key.pem release-key-1 production
```

The command requires a built workspace, creates the output only if it does not exist, and must run in a protected environment with the signing key supplied through an appropriate secret manager. Replace the base publication file with the signed artifact when rendering the signed overlay; never mount the private key into the Data Plane. The helper signs a JSON serialization of the publication, environment and key ID; preserve object member order when transferring the artifact. The signature establishes possession of a trusted signing key, not release approval, tenant authorization or currentness. Protect key registration and require independent approval and audit. A signature alone does not prevent replay or rollback; the optional shared release floor below adds a separate host-managed freshness control.

For key rotation, deploy a trust set containing both keys, restart the pods so they reload it, sign and roll out a release with the new key, then remove the old key and restart again. Existing processes keep their startup trust set and publication until restarted; ConfigMap changes do not revoke an already-running pod. An actor who can replace the image, disable signed mode or change trust roots can bypass verification. Use independent admission policies and control-plane access restrictions, and remove compromised keys promptly.

## Publication access with JWTs

The Data Plane defaults to JWT access when `APP_MIXER_ACCESS_MODE` is absent; the local base explicitly sets `public` for its sample. The `signed-jwt-example` overlay combines signed releases with JWT-protected publication reads and requires an independently provisioned `app-mixer-jwt-keys` ConfigMap containing `jwks.json`. Replace the example issuer, audience and tenant in a trusted environment-specific overlay, and enforce both signed and JWT modes with deployment and admission controls.

The service uses `createJwtCapabilityAuthenticator` to verify RFC 9068 RS256 access tokens against the startup JWKS. It requires the configured exact HTTPS issuer and audience, a valid access-token type and signature, required time and identity claims, a matching `tenant_id`, and a space-delimited `scope` containing `app-mixer:publication.read` (or `APP_MIXER_JWT_SCOPE`). `APP_MIXER_JWT_MAX_AGE_SECONDS` defaults to 600 and is bounded to 86,400. Missing, invalid or unauthorized tokens receive 403 for `/application` and versioned reads, including conditional requests; health probes remain unauthenticated. This is a single-tenant policy for the configured publication, not a general authorization or identity provisioning system. The host must obtain public keys from the trusted issuer, map its actual claims correctly, control issuer and audience, protect the ConfigMap, and maintain a trusted clock.

## Optional request metrics

Set `APP_MIXER_METRICS_PORT` to a distinct TCP port to enable the process-local Data Plane request counters and duration histograms on `GET /metrics`. This requires JWT publication access and binds a separate HTTP listener to `127.0.0.1`, intended for a trusted collector in the same pod. A valid token for the same issuer, audience and tenant must contain the separate `app-mixer:metrics.read` scope; a publication-only token cannot scrape it. The configured publication scope must differ from this scope. JWT revocation checks are reused when enabled, and errors deny the scrape. Requests and authentication are bounded, and the metrics listener closes during Data Plane shutdown. Loopback is shared by all containers in the pod; protect the collector and its credential, and use an encrypted, authenticated path from the collector to the monitoring backend. No Kubernetes Service or public listener is created for metrics. Series reset on restart and do not identify individual users or publications; see [request observations](data-plane-observability.md) for cardinality and operational limits.

The kind rollout check enables the listener in a test deployment and probes it from the pod, including token scope, tenant and revocation checks, the loopback binding, and denial while the revocation database is unavailable. It does not deploy a collector or validate a production monitoring backend.

JWT publication authorization uses per-process deadlines and concurrency limits. `APP_MIXER_PUBLICATION_AUTH_TIMEOUT_MS` defaults to 5,000 and accepts 100–30,000; `APP_MIXER_PUBLICATION_AUTH_MAX_PENDING` defaults to 100 and accepts 1–100. Saturated or timed-out authorization returns HTTP 503, while invalid tokens remain 403. Health probes do not use these slots. A timed-out check cannot start a subsequent release-floor lookup, and its slot remains occupied until the current callback settles; underlying JWT or PostgreSQL work is not forcibly cancelled. Limits are per pod process, not shared cluster-wide. Configure them with database pool capacity and upstream retries in mind. The public-access mode has no publication authorization checks.

JWT bearer tokens are sensitive. Use direct TLS or an authenticated TLS gateway or service mesh that encrypts the entire path to the pod, prevents bypass, and preserves the Authorization header. NetworkPolicy and pod labels alone do not authenticate clients or encrypt traffic. By default keys are loaded only at startup; roll pods after a trust-set change. To reload a trusted mounted JWKS without restarting, set `APP_MIXER_JWKS_RELOAD_MS` from 1,000 to 3,600,000 milliseconds (the sample admission guard permits only its listed intervals). The process reads at most 128 KiB, validates the entire replacement set before changing publication and metrics authentication, and rejects authentication started under a replaced set. Invalid or unavailable files retain the last valid set only until three reload intervals after the last successful read; then readiness fails and both authentication paths deny access until a valid read succeeds. Liveness remains independent. This is a per-process file poll, not remote JWKS or issuer discovery; protect and update the mounted trust source, monitor failures, and maintain an overlap during rotation. A removed key can remain valid for at least a polling interval, and restored older trusted files can restore older keys. A disposable kind test updates a projected ConfigMap across two unchanged replicas and checks overlap, removal, stale denial and recovery for publication and metrics authentication. It does not validate production key provisioning, propagation latency or node failure. The optional PostgreSQL revocation profile below can check individual tokens. Use short-lived tokens, restrict issuer access and remove compromised trust promptly. Authorization decisions are not independently audited by this profile.

## Direct TLS transport

The Data Plane defaults to TLS when `APP_MIXER_TRANSPORT` is absent; the local base explicitly sets `http`. The `signed-jwt-tls-example` overlay combines signed releases, JWT access and direct TLS. It mounts the `app-mixer-data-plane-tls` Kubernetes TLS Secret as `/tls/tls.crt` and `/tls/tls.key`, and configures HTTPS health probes. Provide a certificate valid for the service DNS names and a trusted CA to clients; clients must verify both certificate chain and hostname. The service loads certificate and private key at startup, enforces TLS 1.2 or later and fails startup for missing or invalid settings. Protect Secret access and configure admission to prevent downgrading transport or replacing the image. By default, certificate renewal and trust changes require a coordinated rollout. Setting `APP_MIXER_TLS_RELOAD_MS` (1000 to 86400000) makes the process re-read the certificate, key and optional client CA files at that interval, so renewed Secret files (for example from cert-manager, after the kubelet refreshes the mounted volume) take effect without a restart. Each new set is checked before use: the certificate must parse, match the key and be currently valid, and a client CA cannot be added or removed by a reload. An invalid or half-updated set is rejected and logged, and the server keeps its current credentials; new TLS connections use the new credentials, while existing connections continue with the ones they negotiated. Reloading does not renew certificates, notify clients of trust changes or replace a rollout when the CA itself changes; a Secret mounted with `subPath` is not refreshed by Kubernetes.

The same check is available to other hosts as `createTlsCredentialReloader(server, {load, intervalMs, clientCa, onReload?, onError?})` and `validateTlsCredentials(credentials)` from `@app-mixer/core`. `reloadNow()` applies a set immediately and rejects with the validation error; `stop()` ends polling. The reloader snapshots its loader, client-CA policy and callbacks when created; change those by creating a new reloader. The change fingerprint covers the complete supplied certificate chain and client CA bundle, so changing an intermediate certificate triggers a reload even when the leaf stays the same. Validation checks the leaf and key but does not establish that the supplied chain is trusted by clients; verify the chain and hostname from a client before deployment.

The application can also require client certificates by setting `APP_MIXER_TLS_CLIENT_CA_PATH` to a trusted CA bundle. This is independent of JWT authorization. The sample Kubernetes HTTP probes do not present client certificates, so enabling client-certificate authentication requires a separately designed authenticated health-check path or proxy; do not enable it with the sample probes unchanged. Kubernetes HTTPS probes do not verify server certificates, and therefore do not demonstrate client-side TLS verification. The cluster test separately verifies client trust using a test CA; its included test private keys are public and must never be used outside tests. NetworkPolicy, Secret security, issuer identity, certificate rotation, token revocation and production auditing still need target-cluster controls.

### Certificates issued by cert-manager

The `cert-manager-tls-example` overlay serves the unsigned, public-access Data Plane over TLS with a certificate that cert-manager issues and renews (a private CA stands in for your issuer; replace it with an enterprise CA, Vault or ACME). The certificate has the service names as subject alternative names and no subject, uses an ECDSA key, and gets a new key with every issuance. `APP_MIXER_TLS_RELOAD_MS=10000` makes each pod re-read the Secret, so a renewal needs no restart. Apply the same patches to the signed and JWT overlays for a real deployment. The DNS names assume the namespace `app-mixer-test`.

`deploy/kubernetes/test-support/cert-rotation.sh` (workflow `kubernetes-certificates.yml`, weekly and on main) runs it in a kind cluster with the Data Plane image and cert-manager v1.18.2. For each of the two pods it checks, reading the certificate over a port-forward:
- the issued certificate verifies against the CA and the service name, and not against another host name
- after a manual renewal (`cmctl renew`'s status change) each pod serves a new certificate with a new key, in the same container with no restart, and logs `TLS credentials active: DNS:...`
- for a CA rotation, a client holding both CAs verifies before and after the issuer changes, one holding only the new CA verifies the new leaf, and one holding only the old CA is refused. This is the order to follow: ship the bundle to clients, switch the issuer, then retire the old CA.

Kubelet propagates a changed Secret to the pod within about a minute, plus up to `APP_MIXER_TLS_RELOAD_MS`; the test waits up to five minutes. A certificate without a subject, which is what cert-manager issues unless you set `commonName`, used to make the reload log line fail silently (the reload itself worked); the information now carries `subject` (empty) and `altNames`.

## Capacity

`node scripts/bench-data-plane.mjs [seconds] [connections]` starts the container's start-up script with a mounted publication, drives it with a keep-alive load generator on the same machine and reports requests per second, latency percentiles, the server's CPU time per request and its memory. Measured on 2026-11-08 on a Windows x64 workstation (Node 24, 32 connections, 6 s per scenario, plain HTTP, the generator sharing the CPU):

| Scenario | Before: req/s, p99 | After: req/s, p99 | After: server CPU per request | Memory (RSS, peak) |
| --- | ---: | ---: | ---: | ---: |
| 2 KB publication | 21,200, 3.8 ms | 22,400, 3.4 ms | 0.04 ms | 83 MB |
| 100 KB publication | 3,100, 17 ms | 8,100, 10 ms | 0.11 ms | 83 MB |
| 1 MB publication | 280, 131 ms | 1,100, 52 ms | 0.80 ms | 85 MB (was 180) |
| 2 KB, conditional request (304) | 26,800, 3.2 ms | 26,200, 3.3 ms | 0.03 ms | 83 MB |
| 2 KB with a JWT (RS256, no revocation store) | 11,000, 7.0 ms | 17,500, 5.1 ms | 0.09 ms | 113 MB |

"Before" copied the publication and serialized it twice (once for the ETag, once for the body) on every request. Now the body is serialized once per request, and the start-up script, which holds one frozen publication, passes `immutablePublications: true` so the body and ETag are kept and reused. A host that builds the server itself can set the same option when its repository returns an object that never changes; with the option off, behaviour is unchanged except for the single serialization.

What the figures mean for sizing:
- One core serves tens of thousands of small responses a second; a JWT check adds about 0.05 ms of CPU. A 1 MB publication is limited by moving the bytes, about a thousand responses a second per core. Keep publications small and let clients send `If-None-Match`, which costs a tenth of the CPU and no body.
- The Deployment requests 50m CPU and 96Mi and limits memory to 256Mi. Memory was 83 to 113 MB under sustained load for these sizes, so the limit has room for publications up to the 1 MB the script accepts; revisit it if publications grow. CPU is the resource that scales with traffic, so set the request from your own request rate (about 0.04 to 0.09 ms of CPU per request here) and let the HorizontalPodAutoscaler, if you use one, follow CPU.
- These are single-machine figures over loopback. They exclude TLS, the PostgreSQL revocation check, the network and the readiness probes; measure with your own mix before fixing limits.

### PostgreSQL stores on the request path

`APP_MIXER_TEST_POSTGRES_URL=... node scripts/bench-postgres.mjs [seconds]` measures the revocation lookup (every JWT-protected Data Plane request makes one) and the capability audit append (every capability invocation makes one). Measured on 2026-11-08 against PostgreSQL 16 in Docker on the same Windows workstation (loopback, `synchronous_commit` on, 5 s per row, a pool of 64 connections):

| Operation | Concurrency | ops/s | p50 ms | p99 ms |
| --- | ---: | ---: | ---: | ---: |
| revocation lookup | 1 | 1,460 | 0.65 | 1.4 |
| revocation lookup | 16 | 12,000 | 1.3 | 3.2 |
| revocation lookup | 64 | 10,900 | 5.7 | 8.6 |
| audit append, one tenant | 1 | 330 | 2.9 | 5.1 |
| audit append, one tenant | 16 | 410 | 14 | 190 |
| audit append, one tenant | 64 | 430 | 94 | 840 |
| audit append, 16 tenants | 16 | 4,800 | 3.2 | 6.2 |
| audit append, 16 tenants | 64 | 6,400 | 8.3 | 33 |
| run lifecycle (create, claim, settle), one agent | 1 | 42 | 23 | 40 |
| run lifecycle, one agent | 8 | 190 | 41 | 99 |
| run lifecycle, one agent | 32 | 184 | 177 | 258 |
| run lifecycle, 8 agents | 8 | 397 | 20 | 27 |
| run lifecycle, 8 agents | 32 | 637 | 50 | 68 |
| run lifecycle, one agent with 200,000 finished runs | 8 | 210 | 39 | 47 |

- **The revocation lookup is cheap.** One indexed read, about 12,000 a second across a pool, so the revocation store is not the limit before the Data Plane itself is (about 17,000 JWT requests a second per core). Its cost in latency is a database round trip (0.65 ms here), which the network will add to.
- **Audit appends serialize per tenant.** Each tenant's sequence number comes from one counter row, so appends for one tenant run one after another, each holding the row until its commit is durable. Throughput for one tenant is therefore about one over the commit latency (here about 3 ms, so 330 to 430 a second) however many pods or connections there are, and under more concurrency the extra callers only queue: p99 grew from 5 ms to 840 ms. Different tenants do not interfere (4,800 to 6,400 a second across 16 tenants). A managed database with a slower durable commit lowers the per-tenant figure in proportion.
- **What to do with that.** The audit append is awaited on the invocation path, so a tenant that invokes capabilities faster than its commit rate sees every call slow down, and the sequence guarantees (gap-free, ordered, anchorable) are what cost this. Plan for roughly the reciprocal of your database's commit latency per tenant, rate-limit a tenant that can burst past it, and measure with `bench-postgres.mjs` against your own database before relying on a figure. A different sequence design (for example blocks of numbers per node) would raise the limit but give up gap-free ordering; that is a decision for the owner and has not been made.

The run rows are a whole durable run through `PostgresAgentRuns` (create, claim with a lease and settle, three transactions) by competing workers, with the per-agent concurrency limit raised so it does not refuse them:
- **One worker does about 40 runs a second** (23 ms for the three steps, which is a few durable commits). That is the cost of the registry's bookkeeping, not of running an agent, so runs that last seconds or longer make it negligible.
- **Claims for one agent serialize.** Each claim locks the agent's scope row and counts its active runs, so one agent is limited to about 190 lifecycles a second whatever the number of workers, and more workers only queue (p99 258 ms at 32). Several agents run in parallel (about 400 to 640 a second for eight agents).
- **History does not slow it down.** With 200,000 finished runs the same agent still did 210 a second: the active-run count and the queue use indexes, so an agent's backlog of finished runs costs nothing at claim time. (A first measurement right after bulk-loading history looked twice as slow; that was autovacuum and checkpoint work from the load, and vanished after `VACUUM ANALYZE`.)
- **Plan worker counts by the agent's own concurrency limit.** A single agent's `maxConcurrentRuns` already caps how many of its runs are active; workers beyond that wait. The supervisor reports a `limited` event when that happens.

## OpenShift (not verified)

The manifests have only been run on kind. A run on OpenShift Local (CRC 4.22.1, Kubernetes 1.35) on 2026-11-08 did not get as far as deploying them: with 11 GB for the virtual machine, the node's memory requests (11.2 GiB, mostly operators that were already installed) exceeded what it could allocate (10.25 GiB), so `openshift-controller-manager` stayed `Pending`, no service accounts were created in a new project, and the in-cluster image build failed. Running it needs a VM with roughly 15 GB or more.

What to expect there, from the manifests and OpenShift's documented rules rather than from a run:
- The default `restricted-v2` security constraint assigns each project a user ID range and rejects a pod that asks for a fixed `runAsUser` outside it. The base Deployment sets `runAsUser: 1000` and `runAsGroup: 1000`, so admission is expected to refuse it. An OpenShift overlay would remove those two fields and keep `runAsNonRoot: true`, `readOnlyRootFilesystem`, dropped capabilities and the `RuntimeDefault` seccomp profile.
- The process must then work as an arbitrary non-root user. The Data Plane writes only to the volumes you mount (the release-floor anchor claim and temporary files under `/tmp`), so that should hold, but it is untested.
- Use a Route with TLS re-encryption (or passthrough) instead of an Ingress, and keep the NetworkPolicies, which OpenShift supports.

## Shared token revocation

The `signed-jwt-tls-revocation-example` overlay combines signed releases, JWT access, direct TLS and PostgreSQL token revocation. JWT mode defaults to `postgres` revocation when `APP_MIXER_REVOCATION_MODE` is absent; the local base explicitly sets `disabled`. Provision the table and expiry index using the trusted migration connection described in [JWT capability authentication](jwt-capability-auth.md), before starting the Data Plane. This runtime only reads the revocation table and should use a dedicated role with the minimum required `SELECT` privilege. Create the `app-mixer-revocation-connection` Secret containing a `dsn` file and the `app-mixer-revocation-ca` ConfigMap containing `ca.pem`. The DSN must be a PostgreSQL URL with host, database, username and password and no query parameters. The server requires TLS with CA and hostname verification, bounded connection and query timeouts, and a small connection pool. Do not place database credentials in an image, ConfigMap, logs or source control.

Each JWT is checked against the configured issuer's shared revocation table after signature and claim validation. A revoked token or database error denies the request. Readiness also checks access to the revocation table, while liveness remains independent. This avoids accepting tokens during an unavailable or unprovisioned revocation store, but requests authenticated before a revocation may still finish. Use the same authoritative primary for revocations and checks, maintain safe token-ID retention and clock bounds, and provision high availability, backup, monitoring and failover controls. Database restore, stale replicas, compromised credentials or an incorrectly configured issuer can invalidate revocation guarantees. Protect and audit the separate administrator responsible for revoking tokens.

The overlay adds egress only to same-namespace pods labeled `app-mixer-revocations-db: "true"` on port 5432 and to CoreDNS in `kube-system`. Adapt it for your actual database, DNS implementation and CNI, and verify enforcement in the target cluster. Protect the Secret, CA and Deployment with RBAC and admission controls; prevent disabling JWT, TLS or revocation. The CI database manifest under `test-support` is disposable and uses ephemeral storage and test credentials; it is not suitable for production. CI checks revocation and fail-closed behavior during a database outage on a real PostgreSQL instance, but does not validate production failover or NetworkPolicy enforcement.

### Failover drill

`packages/core/test/postgres-revocation-failover.test.mjs` (opt-in with `APP_MIXER_TEST_POSTGRES_FAILOVER=docker`, run in CI) starts a PostgreSQL primary with a synchronous standby (`synchronous_commit=remote_apply`) behind a TCP proxy that stands in for the service address a platform repoints. It revokes a token, kills the primary, and checks that revocation lookups fail with a database error (which the authenticator turns into a denial) and that new revocations are refused while no primary exists. It then promotes the standby, repoints the proxy, and checks that the acknowledged revocation is still in force, that an unrevoked token is accepted again, and that a new revocation is accepted. The same cluster holds the release-floor registry: a floor advanced before the kill still refuses lower releases on the promoted standby, release checks fail while no primary exists, and the floor can be advanced again afterwards. The extension approval store is in the same drill: an approval granted before the kill is still in force on the promoted standby, a revoked one stays revoked, its two-event audit history survives, checks during the outage do not allow, and a new revocation takes effect afterwards. The shared capability audit log is in it too: three events recorded before the kill are still listed in order after promotion, an audit write during the outage fails (so an audited operation does not run), and the next event continues the tenant's sequence with no gap or duplicate. The authentication-failure audit log gets the same checks: two failures recorded before the kill survive, a write during the outage fails, and the next failure continues the sequence. The scripted promotion and repoint took under a second here; that measures the drill's own steps, not failure detection, which a real platform adds.

The drill proves nothing about asynchronous replication, where an acknowledged revocation can be lost if the primary fails before the standby receives it. Run the revocation database with synchronous replication to at least one standby, as the drill does. Automatic failover, detection time, split-brain protection, connection draining and the platform's address switch belong to the managed database or operator and have not been exercised in a production cluster.

### Restoring an older backup

`packages/core/test/postgres-restore-rollback.test.mjs` (opt-in with `APP_MIXER_TEST_POSTGRES_RESTORE=docker`, run in CI) records what happens when an older backup is restored over a live database. After the restore, none of these stores notices that it went back in time:

| Store | State acknowledged after the backup | After restoring the backup |
| --- | --- | --- |
| Token revocations | A token revoked after the backup | Active again |
| Release floor | A raised floor | Back at the old value, so a release below the new floor is allowed again |
| Extension approvals | An approval revoked after the backup | Granted again |
| Capability audit log | Two events | Gone, and the next event reuses sequence 4 with no sign of the gap |

Treat a restore as a security event, not only a data event. These steps are guidance and are not tested here: before accepting traffic again, raise the release floor to the last value in the release journal, re-apply the revocations and approval revocations recorded since the backup (from the identity provider, the change record or the log of the stopped primary), force re-issuance of tokens issued before the restore, and record the restore and its time window in your audit trail. Prefer point-in-time recovery to the latest consistent point over restoring an old snapshot, and prefer failover to a synchronous standby (see the failover drill) over restoring a backup at all. Only the remote connector's promotion floor can be anchored outside the target database today; the stores above have no independent anchor, which is why the P3-03 and P3-04 rollback-protection items stay open.

The drill proves nothing about asynchronous replication, where an acknowledged revocation can be lost if the primary fails before the standby receives it. Run the revocation database with synchronous replication to at least one standby, as the drill does. Automatic failover, detection time, split-brain protection, connection draining and the platform's address switch belong to the managed database or operator and have not been exercised in a production cluster.

## Admission guard for the Data Plane

The optional `admission-example` uses the Kubernetes `admissionregistration.k8s.io/v1` ValidatingAdmissionPolicy API. A security administrator can bind it only to namespaces labeled `app-mixer.dev/enforce-data-plane=true`, with a separately managed `app-mixer-security-policy` ConfigMap in each namespace. Its data keys are `image`, `releaseEnvironment`, `applicationId`, `issuer`, `audience` and `tenantId`. `image` must be the exact approved image reference pinned by SHA-256 digest. Install the policy and binding with cluster-admin authority, create and protect the parameters, then label a test namespace and use server-side dry runs before enforcement in production. Kubernetes must support and enable ValidatingAdmissionPolicy; see the [Kubernetes documentation](https://kubernetes.io/docs/reference/access-authn-authz/validating-admission-policy/). A missing parameter fails closed. Deployment writers may need permission to read the referenced parameter resource.

For the Deployment named `app-mixer-data-plane`, the example requires one approved container, fixed signed/JWT/TLS/PostgreSQL revocation and release-floor modes and paths, issuer/application/tenant values matching the protected parameters, the expected trust and credential volumes, HTTPS probes and restricted pod/container security settings. A separate policy and binding enforce the same two-replica minimum on Deployment scale updates, including autoscaler requests. A separate deletion policy and binding deny individual deletion of the named Deployment, including `kubectl delete --all` while the namespace is labeled; removal requires an administrator to change the guard or namespace label. The Service policy requires the named Service to remain a non-headless ClusterIP with no external IPs, the exact Data Plane selector, cluster-wide internal routing, ready endpoints and one TCP port 3002 targeting `http`; it also denies its deletion. These checks prevent the Service from silently restricting traffic to node-local endpoints or publishing unready pods, but do not prevent other workloads from matching the selector. Another policy and binding protect the named `app-mixer-data-plane` PodDisruptionBudget: create and update require `minAvailable: 1` and the exact two-label Data Plane selector, and deletion is denied while the namespace is labeled for enforcement. Other disruption budgets are outside this rule. An authorized administrator must adjust enforcement for planned removal or namespace cleanup; protect the binding and namespace labels with separate controls. A [PodDisruptionBudget](https://kubernetes.io/docs/concepts/workloads/pods/disruptions/) only constrains eligible voluntary evictions, not node failures, workload deletion or all forms of disruption. The Deployment must have at least two replicas, use the sample rolling update (zero unavailable and one surge), and allow at least ten seconds of termination grace. The readiness, liveness and startup probes must use their approved paths on the named local TCP listener at port 3002, without an alternate host or custom headers; extra declared container ports and host ports are rejected. The admission example also rejects a paused Deployment, limits `minReadySeconds` to 60 and requires `progressDeadlineSeconds` between 60 and 1,800 seconds. These are sample operational bounds: adjust and test them for startup and rollout behavior before enforcing the guard. Kubernetes reports a missed progress deadline as a Deployment condition; this guard does not automatically roll back or alert. The guard also constrains probe timing: readiness period at most 5 seconds, timeout at most 5 seconds, failure threshold at most 2 and success threshold 1; liveness period at most 30 seconds, timeout at most 5 seconds and failure threshold at most 6; startup period at most 10 seconds, timeout at most 5 seconds, failure threshold at most 60 and period multiplied by failure threshold at most 300 seconds. Initial delays are at most 5 seconds for readiness and 30 seconds for liveness and startup. A liveness or startup probe-level termination grace, if specified, must be at least 10 seconds, so it cannot silently override the pod grace with a shorter drain window. Readiness cannot have a probe-level grace. Kubernetes documents [probe timing and probe-level grace behavior](https://kubernetes.io/docs/tasks/configure-pod-container/configure-liveness-readiness-startup-probes/). These bounds reduce the risk of deployments delaying detection of unavailable instances or cutting short draining; they do not guarantee actual recovery times, protect against node failure or establish suitable thresholds for every workload. Test and adapt them to observed startup and shutdown behavior on the target cluster. The optional variables it permits beyond the approved set include, each at most once, `APP_MIXER_PUBLICATION_AUTH_TIMEOUT_MS` (100–30,000), `APP_MIXER_PUBLICATION_AUTH_MAX_PENDING` (1–100), `APP_MIXER_METRICS_PORT` (a TCP port from 1 to 65535 other than the service port 3002, which the CI rollout sets to exercise metrics) and `APP_MIXER_TLS_RELOAD_MS` whose value is one of 10,000, 30,000, 60,000, 300,000, 900,000 or 3,600,000 milliseconds (a fixed list keeps the policy's evaluation cost constant; edit it to suit your rotation tooling, within the Data Plane's own 1,000 to 86,400,000 range), which enables the TLS credential reload described above; CI dry-runs the accepted values and the rejected unlisted, malformed, duplicate and unrelated variables. It rejects other extra environment variables, entrypoint overrides, init containers, sidecars, alternate key selections and common privilege escalation settings. It intentionally fixes the current sample's 5,000 ms drain delay and default JWT scope/age; update and review the policy together with any deployment changes. CI exercises accepted and rejected server-side dry runs and missing parameters on a disposable cluster.

This is a targeted guard, not a complete cluster security boundary. It checks only that named Deployment on create/update and its scale subresource; it does not govern direct Pods, other workloads or labels that could impersonate the Service selector, changes to unrelated Services or NetworkPolicies, unrelated deployments or disruption budgets, admission resources, trust ConfigMaps, Secrets, namespace labels, or the integrity and freshness of their contents. It does not verify the image signature or release provenance. Restrict those actions and policy parameters with separate RBAC, admission, image verification, network and release controls. Cluster administrators can change or remove the guard. Review fail-closed behavior, policy compatibility, recovery access and deployment-writer parameter-read permissions on the target cluster before enabling it.

## Shared release floor

The `signed-jwt-tls-revocation-fresh-example` overlay enables `APP_MIXER_RELEASE_FLOOR_MODE=postgres`. It requires signed publication mode, JWT tenant binding and the same TLS-protected PostgreSQL primary used for revocation. A `PostgresPublicationReleaseRegistry` can provision two tables using a trusted migration connection and provides `register(scope, version, definitionDigest)`, `advanceFloor(scope, version)` and `isAllowed(scope, version, definitionDigest)`. The scope is the host-selected tenant, application and environment. Register an independently approved version with the lowercase `definitionSha256` digest of its verified definition; the same scoped version cannot be registered with another digest through this API. `advanceFloor` requires a registered version and concurrent calls cannot lower the stored floor. A missing floor, missing authorization, mismatched digest or database error prevents readiness and publication reads. The Data Plane checks the authoritative primary on each read and readiness probe; a request that passed its check before the floor advanced may still finish.

To roll out without deliberately taking every replica offline, register the new approved version first while the old version remains above the current floor, roll out and verify the new version, then advance the floor to the new version. During that overlap the older release remains acceptable. After advancing, older signed versions and new content using an existing version are denied. A deliberate rollback requires a new, higher version containing the reviewed older content. The optional admission guard requires floor mode for the named deployment. The floor is disabled in earlier sample overlays.

This registry does not verify signatures, approve releases, authenticate administrators or provide independent audit; the release pipeline must do so before registration. Provision the runtime database role with read-only access to both release tables and the revocation table, and restrict administrative writes to a separate authorized identity. Protect the primary, schema, credentials and backups from rollback or substitution, use autocommitted reads from the current primary, and provide production failover and monitoring. A privileged database administrator or deployment administrator who can disable the guard or replace trust roots can bypass these controls. Restoring an older database can lower the floor; independent rollback-resistant storage and target-cluster controls remain necessary. The test database is disposable and must not be used for production.

## Multi-node failure exercise

The `kubernetes-node-recovery.yml` workflow builds the Data Plane image in a disposable kind cluster with two worker nodes. The test applies the sample Deployment with the strict-placement component, scales it down and then to two replicas, and verifies the publication through both pods and the Service. It separately stops one worker container and disconnects one worker from the disposable kind network, waits until the affected endpoint is no longer ready, verifies the surviving Service and pod, restores the node or network, and checks that both replicas and endpoints return. It then temporarily makes the disposable control-plane node a third eligible host, rolls out an updated pod template and checks that the Service retains a ready endpoint and both new replicas are available on distinct hosts. It also server-dry-runs the protected overlay. The workflow also exercises a signed publication with JWT tenant authorization and direct TLS during a worker network partition. It creates temporary release and JWT keys, uses a checked-in test TLS certificate, and checks that missing or wrong-tenant credentials are rejected before and after failure and rollout. The complete workflow, including this secured partition scenario and the zone and admission checks, passed in [GitHub Actions run 41546756741](https://github.com/bassemZohdy/app-mixer/actions/runs/41546756741). These exercises run on a single machine; they do not test production identity or certificate operations, shared revocation or release-floor databases, real node or cloud network failures, durable databases, or multi-zone availability.

The shipped Deployment uses preferred anti-affinity and can place both replicas on the same node. The optional `strict-placement-example` combines the signed/JWT/TLS/revocation/release-floor overlay with the `strict-placement` component, which requires distinct hostname values for matching Data Plane pods at scheduling time. The failure test applies the same component to the local unsigned example. Required anti-affinity can leave a replica pending if too few eligible nodes are available. With two replicas and the existing `maxUnavailable: 0`, `maxSurge: 1` rolling strategy, an ordinary rollout also needs capacity on a third eligible node; otherwise the rollout can stall until capacity is added. With more replicas, provision sufficient separate nodes and spare rollout capacity. This constraint does not enforce cross-zone placement. The optional `strict-placement-admission` policy and binding can separately protect the named Deployment's required hostname anti-affinity, exact selector and matching pod labels in namespaces labeled `app-mixer.dev/enforce-strict-placement=true`. They reject direct node assignment, a non-default scheduler, alternate namespaces and dynamic selector keys. Install the overlay before enabling the label, combine this policy with the existing security admission policy, and protect both bindings, namespace labels and policy objects with administrative RBAC. The guard cannot prove sufficient node capacity, scheduler integrity, real failure-domain separation or that unrelated workloads cannot affect scheduling. It does not govern direct Pod creation or mutation, namespace labels, policy resources or other deployments; restrict those separately. The node-recovery workflow runs server-side acceptance checks for the guard, including namespace opt-in and placement bypasses. Its CEL fields must be supported by the target Kubernetes version; test server-side dry runs and recovery access before enabling it. Production operators must choose and verify placement, node capacity, disruption controls and failure behavior for their cluster. The optional `zone-placement-example` adds a required anti-affinity term for `topology.kubernetes.io/zone` to the strict-host protected overlay. Matching replicas are scheduled in distinct labeled zones as well as distinct hosts. This is a scheduling constraint: node labels must reflect real independent failure domains, existing pods are not moved if labels change, and a missing or unavailable eligible zone can leave a replica pending. For two replicas with the existing zero-unavailable surge rollout, provide a third eligible zone with capacity; otherwise updates can stall. The strict-host admission policy permits a correctly formed zone term but does not require it to remain present. To guard both rules, install the optional `zone-placement-admission` policy and binding and label the namespace `app-mixer.dev/enforce-zone-placement=true` after deploying the zone overlay. It requires the exact host and zone terms, matching pod labels and the default scheduler, and rejects alternate namespaces, dynamic selector keys and direct node assignment. It can be combined with the host and general security guards. Protect namespace labels, policy resources and direct Pod access separately; the guard cannot verify that zone labels represent real independent infrastructure or that enough eligible capacity exists. The node-recovery workflow simulates zone labels on kind nodes and exercises loss, recovery and a three-domain rollout. A separate capacity scenario verifies that a second replica stays pending when only one zone is eligible, becomes ready when a second appears, and that a zero-unavailable rollout keeps two ready endpoints while its surge waits for a third zone, then completes when that zone is added. These tests do not simulate a real cloud zone failure.

A forced stop also does not test graceful node draining.

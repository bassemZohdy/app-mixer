# Local durable agent-run registry

`SqliteAgentRuns` stores run lifecycle records scoped by tenant, agent and run ID. `create` pins a definition version, maximum attempts and absolute deadline, and starts in `queued`. `get` and paginated `list` inspect records; archived terminal runs are excluded from lists unless explicitly requested. A host must verify the referenced agent definition, its enabled status and policy before creating or claiming a run. The registry does not load definitions or store run input.

`claim` moves a queued run to `running`, increments attempts and grants a random lease token with an expiration bounded by the run deadline. `renew` and `settle` require the current token, a live lease and the expected run revision. Every state change increments the revision and is serialized in SQLite; stale concurrent claims and stale worker completions are rejected. Hosts must protect lease tokens and provide trusted, consistent time.

Pausing or cancelling a running run records a request; it does not claim the worker has stopped. The worker must stop cooperatively and acknowledge `stopped`, or report a completed or uncertain outcome. Queued runs can pause or cancel immediately; paused runs can resume while attempts remain. Only terminal runs can be archived. Expired running leases become `uncertain` through `recoverExpired`; they are never automatically replayed. Before `reconcile`, the host must establish that the old worker has stopped and determine the external outcome. Retry is allowed only when the host has verified it is safe, attempts remain and the deadline has not passed. A database lease does not fence an external API, so idempotency and an action journal are still required.

A trusted host can call `expiredLeasePage(scope, now, {after?, limit?})` to scan expired running, pause-requested and cancel-requested leases in lease-time and run-ID order. Pages return only run ID, revision, status and lease expiry; they do not return lease tokens, owners, inputs or results. This direct method does not authenticate or authorize callers. Pages are bounded to 100, are not a consistent cross-page snapshot, and changes before a cursor require another scan. `registerAgentExpiredLeaseDiscovery` optionally exposes a fixed-scope capability accepting `{query: {cursor?}}`. The host fixes a page size and a 32-byte cursor key, and provides separate `list` and per-lease `read` policy decisions. Returned records and list access are rechecked, and the lease revision and expiry are verified again before returning. Continuation cursors are encrypted, fixed-size and bound to the tenant, agent, authenticated principal and operation; filtered pages may be empty while still carrying a cursor. Key rotation invalidates old cursors. Optional paired `timeoutMs` and `maxPending` bound individual asynchronous policy calls; uncooperative callbacks keep their slots until they settle. An initially denied record is filtered out; a revoked permission returns HTTP 403, a changed lease 409, and policy timeout or saturation 503. The host must authenticate callers and authorize the whole listing; this does not recover, retry or prove that a worker stopped.

## Host-driven worker

`DurableAgentWorker.runOnce(scope, runId)` runs one explicitly selected queued record. It checks the current enabled definition and the pinned version, calls host `authorizeStart` before and after claiming, then invokes the host's `execute` callback with an abort signal and `assertLease`. It periodically renews the lease and aborts on a pause/cancel request, changed definition, lost lease or deadline. The host can use `createConfiguredAgentRun` within `execute` and call `assertLease` from the capability authorization callback immediately before each operation.

For a shared asynchronous definition lookup, set `asyncDefinitions: true` and await `assertLeaseAsync` in the host's authorization callback immediately before each protected operation. In this mode synchronous `assertLease` fails closed. The worker rechecks the definition before claim, before execution, during serialized lease renewals and before accepting successful or failed execution; a failed renewal aborts an active run and leaves its outcome uncertain. `assertLeaseAsync` checks the local lease both before and after the remote lookup. The definition read and local lease transaction are not atomic, so changes may occur after a check; external effects still need idempotency and reconciliation. Local lease and cancellation checks continue while a definition renewal is pending. Once the local lease is lost or execution finishes, the worker stops waiting for an obsolete lookup and ignores any late result; when available, `getWithSignal` also receives a cancellation signal for in-flight run-time checks. Providers that ignore the signal may continue running in the background. Pre-claim lookups and other host callbacks still require bounded timeouts; shared-slot operations also need bounded database behavior. As with any lease, a previously dispatched external call cannot be recalled.

The worker can optionally receive `tracing: {tracer}` with a host-configured OpenTelemetry tracer. Each `runOnce` call creates an `agent.run` internal span under the caller's active context and makes it active while checking policy, claiming, executing and settling. The span records only a fixed final run-state value; a failed or uncertain outcome, or an exception, is marked as an error without exception details. It does not record tenant, agent, run, worker, lease, prompt, model output or action identifiers. Instrumentation errors do not cause the worker to replay or skip execution. The host must configure the SDK, context manager, sampler and exporter, and review any separately instrumented model or capability calls for sensitive data.

For cross-process correlation, a trusted host may supply a version-00 W3C `traceParent` when creating a run or enqueueing an event. It is stored atomically with the run and cannot be changed; duplicate events retain the original context. Configure the worker with `tracing: {tracer, usePersistedParent: true}` to use that context as the remote parent, including after reopening the database. With the option disabled, or when no valid context is available, the worker uses its active context. Only the traceparent is stored; tracestate and baggage are excluded. The host must authenticate the source of any context it accepts: request authentication alone does not establish trust in an arbitrary trace header. Trace context is not authorization, and a remote sampling flag can affect the host's sampler. Protect the database and backups, and plan retention; these records are retained indefinitely. Schedulers do not capture context automatically.

A span reports the local attempt, not a complete audit or proof of external effects; a process crash can prevent it from being exported. Distributed tracing policy and production observability remain host responsibilities.

The host returns `succeeded`, `failed`, `stopped` or `uncertain` only when it can substantiate that outcome. A thrown error after execution starts or an unrecognized result is recorded as uncertain. `stopped` acknowledges a pause or cancel only when the worker has stopped safely; otherwise it becomes uncertain. A lost or expired lease prevents settlement and requires `recoverExpired` and explicit reconciliation. Cancellation and lease loss are cooperative: an implementation that ignores the signal can continue running, and a lease check cannot fence an external system. Never automatically retry an ambiguous external action; use the [action journal](agent-action-journal.md) and external idempotency.

The host can drive individual runs or use the optional dispatcher below. It obtains trusted input, protects lease tokens, supplies authorization and policy-enforced capabilities, and must wait for an old worker to stop before reconciling. The worker enforces the configured local concurrency limit but does not store input or output, automatically select checkpoints, or implement production identity. The worker snapshots its validated settings and callback references at construction; replace it to change those settings. Referenced definition stores and callback-owned policy state remain live. Optionally set both `startupCallbackTimeoutMs` (100 to 30,000 milliseconds) and `maxPendingStartupCallbacks` (1 to 100) to bound asynchronous definition lookups and authorization at startup, including the second authorization after claim. `authorizeStartWithSignal` may supply a cancellation-aware policy and takes precedence over `authorizeStart`; the latter remains required. Asynchronous definitions use `getWithSignal` when provided. On timeout, the signal is aborted and late results cannot start execution; uncooperative callbacks retain capacity until they settle. A pre-claim timeout leaves the run queued; an authorization failure after claim follows the existing pre-execution failure handling. These bounds are per worker and do not bound synchronous code, shared-slot calls, execution, or every later lease-validation callback. A process crash remains uncertain until manually reconciled.

## Local queued-run dispatcher

`DurableAgentDispatcher` optionally polls one host-selected tenant and agent. Construct it with the same `SqliteAgentRuns` instance used by a configured `DurableAgentWorker`, a bounded `maxPerPass` (1â€“100), a polling interval, and an `onError` callback. `start()` enables polling; `runOnce()` performs one pass without enabling a timer. Each pass scans queued run IDs in bounded pages and executes them sequentially through the worker, which still checks definitions, policy, quotas and leases. Failed claims or authorization checks are reported per run and do not block later IDs; the in-memory cursor wraps after the last page. Restarting loses the cursor, and a run queued before it is reached on the next scan. The dispatcher captures its configured scope, limits, worker and callback references at construction; create another dispatcher to change them. Referenced stores and callback-owned state remain live. `SqliteAgentRuns.queuedPage` is also available for trusted hosts; it is not an authorization boundary or a consistent snapshot across pages.

`stop()` prevents selecting further runs in polling or a manual pass and waits for the current worker invocation to finish. It does not cancel that invocation, including an authorization or external operation already in progress; the host must request cancellation through the run registry when appropriate. Polling is local to one process and scope; competing dispatchers rely on the existing SQLite claim and concurrency checks. The dispatcher does not recover expired leases, retry uncertain runs, or verify external outcomes. The host must secure the database, provide authenticated policy and input, handle errors and retention, and establish that old workers have stopped before reconciliation. Long-running or uncooperative execution can delay stopping indefinitely.

## Expired queued and paused runs

A queued or paused run whose deadline has passed cannot start another attempt. A trusted host can call `expiredPage(scope, now, {after?, limit?})` to scan them by deadline and run ID, and `expireDeadline(scope, runId, revision, now)` to mark an eligible run failed. The transition rechecks the deadline and revision in a SQLite transaction, clears approval and delegation waits, and records the ordinary lifecycle transition. Resuming any paused run at or after its deadline is rejected. No queued or paused run is expired automatically by default.

## LangGraph checkpoints

`SqliteAgentCheckpointer` implements the LangGraph checkpoint saver contract for a single tenant, agent and run. Open it against the same SQLite database as the run registry, passing the active lease token. Checkpoints and pending writes persist across restart, preserve parent and task-write ordering, and are partitioned by run and LangGraph namespace. Writes and thread deletion verify the current run lease within the same SQLite transaction; an expired or replaced worker cannot write. Reads are scoped by the saver but are not authorization checks. The host must authorize access, protect lease tokens, close the saver after all operations finish, and protect the database and backups: checkpoints may contain sensitive prompts, messages and tool results and are not encrypted.

A host can pass `{saver, threadId: runId, resume: false}` as `checkpoint` to `createConfiguredAgentRun`; a fresh invocation refuses an existing checkpoint. After a crash, the host must first establish that the old worker stopped, reconcile the uncertain run, claim a new lease, and construct a new saver with that token. Only then may it explicitly use `resume: true`. The checkpoint thread ID must match the run ID. The resumed graph uses saved state rather than the supplied messages. A missing checkpoint fails closed. The host must preserve graph, model and tool compatibility across attempts.

A checkpoint records execution state, not the outcome of an external side effect. A crash after dispatch and before its result is saved can cause a resumed node to repeat the call. Do not resume such a run until the external outcome has been reconciled and replay is safe; use the [action journal](agent-action-journal.md) and a downstream idempotency contract; automatic reconciliation remains open. The host-driven worker does not automatically create a saver or decide when resume is safe.

## Waiting for delegation renewal

When a configured agent encounters an expired delegation before dispatch, its terminal AG-UI event has code `AGENT_DELEGATION_EXPIRED`. A host using a persisted grant and a journal for **every** external effect can map that event to the worker outcome `{status: 'delegation_expired', grantId: grant.grantId, revision: grant.revision}` after execution has stopped. The worker verifies the live lease, exact expired grant revision and absence of `dispatching` or `uncertain` journal entries in the same database transaction before recording the run as `paused`. An unclassifiable error, an expiry inside a journal dispatch, a changed grant, missing journal table or an unresolved action results in `uncertain` and requires explicit reconciliation. An expiry event alone is not proof that an arbitrary host integration has stopped all effects; the host must return this outcome only after establishing that fact.

A paused run exposes `delegationWait` with the grant ID, user and expired revision, allowing the host to request renewal from an authorized person. A durable local inbox records the renewal request; external notifications are not sent. See [agent approvals](agent-approvals.md). After authorized renewal, `runs.request(scope, runId, revision, 'resume')` atomically requires a newer, unrevoked, unexpired revision of that same grant and user, an unexpired run deadline and remaining attempts. Cancellation clears the wait. The host must authorize administrative operations, verify current delegated policy again, and select a safe checkpoint/replay strategy before starting a new worker; a renewal does not itself start the run. A crash, lease loss, or action whose outcome is unknown still requires the existing stop-and-reconcile procedure.

## Waiting for approval

A host can classify a configured run's `AGENT_APPROVAL_REQUIRED` event using `pendingApproval()` and return an `approval_required` worker outcome after all execution has stopped. The run is paused with its action ID only if the pending (or just-approved) request and live lease match and the action journal contains no unresolved dispatches. Resume is explicit and requires the corresponding approval to remain approved and unexpired. Cancellation clears the wait; rejected or expired requests cannot resume it. The worker falls back to `uncertain` if these checks fail. The host must journal every effect, authorize administrative operations, and establish a safe checkpoint or deterministic replay strategy; a pause does not prove arbitrary external host code has stopped. See [agent approvals](agent-approvals.md).

## Daily run quota

`DurableAgentWorker` enforces the current definition's `maxRunsPerDay` together with `maxConcurrentRuns` when claiming a run. The SQLite claim transaction records the first successful claim for each tenant, agent and run, and counts distinct first starts in the current UTC calendar day. Competing local workers share the same limit. A denied claim leaves the run queued and does not consume an attempt. Retries and resumption of the same run do not consume another slot, even on a later day; they still obey the attempt, deadline and concurrency limits. A changed definition is checked before claim, and a lower daily limit takes effect for subsequent new starts.

Direct callers of `SqliteAgentRuns.claim` can supply `maxRunsPerDay` as the final argument. Omitting it leaves the direct claim unlimited but still records its first start for later quota enforcement. Hosts must not bypass configured-worker enforcement when the quota is required, must supply a trusted consistent clock and coordinate all workers on the same SQLite database. Start records are durable and currently retained indefinitely. Runs last started before this feature cannot be reconstructed because earlier records did not store their first-start times; a legacy run is counted on its first subsequent claim. Provider-specific token enforcement, cost budgets, a distributed quota service, and production retention remain open.

Configured agents can separately opt in with `tracing: {tracer}`. Each model invocation and each schema-validated capability invocation creates an `agent.model` or `agent.capability` internal span under the active context. With a host-configured asynchronous context manager, these spans can be children of the durable worker's `agent.run` span. Spans contain only fixed operation outcomes and fixed error categories; they omit tenant, agent, run, call, operation and principal IDs, prompts, outputs, tool arguments, credentials and usage amounts. Expected approval or delegation waits also end their capability span as failed. Malformed tool inputs rejected before capability invocation have no capability span. Tracing failures are ignored and never deliberately repeat an operation.

The host controls sampling, context management, exporters, transport, access and retention. Additional instrumentation supplied by the host or its dependencies may capture sensitive information or introduce spans between these operations and the worker. These spans do not propagate trace headers to a model provider, establish that an external effect occurred, or replace the action journal, budget reconciliation or an audit record.

`ConfiguredAgentOperationMetrics` optionally collects process-local counts and latency histograms for configured model and capability operations. ## Shared run slots

`SqliteAgentRuns` enforces `maxConcurrentRuns` and `maxRunsPerDay` only within one database file, so workers on separate nodes with their own registries could each reach the limit. `PostgresAgentRunSlots({enabled: true, query, transaction})` adds an optional shared limiter on one PostgreSQL primary; call `initialize()` once. Pass it to `DurableAgentWorker` as `sharedSlots`. Before its local claim, the worker acquires a slot for the run under a per-agent row lock, enforcing the manifest's concurrency and distinct-runs-per-UTC-day quotas across every worker using the database. A full agent fails with `Agent run quota exceeded` and leaves the run queued. Retries of a run already counted that day do not consume another daily slot, and a run cannot hold two slots at once.

Slots expire on database time after the worker's lease duration, so a crashed worker's slot frees itself; expired slots are removed on the next acquisition for that agent. The worker renews the slot with every local lease pulse. If execution ends while a renewal is pending, the worker allows a bounded 100�1000 ms grace period; on cancellation or after that grace period, it stops waiting and records an uncertain outcome unless a cooperative stop can be acknowledged. The worker then attempts to release the exact slot token; a late renewal cannot recreate a successfully released slot. If release fails, an outstanding renewal may extend the slot before it expires, temporarily reducing capacity. If renewal fails because the slot expired or was removed, the worker aborts execution as it does for a lost local lease. The slot is released after settlement, or immediately if the local claim fails. `active(scope)` reports unexpired slots, and `pruneStarts(retainDays)` deletes old daily counters.

Set `verifySharedSlotAtUse: true` on a worker with `sharedSlots` to make `assertLeaseAsync` check that the exact shared slot token is still unexpired immediately before protected work. In this mode `assertLease` fails closed, so hosts must await `assertLeaseAsync`; a missing slot or failed check aborts the run and prevents a successful outcome from being accepted. The option is fixed when the worker is created. `holds(scope, runId, token)` is also available for trusted hosts. These checks add a PostgreSQL read. Cancellation fences a late result, but the underlying query may continue, so hosts must bound database operations and release calls. A PostgreSQL integration test connects this check to a configured agent capability and verifies normal dispatch and rejection after a slot disappears during a model call. The check and a later external effect are not atomic; a slot can expire after the check, so external idempotency and reconciliation remain necessary.

A PostgreSQL-backed process-termination test kills a worker after slot acquisition and during execution. It verifies that another tenant remains isolated, the dead slot expires, the daily distinct-run limit persists, and an interrupted local run becomes uncertain and requires explicit reconciliation before retry. This uses a local PostgreSQL instance and SQLite file; it does not establish behavior for node failure or production storage.

Slots limit execution, not queued runs; the local registries still own run state, leases and recovery. Database time avoids clock skew between workers but makes availability depend on PostgreSQL: if it is unreachable, workers cannot start runs. A worker paused for longer than its lease can lose its slot while another worker starts a run, so keep leases longer than expected pauses and treat an aborted run's outcome as uncertain. Use a restricted role, trusted `search_path` and statement timeouts, and direct all workers to the same current primary.

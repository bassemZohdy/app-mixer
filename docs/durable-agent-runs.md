# Local durable agent-run registry

`SqliteAgentRuns` stores run lifecycle records scoped by tenant, agent and run ID. `create` pins a definition version, maximum attempts and absolute deadline, and starts in `queued`. `get` and paginated `list` inspect records; archived terminal runs are excluded from lists unless explicitly requested. A host must verify the referenced agent definition, its enabled status and policy before creating or claiming a run. The registry does not load definitions or store run input.

`claim` moves a queued run to `running`, increments attempts and grants a random lease token with an expiration bounded by the run deadline. `renew` and `settle` require the current token, a live lease and the expected run revision. Every state change increments the revision and is serialized in SQLite; stale concurrent claims and stale worker completions are rejected. Hosts must protect lease tokens and provide trusted, consistent time.

Pausing or cancelling a running run records a request; it does not claim the worker has stopped. The worker must stop cooperatively and acknowledge `stopped`, or report a completed or uncertain outcome. Queued runs can pause or cancel immediately; paused runs can resume while attempts remain. Only terminal runs can be archived. Expired running leases become `uncertain` through `recoverExpired`; they are never automatically replayed. Before `reconcile`, the host must establish that the old worker has stopped and determine the external outcome. Retry is allowed only when the host has verified it is safe, attempts remain and the deadline has not passed. A database lease does not fence an external API, so idempotency and an action journal are still required.

This is a local lifecycle primitive, not a durable execution engine. The host must authenticate and authorize every operation, validate scope and definition references, coordinate workers, securely store input/checkpoints, enforce token and cost quotas, and handle cancellation and reconciliation. The optional local scheduler is described in [agent schedules](agent-schedules.md); distributed clocks, production identity and actor-level audit remain open. Registry state alone cannot prove that external effects did or did not occur.

## Host-driven worker

`DurableAgentWorker.runOnce(scope, runId)` runs one explicitly selected queued record. It checks the current enabled definition and the pinned version, calls host `authorizeStart` before and after claiming, then invokes the host's `execute` callback with an abort signal and `assertLease`. It periodically renews the lease and aborts on a pause/cancel request, changed definition, lost lease or deadline. The host can use `createConfiguredAgentRun` within `execute` and call `assertLease` from the capability authorization callback immediately before each operation.

For a shared asynchronous definition lookup, set `asyncDefinitions: true` and await `assertLeaseAsync` in the host's authorization callback immediately before each protected operation. In this mode synchronous `assertLease` fails closed. The worker rechecks the definition before claim, before execution, during serialized lease renewals and before accepting successful or failed execution; a failed renewal aborts an active run and leaves its outcome uncertain. `assertLeaseAsync` checks the local lease both before and after the remote lookup. The definition read and local lease transaction are not atomic, so changes may occur after a check; external effects still need idempotency and reconciliation. Set bounded timeouts on the host's lookup: an outstanding renewal must finish before the worker settles. As with any lease, a previously dispatched external call cannot be recalled.

The worker can optionally receive `tracing: {tracer}` with a host-configured OpenTelemetry tracer. Each `runOnce` call creates an `agent.run` internal span under the caller's active context and makes it active while checking policy, claiming, executing and settling. The span records only a fixed final run-state value; a failed or uncertain outcome, or an exception, is marked as an error without exception details. It does not record tenant, agent, run, worker, lease, prompt, model output or action identifiers. Instrumentation errors do not cause the worker to replay or skip execution. The host must configure the SDK, context manager, sampler and exporter, and review any separately instrumented model or capability calls for sensitive data.

For cross-process correlation, a trusted host may supply a version-00 W3C `traceParent` when creating a run or enqueueing an event. It is stored atomically with the run and cannot be changed; duplicate events retain the original context. Configure the worker with `tracing: {tracer, usePersistedParent: true}` to use that context as the remote parent, including after reopening the database. With the option disabled, or when no valid context is available, the worker uses its active context. Only the traceparent is stored; tracestate and baggage are excluded. The host must authenticate the source of any context it accepts: request authentication alone does not establish trust in an arbitrary trace header. Trace context is not authorization, and a remote sampling flag can affect the host's sampler. Protect the database and backups, and plan retention; these records are retained indefinitely. Schedulers do not capture context automatically.

A span reports the local attempt, not a complete audit or proof of external effects; a process crash can prevent it from being exported. Distributed tracing policy and production observability remain host responsibilities.

The host returns `succeeded`, `failed`, `stopped` or `uncertain` only when it can substantiate that outcome. A thrown error after execution starts or an unrecognized result is recorded as uncertain. `stopped` acknowledges a pause or cancel only when the worker has stopped safely; otherwise it becomes uncertain. A lost or expired lease prevents settlement and requires `recoverExpired` and explicit reconciliation. Cancellation and lease loss are cooperative: an implementation that ignores the signal can continue running, and a lease check cannot fence an external system. Never automatically retry an ambiguous external action; use the [action journal](agent-action-journal.md) and external idempotency.

The host can drive individual runs or use the optional dispatcher below. It obtains trusted input, protects lease tokens, supplies authorization and policy-enforced capabilities, and must wait for an old worker to stop before reconciling. The worker enforces the configured local concurrency limit but does not store input or output, automatically select checkpoints, or implement production identity. A process crash remains uncertain until manually reconciled.

## Local queued-run dispatcher

`DurableAgentDispatcher` optionally polls one host-selected tenant and agent. Construct it with the same `SqliteAgentRuns` instance used by a configured `DurableAgentWorker`, a bounded `maxPerPass` (1–100), a polling interval, and an `onError` callback. `start()` enables polling; `runOnce()` performs one pass without enabling a timer. Each pass scans queued run IDs in bounded pages and executes them sequentially through the worker, which still checks definitions, policy, quotas and leases. Failed claims or authorization checks are reported per run and do not block later IDs; the in-memory cursor wraps after the last page. Restarting loses the cursor, and a run queued before it is reached on the next scan. `SqliteAgentRuns.queuedPage` is also available for trusted hosts; it is not an authorization boundary or a consistent snapshot across pages.

`stop()` prevents selecting further runs and waits for the current worker invocation to finish. It does not cancel that invocation, including an authorization or external operation already in progress; the host must request cancellation through the run registry when appropriate. Polling is local to one process and scope; competing dispatchers rely on the existing SQLite claim and concurrency checks. The dispatcher does not recover expired leases, retry uncertain runs, or verify external outcomes. The host must secure the database, provide authenticated policy and input, handle errors and retention, and establish that old workers have stopped before reconciliation. Long-running or uncooperative execution can delay stopping indefinitely.

## Expired queued and paused runs

A queued or paused run whose deadline has passed cannot start another attempt. A trusted host can call `expiredPage(scope, now, {after?, limit?})` to scan them by deadline and run ID, and `expireDeadline(scope, runId, revision, now)` to mark an eligible run failed. The transition rechecks the deadline and revision in a SQLite transaction, clears approval and delegation waits, and records the ordinary lifecycle transition. Resuming any paused run at or after its deadline is rejected. No queued or paused run is expired automatically by default.

`AgentRunExpiryWorker` is an optional, explicitly started host-driven poller for one tenant and agent. It pages through expired runs and requires a host `authorize(run)` callback for every transition; denied entries are revisited after the scan wraps, while stale revisions are not applied. `runOnce()` performs a single bounded pass; `stop()` prevents transitions after an in-flight authorization returns. The host must authenticate and authorize whoever configures and runs this worker, supply a consistent trusted clock, and separately record operator identity if required. The ordinary lifecycle history records the status change but does not itself attribute it to the operator or distinguish expiration from another failure. Pages are not a consistent snapshot, and restarting resets the scan cursor.

To retain operator-attributed expiry decisions, pass `{principalId, reference}` as the final argument to `expireDeadline`, or set `evidence` to that object on `AgentRunExpiryWorker`. The host must authenticate and authorize that principal and retain the referenced supporting evidence. The expiry and the audit record commit in the same SQLite transaction; an audit insertion failure leaves the run unchanged. `SqliteAgentExpiryHistory(path, {scope, authorize})` offers scoped, paginated access and separately authorizes listing and each record. Records contain run ID, new revision, prior state, deadline, actor, reference and host time, but no run input or lease token. Filtered pages can be empty and still have a continuation cursor.

Audit is opt-in for each expiry call or worker. Unattributed calls, older binaries and direct database changes can bypass these records; upgrade and restrict all writers before relying on coverage. SQLite triggers prevent ordinary modification or deletion, but administrators can change the database or restore backups. Protect references, database and backups, export independent audit where needed, and plan retention. This local record does not prove the host clock or establish the outcome of prior external effects.

Expiry accepts only queued or paused runs without a lease. It fails closed if the same database has unresolved action-journal dispatches or token reservations. It never changes running or uncertain runs: establish that an old worker stopped and reconcile those runs and external effects using the existing recovery procedures. A failed run does not establish whether earlier effects occurred. Older clients, unjournaled effects, direct database access, policy changes during authorization and operations on other databases remain host responsibilities. Deadline expiry clears wait markers but does not revoke a grant or resolve an approval request.

## LangGraph checkpoints

`SqliteAgentCheckpointer` implements the LangGraph checkpoint saver contract for a single tenant, agent and run. Open it against the same SQLite database as the run registry, passing the active lease token. Checkpoints and pending writes persist across restart, preserve parent and task-write ordering, and are partitioned by run and LangGraph namespace. Writes and thread deletion verify the current run lease within the same SQLite transaction; an expired or replaced worker cannot write. Reads are scoped by the saver but are not authorization checks. The host must authorize access, protect lease tokens, close the saver after all operations finish, and protect the database and backups: checkpoints may contain sensitive prompts, messages and tool results and are not encrypted.

A host can pass `{saver, threadId: runId, resume: false}` as `checkpoint` to `createConfiguredAgentRun`; a fresh invocation refuses an existing checkpoint. After a crash, the host must first establish that the old worker stopped, reconcile the uncertain run, claim a new lease, and construct a new saver with that token. Only then may it explicitly use `resume: true`. The checkpoint thread ID must match the run ID. The resumed graph uses saved state rather than the supplied messages. A missing checkpoint fails closed. The host must preserve graph, model and tool compatibility across attempts.

A checkpoint records execution state, not the outcome of an external side effect. A crash after dispatch and before its result is saved can cause a resumed node to repeat the call. Do not resume such a run until the external outcome has been reconciled and replay is safe; use the [action journal](agent-action-journal.md) and a downstream idempotency contract; automatic reconciliation remains open. The host-driven worker does not automatically create a saver or decide when resume is safe.

## Waiting for delegation renewal

When a configured agent encounters an expired delegation before dispatch, its terminal AG-UI event has code `AGENT_DELEGATION_EXPIRED`. A host using a persisted grant and a journal for **every** external effect can map that event to the worker outcome `{status: 'delegation_expired', grantId: grant.grantId, revision: grant.revision}` after execution has stopped. The worker verifies the live lease, exact expired grant revision and absence of `dispatching` or `uncertain` journal entries in the same database transaction before recording the run as `paused`. An unclassifiable error, an expiry inside a journal dispatch, a changed grant, missing journal table or an unresolved action results in `uncertain` and requires explicit reconciliation. An expiry event alone is not proof that an arbitrary host integration has stopped all effects; the host must return this outcome only after establishing that fact.

A paused run exposes `delegationWait` with the grant ID, user and expired revision, allowing the host to request renewal from an authorized person. A durable local inbox records the renewal request; external notifications are not sent. See [agent approvals](agent-approvals.md). After authorized renewal, `runs.request(scope, runId, revision, 'resume')` atomically requires a newer, unrevoked, unexpired revision of that same grant and user, an unexpired run deadline and remaining attempts. Cancellation clears the wait. The host must authorize administrative operations, verify current delegated policy again, and select a safe checkpoint/replay strategy before starting a new worker; a renewal does not itself start the run. A crash, lease loss, or action whose outcome is unknown still requires the existing stop-and-reconcile procedure.

## Waiting for approval

A host can classify a configured run's `AGENT_APPROVAL_REQUIRED` event using `pendingApproval()` and return an `approval_required` worker outcome after all execution has stopped. The run is paused with its action ID only if the pending (or just-approved) request and live lease match and the action journal contains no unresolved dispatches. Resume is explicit and requires the corresponding approval to remain approved and unexpired. Cancellation clears the wait; rejected or expired requests cannot resume it. The worker falls back to `uncertain` if these checks fail. The host must journal every effect, authorize administrative operations, and establish a safe checkpoint or deterministic replay strategy; a pause does not prove arbitrary external host code has stopped. See [agent approvals](agent-approvals.md).

## Daily run quota

`DurableAgentWorker` enforces the current definition's `maxRunsPerDay` together with `maxConcurrentRuns` when claiming a run. The SQLite claim transaction records the first successful claim for each tenant, agent and run, and counts distinct first starts in the current UTC calendar day. Competing local workers share the same limit. A denied claim leaves the run queued and does not consume an attempt. Retries and resumption of the same run do not consume another slot, even on a later day; they still obey the attempt, deadline and concurrency limits. A changed definition is checked before claim, and a lower daily limit takes effect for subsequent new starts.

Direct callers of `SqliteAgentRuns.claim` can supply `maxRunsPerDay` as the final argument. Omitting it leaves the direct claim unlimited but still records its first start for later quota enforcement. Hosts must not bypass configured-worker enforcement when the quota is required, must supply a trusted consistent clock and coordinate all workers on the same SQLite database. Start records are durable and currently retained indefinitely. Runs last started before this feature cannot be reconstructed because earlier records did not store their first-start times; a legacy run is counted on its first subsequent claim. Provider-specific token enforcement, cost budgets, a distributed quota service, and production retention remain open.

## Optional local model token budget

`SqliteAgentTokenBudget` reserves a maximum number of tokens for each model invocation under a live run lease. Its limit is pinned on first reservation and persists with individual calls. The reservation transaction includes already settled usage and all outstanding reservations, so competing local callers cannot reserve beyond the limit. Settling records actual usage and returns unused capacity; an unknown result remains reserved across restarts. `list`, `get` and `summary` let the host inspect records. A stale worker cannot reserve or settle. After stopping the old worker and marking the run uncertain, a trusted host can reconcile a reservation with verified provider usage before retrying. Reconciliation and inspection require host authorization; protect the SQLite database and audit the host's decisions.

An outstanding reservation forces worker settlement to `uncertain`, even when execution reports success, failure or a cooperative stop. Approval and delegation waits also reject outstanding reservations, causing the worker to settle as uncertain. The host must reconcile every reserved call with verified provider usage before changing the uncertain run to any other state; this check and the state change share one SQLite transaction. The guard covers token-ledger records in the same database, including after restart. It cannot fence a provider, reconstruct unrecorded calls, or repair older terminal runs that already contain unresolved reservations. The host must establish that the old worker has stopped and preserve evidence for any manual repair of such legacy records.

A configured agent can opt in with `tokenBudget: {budget, maxTokensPerCall}`. The store must match the tenant, agent, run and manifest `maxTokensPerRun`. The host's model factory must return a `LimitedToolModel` whose `invokeLimited` enforces the supplied `maxTotalTokens` across **input and output** before dispatch and returns reliable `usedTokens`. It receives the ledger `callId` so the host can correlate the request with provider records. The runtime reserves the configured fixed maximum before invoking it and records usage before accepting the message; a call is refused when the remaining budget is smaller than that reservation. Missing usage, a provider error or lease loss leaves the reservation outstanding. Reported usage beyond the reservation is recorded, fails the run and blocks further reservations for that run. The existing generic OpenAI-compatible model does not implement this total-token contract; it must not be treated as budget-enforced without a provider-specific adapter.

An optional per-run cost limit can be configured in the same `SqliteAgentTokenBudget` with `cost: {currency: 'USD', maxMicros: 1000000}` and in the configured runtime with `tokenBudget: {budget, maxTokensPerCall, maxCostMicrosPerCall}`. Amounts are integer millionths of the configured currency unit; the currency is an uppercase three-letter host label and is not validated against an exchange-rate service. The limit and currency are pinned on the first reservation. Cost and token reservations, settlements and reconciliations commit together. `costSummary()` reports committed and outstanding amounts and `getCost(callId)` inspects an individual call. A cost budget cannot be added after a run already has token calls; a current non-cost budget instance cannot reserve against a run with a pinned cost budget. All writers must be upgraded before enabling this feature, because older binaries do not enforce the new ledger.

The host must supply a `CostLimitedToolModel` implementing `invokeLimitedCost`, which receives the token cap, cost cap, currency and call ID, and enforces both caps **before dispatch** using trusted pricing and provider controls. It returns reliable integer `usedTokens` and `usedCostMicros` in the same currency. The runtime will not use an ordinary `LimitedToolModel` for a cost-limited run. It records a reported overrun, fails the call and blocks further reservations; unknown or invalid usage leaves both reservations outstanding. A trusted host must independently verify both amounts before calling `reconcile(callId, usedTokens, usedCostMicros)` on an uncertain run. Provider pricing, fees, taxes, currency conversion, rate changes, non-model effects and billing adjustments are not calculated by this ledger; the host must include all applicable costs in its conservative bound and reconciliation policy. The maximum limit or reported amount is 100,000,000,000 micros per call or run. Existing run calls cannot be retroactively priced by enabling this option.

These controls rely on the host and provider to enforce reservations and report accurate usage: a local lease cannot fence a remote model request, and a provider can still bill or continue after cancellation. The host must account for all model calls, select conservative limits including prompt tokens, and reconcile ambiguous requests without assuming zero usage. Provider-specific enforcement, distributed coordination and production audit remain open.

The local process-crash acceptance tests kill a separate worker after reserving tokens, and again with both token and cost limits, before dispatch, after a simulated provider records usage but before returning, and after the ledger records usage. They reopen SQLite, check lease expiry, stale-worker fencing and tenant isolation, verify that unresolved reservations block run recovery, and reconcile token and cost amounts from the test provider's independent record. The provider is an in-memory test double with a definitive lookup; the test does not prove that a real provider offers reliable usage lookup, enforces a token cap, or stops after a worker dies. Production storage and production pod-level recovery remain unverified.

The `Agent pod recovery` CI workflow separately runs one action-journal recovery scenario in a single-node kind cluster. A simulated provider records an effect and withholds its response; CI deletes the worker pod and the manager pod, remounts the same host-path persistent volume in a replacement manager, and verifies lease fencing, tenant isolation, independent reconciliation and a retry that does not dispatch the effect twice. The provider remains alive during this test and its state is in memory. The test uses deterministic clocks, a test-only image and local SQLite on a single node. It does not verify production storage, node loss, multi-node SQLite access, network partitions, real provider idempotency or billing, or a production worker deployment. Operators still need to establish that an old worker has stopped before recovery.

## Run lifecycle history

`SqliteAgentRuns` installs SQLite triggers that append a run event in the same transaction as run insertion and lifecycle change, including runs created by event ingress and schedules. Events include tenant, agent, run, definition version, revision, status before and after, attempt count, worker ID where available, archive state and approval or delegation wait identifiers. They exclude lease tokens, prompts, model output and trigger payloads. `observedAt` is the database machine's wall-clock timestamp in UTC milliseconds; event IDs provide ordering when timestamps tie. Routine lease renewals do not produce events, so recorded revisions can have gaps.

`SqliteAgentRunHistory` provides scoped, paginated reads across an agent or for a specific run. The host authenticates the actor and supplies separate list and per-event read authorization; filtering may yield an empty page with a `nextAfter` cursor. Event rows are append-only under the installed database triggers, and history write failures roll back the associated run change. These records are local operational history, not a complete actor audit: the registry does not know who requested administrative actions, rejected attempts are not captured, existing runs are not backfilled, and external writes can bypass protections if a database administrator alters the schema. The host must audit actor identity and denied operations, secure the database and backups, and plan retention. History grows with lifecycle changes; production telemetry, retention and distributed audit remain open.

## Run-state metrics

`SqliteAgentRunMetrics` opens the run database read-only for one host-selected tenant and agent. Supply `scope` and an `authorize(actor, scope)` callback; `snapshot(actor)` and `render(actor)` require an authenticated actor from that tenant and check aggregate access both before and after reading. Authorization must cover the entire selected aggregate, not merely a subset of its runs. The snapshot returns current counts by the nine fixed run states and the archive flag, including zero values. `render` emits the same values as Prometheus `app_mixer_agent_runs` gauges; it contains no tenant, agent, run, worker, token or actor labels. A malformed database state fails instead of creating dynamic labels.

The result is a point-in-time count of retained run records, not a counter of executions or a measure of latency, token use, cost or success rate. A resumed run is still one record, and archiving moves it to the archived series. The host must protect the database, authorize aggregate access, bound scrape frequency and provide authenticated transport and trusted deployment labels. The query scans the selected agent's retained runs; large histories need retention and capacity planning. Authorization is rechecked after the read but is not atomic with later policy changes or metric delivery. These metrics do not replace audit or distributed telemetry.

Set `includeOperational: true` to add fixed-label gauges for queued and paused runs past their deadline and running, pause-requested or cancel-requested runs past their lease expiry. `operational(actor)` returns the count and age of the oldest overdue item in seconds for each of those three categories; `render` exposes `app_mixer_agent_overdue_runs` and `app_mixer_agent_oldest_overdue_seconds`. An empty category has age zero. Supply a trusted consistent `clock` when the host uses one for lifecycle operations. Archived and terminal records are excluded. A missing lease on an active run fails the scrape rather than producing a misleading value. These aggregates do not expire or recover runs, determine whether a worker has stopped, or establish external effects. Run-state and overdue queries are separate snapshots and can differ if runs change during a scrape.

Set `includeSchedules: true` to add `app_mixer_agent_due_schedules` and `app_mixer_agent_oldest_due_schedule_seconds`: the number of enabled schedules in the scope whose next occurrence is due but not yet fired, and the age of the oldest. A value that keeps growing means no schedule worker is firing, or the backlog limit is holding occurrences back. Set `includeActions: true` to add `app_mixer_agent_actions{status}` for the five journal states (`ready`, `dispatching`, `uncertain`, `succeeded`, `failed`), every state always present; `dispatching` and `uncertain` are the actions a recovery worker or reviewer must resolve. The journal records no timestamps, so there is no age for actions. `schedules(actor)` and `actions(actor)` return the same values, use the same authorization and actor checks as the other methods, and throw when their option is not set. Each option requires its table (`agent_schedules` or `agent_action_journal`) in the same database, or construction fails. Neither metric carries schedule, run or action identifiers. Set `includeApprovals: true` to add `app_mixer_agent_approvals{status}` for `pending`, `approved`, `rejected`, `cancelled` and `expired` human approvals in the scope (an approval past its expiry counts as `expired`, as the approval store reports it); a `pending` count that keeps growing means reviewers are not keeping up. The approval store records no request time, so there is no age gauge. Set `includeNoticeDeliveries: true` to add `app_mixer_agent_notice_deliveries{status}` for `pending`, `sending`, `uncertain` and `delivered` notice deliveries: a `pending` count that keeps growing means the delivery worker is not keeping up, and `uncertain` or a `sending` delivery that never finishes needs an operator (the outbox keeps no delivery time, so there is no age gauge). Set `includeTokens: true` to add `app_mixer_agent_token_calls{state}` and `app_mixer_agent_tokens{state}`: model calls with a token reservation and the tokens they hold, `reserved` (not yet settled, so a call that never settles needs reconciliation) or `settled` and `committed`, summed across the agent's runs. Set `includeMemories: true` to add `app_mixer_agent_memories{state}` for the agent's `live`, `expired` and `deleted` memories across every owner: an `expired` memory is past retention but still stored until purged, so a growing count means the retention worker is not running, and `deleted` tombstones await compaction. Set `includeCosts: true` to add `app_mixer_agent_cost_micros{currency,state}`: cost in millionths of each currency held by unsettled (`reserved`) reservations or `committed` by settled calls, summed across the agent's runs. At most eight currencies are reported; a ninth makes the scrape fail rather than add a label.

`createAgentMetricsServer({metrics, authenticate, timeoutMs, maxPending})` optionally exposes `GET /metrics` on a separate HTTP server. The host-supplied authenticator receives the request and an abort signal and must return a trusted tenant and principal; the metrics object's aggregate authorization still applies. Unauthenticated requests receive 401, denied aggregates 403, and unavailable or timed-out scrapes 503 without internal error details. The host must bind the listener to loopback or a protected network, secure transport, authenticate and audit scrapers, and use its own trusted mapping from listener to tenant and agent. Do not expose this HTTP listener publicly.

Timeouts are 100–30,000 ms and `maxPending` is 1–1,000. A timeout or disconnect aborts the authentication signal, but an unfinished authentication or authorization callback continues to occupy a slot until it settles. Callbacks should finish promptly and authentication should honor cancellation. SQLite's synchronous query cannot be interrupted by the JavaScript timeout while it blocks the event loop; isolate or capacity-plan large databases and apply network-level rate limits. The endpoint does not install a scheduler, exporter, TLS or production identity.

## Shared run slots

`SqliteAgentRuns` enforces `maxConcurrentRuns` and `maxRunsPerDay` only within one database file, so workers on separate nodes with their own registries could each reach the limit. `PostgresAgentRunSlots({enabled: true, query, transaction})` adds an optional shared limiter on one PostgreSQL primary; call `initialize()` once. Pass it to `DurableAgentWorker` as `sharedSlots`. Before its local claim, the worker acquires a slot for the run under a per-agent row lock, enforcing the manifest's concurrency and distinct-runs-per-UTC-day quotas across every worker using the database. A full agent fails with `Agent run quota exceeded` and leaves the run queued. Retries of a run already counted that day do not consume another daily slot, and a run cannot hold two slots at once.

Slots expire on database time after the worker's lease duration, so a crashed worker's slot frees itself; expired slots are removed on the next acquisition for that agent. The worker renews the slot with every local lease pulse. If renewal fails because the slot expired or was removed, the worker aborts execution as it does for a lost local lease. The slot is released after settlement, or immediately if the local claim fails. `active(scope)` reports unexpired slots, and `pruneStarts(retainDays)` deletes old daily counters.

Slots limit execution, not queued runs; the local registries still own run state, leases and recovery. Database time avoids clock skew between workers but makes availability depend on PostgreSQL: if it is unreachable, workers cannot start runs. A worker paused for longer than its lease can lose its slot while another worker starts a run, so keep leases longer than expected pauses and treat an aborted run's outcome as uncertain. Use a restricted role, trusted `search_path` and statement timeouts, and direct all workers to the same current primary.

`packages/agent/test/postgres-run-quota-nodes.test.mjs` (run in the PostgreSQL CI job) checks the limiter across nodes. Two separate processes, each with its own connection pool, are released at the same instant over 20 rounds. In every round they attempt 30 starts against `maxConcurrentRuns` 5, then 30 starts against `maxRunsPerDay` 7. Every round admits exactly 5 and exactly 7, and the slot and start tables hold exactly those rows. Both nodes are admitted within the same round, so they really compete. Without the scope row lock (`FOR UPDATE`), the first round admits all 30.

## Shared run registry across nodes

`SqliteAgentRuns` is shared only by processes that open one SQLite file. `PostgresAgentRuns({enabled: true, query, transaction})` keeps runs and their action journal on one PostgreSQL primary, so workers on separate nodes share one registry. Call `initialize()` once. Lease times use the database clock, so node clock skew does not shorten or extend a lease. The host's `transaction` callback checks a client out of its pool for the length of one transaction. Attach an `error` listener to that client while it is checked out and remove it before releasing the client: a connection lost between two statements (a database failover or restart) emits `error` on the checked-out client itself, the pool's own error handler covers only idle clients, and with no listener Node ends the process. The failover tests' helpers do this, and the pool should also have an `error` listener for its idle clients.

- **Lifecycle.** It has the same transitions as the SQLite registry: `create`, `claim`, `renew`, `request` (pause, resume, cancel), `settle`, `recoverExpired`, `reconcile` and `archive`. Each one locks the run row and checks the expected revision, so of two nodes acting on one revision exactly one wins. `create` refuses a run ID that already exists (`Run already exists`). Create a run handed off by `PostgresAgentSchedules.claimRun` under its run ID, so a request reclaimed after a node failure cannot start a second run.
- **Limits.** `claim(scope, runId, revision, workerId, leaseMs, {maxConcurrentRuns, maxRunsPerDay})` counts active runs and first starts under one per-agent lock, so the limits hold across nodes. A retry of an already-started run does not count as a new run for the day.
- **Discovery.** `queued(scope)` and `expiredLeases(scope)` list candidates for claiming and for recovery.
- **Action journal.** `journal(scope, runId, leaseToken)` returns a `PostgresAgentActionJournal` with the semantics of `SqliteAgentActionJournal`. `invoke` records the action, dispatches it at most once per idempotency key and stores the result. Every step locks the run and requires the caller's live lease in the same transaction, so a worker whose lease expired or was released cannot record or dispatch. `settle` turns a run with a dispatching or uncertain action into `uncertain`, and `reconcile` refuses to retry it until each such action is decided. To recover, call `markUncertain` for a dispatching action, then `reconcileWith(actionId, verify)`: it asks the external system what happened, without replaying the action, and rejects a stale decision.

Approval and delegation waits, token budgets, lifecycle history, metrics and expiry audit belong to the SQLite registry only. The host authenticates nodes, authorizes every call and protects the primary connection. It must call `recoverExpired` only once the old worker can no longer act; a killed process or an expired lease plus the journal fence meets that.

`packages/agent/test/postgres-run-nodes.test.mjs` (run in the PostgreSQL CI job) starts two worker processes against six runs of three journaled actions each. Both are killed with SIGKILL during their first dispatch. One is killed after the external system applied the effect but before the reply arrived. The other is killed before the effect was applied. Two new processes then race to recover. Each interrupted run is recovered exactly once and retried once. The applied action is verified and reused, and the unapplied one is dispatched once. The external system, which does not deduplicate, records exactly 18 effects under 18 distinct idempotency keys. Treating a verified effect as unapplied, creating a run twice, or removing the journal's lease fence each makes the test fail.

## Scheduling workers on the shared registry

`PostgresRunSupervisor` is the loop a deployed worker process runs against `PostgresAgentRuns`. Construct it with:
- the registry, scope and a stable `workerId` (for example the pod name)
- an `execute({run, journal, signal})` callback that performs one run through the lease-fenced journal
- a `verify(request)` callback that asks the external system whether an interrupted action took effect
- `onError`, an optional `onEvent`, and optional `leaseMs`, `pollMs`, `maxConcurrent` (per worker), claim `limits`, `recoveryGraceMs` and `reviewCooldownMs`

Every `pollMs`, after `start()`:
1. **Recovers expired leases.** A run whose lease expired more than `recoveryGraceMs` ago becomes uncertain. The grace period lets a worker that is only slow notice its lost lease before its run is taken over.
2. **Reconciles uncertain runs.** It marks each dispatching action uncertain and calls `verify`. If any action is still `unknown`, or the run is uncertain only because a reservation is still open (a model call whose usage is not known, which a person must reconcile), the run is reported once (`review` event) and left alone for `reviewCooldownMs` (30 seconds by default), so it is neither re-verified against the external system nor reported on every pass. Every uncertain run is examined, paging through them in run ID order, so runs waiting for review cannot hide the ones behind them. Otherwise the run is retried, or failed once its attempts or deadline are used up.
3. **Claims queued runs** up to `maxConcurrent` and executes them in the background. `maxConcurrent` is this worker's own parallelism. The agent-wide cap is separate: unless `limits.maxConcurrentRuns` is set, an agent runs one run at a time across all workers. When a claim is refused by that cap or the daily run limit, the supervisor emits a `limited` event and stops claiming for that pass, so a worker configured with `maxConcurrent` above one but no `limits` is visibly limited instead of silently idle.

While a run executes, the supervisor renews its lease every third of `leaseMs`. A lease is renewed only while the run is `running`: once a pause or cancel is requested the next renewal is refused ("Run cannot be renewed"), so a worker must stop, or finish its current step, within the lease it already holds. A step that needs longer than that leaves the run uncertain when the lease expires, to be reconciled. Choose `leaseMs` above the longest step you cannot interrupt. A paused run whose attempts are all used cannot be resumed (the call fails with a conflict, "Run attempts exhausted"), so an approval or delegation renewal that arrives for it does not bring it back; raise `maxAttempts` for runs that may pause late. If the lease is lost, or a pause or cancel is requested, it aborts `signal`. When `execute` returns, it settles the run. A thrown error or an unknown result settles as uncertain. A pause or cancel request can land between the supervisor reading the run and settling it; the settle then loses a revision race, and the supervisor reads the run again and retries up to three times rather than leaving a finished run leased until its lease expires.

`stop()` stops claiming and waits for the runs this worker holds; a later `start()` resumes claiming. Call it on SIGTERM and set the termination grace period above the longest run. `stop({abort: true})` signals the runs to stop; one stopped this way is handed back as uncertain, so another worker reconciles and retries it.

Several workers on different nodes can run supervisors on the same scope. Claims, recovery and reconciliation are all revision-checked, so a lost race is skipped quietly. The external system must accept the action's idempotency key: a worker that lost its lease mid-dispatch may still reach the provider before it stops.

Tests:
- `packages/agent/test/postgres-run-nodes.test.mjs`: the node-failure processes run this supervisor. A drain test stops a worker while two runs are in flight; it finishes both, claims nothing new and exits cleanly.
- `packages/agent/test/postgres-run-failover.test.mjs` (opt-in with `APP_MIXER_TEST_POSTGRES_FAILOVER=docker`, run in CI) fails the store itself under load: two worker processes hold runs while the PostgreSQL primary is killed, a synchronous standby is promoted behind the same address four seconds later, and every run must still finish with each external effect applied exactly once. Locally all 16 runs finished, seven of them on a second attempt, and the workers reported many database errors during the outage and kept running. The effects server has no deduplication, so a replayed action would show. This is one standby on one machine; detection time, automatic failover, a managed service's failover behaviour and writes that were in flight but unacknowledged at the kill are not characterised beyond what the exactly-once result shows.
- The same file also freezes a worker with SIGSTOP while it holds a run whose first action has been applied but not acknowledged, which stands in for a pause or partition that outlasts the lease (Linux and macOS only). A second worker recovers the run once the lease expires, verifying the applied action instead of replaying it, and finishes every run. The frozen worker is then resumed and given the reply it was waiting for: it dispatches nothing, completes nothing, the run was retried once and every effect is applied exactly once. This is one process on one machine, not a network partition between a node and the database.
- `deploy/kubernetes/test-support/agent-recovery/run-supervisor.sh` (run by the agent pod recovery workflow in kind): schedules the supervisor as a two-replica Deployment against PostgreSQL with 60 runs. It crashes one worker process with SIGKILL while it holds a run, so the container restarts in place, then rolls the Deployment so every old pod drains on SIGTERM. Every run succeeds, the external system, which does not deduplicate, records exactly 180 effects, and at least one run was recovered after the crash.
- `deploy/kubernetes/test-support/agent-recovery/node-failure.sh` (the `node-failure` job of the same workflow, in a kind cluster with a control plane and two worker nodes): the PostgreSQL and effects pods sit on the first worker; two run workers are spread across both. With a worker holding runs, the second worker node's container is killed (`docker kill`, no graceful shutdown). The control plane marks the node not ready, evicts the pod after a 5-second toleration (the Kubernetes default is 300 s), and the Deployment starts a replacement on the surviving node. The surviving worker takes over the dead worker's runs when their leases expire, every run finishes, and each external effect is applied exactly once. In a local run, the replacement was running about 50 s after the kill and the dead worker's runs had been recovered by the survivor. Kind nodes are containers on one machine, so this shows the scheduling and lease behaviour, not a real network partition, a zone outage or a managed node pool; a partitioned worker that keeps running is not simulated.

## Shared cost budget across nodes

`SqliteAgentTokenBudget` caps one run. `PostgresAgentCostBudget({enabled: true, query, transaction})` caps what an agent spends per UTC day, by the database clock, across every run and node sharing a `PostgresAgentRuns` database. Call `initialize()` after the registry's `initialize()`, and set the limit with `configure(scope, {currency, maxMicrosPerDay})`.

- **`reserve(scope, runId, leaseToken, callId, costMicros)`** reserves the worst-case cost of one model call before it is made. It requires the caller's live run lease and admits the reservation under one per-agent lock, so nodes reserving at the same moment cannot together pass the limit (`Cost budget exhausted`).
- **`settle(...)`** records the provider-reported cost.
- **Provider overrun.** If a call cost more than it reserved, every node is refused for the rest of that day (`Cost provider limit violated`).
- **Open reservations.** A run settled with a reservation still open becomes uncertain. `reconcile(scope, runId, callId, usedMicros)` records the actual cost once the old worker has stopped.
- **`summary(scope, day?)`** reports the limit, committed and reserved spend, and whether an overrun occurred.

`packages/agent/test/postgres-cost-budget-nodes.test.mjs` (run in the PostgreSQL CI job) starts four processes, each with its own pool and four concurrent callers.
- One 100,000-micro budget admits exactly 100 calls of 1,000 micros, spread across all four nodes.
- Thirty further rounds release all 16 callers at once against a three-call budget. Each round admits exactly three calls and commits exactly the limit.
- Without the per-agent lock, the nodes overspend in the first round.

The host still configures limits, reconciles open reservations, and enforces provider-side caps on each model provider.

## Run-start history retention

`SqliteAgentRuns` records one start per run for the daily run quota. `pruneStarts(retainDays, now?)` (the SQLite counterpart of `PostgresAgentRunSlots.pruneStarts`) deletes records older than `retainDays` (1 to 3,660) for every tenant and agent in the database and returns the count. Quotas only count the current day, so older records are history; a run that is retried after its record was pruned counts as a new start. The host decides who may call it and how long to keep history.

## Dispatch order

Queued runs start in creation order. `SqliteAgentRuns` numbers every run with a monotonic `created_seq` (added to existing databases on open and backfilled from their row order) and `queuedPage` returns the oldest queued runs first; its `next` cursor is still the last run ID and is resolved to its sequence. `PostgresAgentRuns` numbers runs with an identity column `sequence` (added by `initialize()`, which numbers existing rows in their physical order) and `queued` orders by it. Run IDs no longer influence dispatch order, so random UUIDs from schedules, triggers and event ingress start in the order they were created. `list` still pages by run ID.

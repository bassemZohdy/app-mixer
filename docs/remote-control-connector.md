# Remote Control Plane connector

`createRemoteControlConnector` is an optional, host-driven import path from a configured Control Plane into a local `DefinitionRepository`. The host provides the source origin and bearer token, source and target environment names, application ID, local repository, authorization and audit callbacks, and timeout. `importPublication({actor, sourceVersion, expectedVersion})` requests that exact source version, verifies the package digest and application/environment/version identity, asks the host to authorize both export and local import, and calls the local repository's promotion method with the expected target version. The repository's publication guard and optimistic concurrency still apply. Pass `createDataPlane` the local repository: serving published definitions requires no connector or live Control Plane.

The source uses HTTPS with platform certificate verification, no redirects and bounded JSON responses. Explicit loopback HTTP is available for local development. The source origin, credential, environment and actor must come from trusted host configuration and authentication; do not derive them from an incoming token or arbitrary request. The host must bind source identity to the correct tenant and environment, restrict network access, authorize both stages, and provide durable audit where required. Authorization may change between the last check and the local commit; enforce stricter policy inside the target transaction if necessary.

By default the package digest detects alteration but is not a signature; TLS and the configured source authenticate the transport. For signed delivery, pass a trusted `PromotionExportSigner` as the seventh argument to the source's `createControlPlane`. It receives the exported package, requested target environment and expected target version; it must authorize the signing operation and use `signPromotionPackage` with that expected version. Configure the connector with `verifyWithEvidence` from `createSignedPromotionVerifier(..., {requireVersionBound: true})`. The connector requests the signed endpoint, verifies the trusted key and source binding through that callback, requires version-bound evidence, and writes it atomically with the local promotion through `promoteVerified`. A missing signer, untrusted key, altered package or wrong version fails before local import. The host must protect signing keys, authorize source and target environments, authenticate the source API and protect against rollback of the local database. Signatures prove key possession, not human identity or release freshness.

For optional version discovery, configure `discovery: {authorize, audit}` with host-owned callbacks and call `discoverLatest({tenantId, principalId})`. The source's authenticated `GET /publications/latest` returns only its application ID and current publication version. The connector checks that the application matches its configured ID and returns `{applicationId, sourceVersion}`. Discovery requires separate authorization and audit, checks authorization both before the request and before returning the version, and never imports automatically. The result is a point-in-time observation from the configured source, not a signed freshness proof; the host must protect against source or database rollback and decide whether a discovered version is permitted. Pass the chosen version and a local version precondition to `importPublication`, whose export and import authorization checks still apply.

Set `requireAdvancingSource: true` to require each import's source version to be greater than every earlier promotion for the same application, source environment and target environment. `ApplicationStore` and `SqliteApplicationStore` implement this through `promoteAdvancing`; SQLite checks the history and writes the publication, provenance and any signature evidence in one transaction. A repeated or older source is rejected, and the connector reports an uncertain import outcome as it does for any repository error; inspect the local publication and provenance before retrying. A custom repository must implement the same atomic contract. Existing promotions establish the floor even if they were imported without this option. Different source or target environments have separate floors.

This protects only imports made through the advancing method and retained local promotion history. Direct promotion, local publication and rollback can bypass it, so the host must control every write path. Restoring or replacing the target database can erase the floor; protecting against database rollback requires independent durable state. The source environment is a host-controlled identity, not a verified origin or epoch. Bind it to a stable source and establish a new policy when migrating or resetting source versions. Signed imports additionally require the signed mode above; monotonic source versions alone do not authenticate freshness or the publisher.

`SqliteRemoteRollout` provides an optional host-scheduled single-pass coordinator. Construct it with a persistent SQLite journal path, a connector configured with authorized discovery, version-bound signature verification and `requireAdvancingSource: true`, and a host-owned service actor. Its repository must implement `getPromotionFloor` and `getPublished`; both built-in repositories do. Invoke `runOnce()` on a host-controlled schedule. It discovers the latest source, skips an already imported source version, rejects a source behind the retained floor, and imports a newer version with the current local publication as a precondition. Separate coordinator instances sharing the journal cannot overlap for the same tenant, application and environment pair. The host supplies scheduling, backoff, telemetry and deployment configuration.

The coordinator records a claim before discovery and records the intended source and target versions before import. A failed import or interrupted process leaves a persistent gate; subsequent passes refuse to run. `getState()` exposes the pending versions. To recover, first stop all workers for that rollout, inspect the target publication and provenance, repair any audit failure, and call `recover(state => ...)` with a host-controlled authorization decision that returns exactly `true` only after reconciliation. Recovery does not cancel a worker in another process: never recover while any prior worker might still execute. After recovery, a later pass rechecks discovery and the promotion floor. A pre-import failure in a live worker releases its claim; a process crash at any stage requires recovery. Keep the journal durable and bind it consistently to the same target repository and environment identities. Restoring, deleting or substituting either database can invalidate the gate or floor; the coordinator is not a distributed lease, production identity system, or external rollback-proof store.

`registerRemoteRolloutStatusCapability(registry, rollout, {candidate, scope, authorize, authorizeStatus, timeoutMs?, maxPending?})` exposes read-only status for one host-fixed tenant, application, source and target environment. The supplied scope must match the coordinator, and the authenticated actor must belong to that tenant. The capability accepts an empty input and returns only the phase, source version and expected target version; the internal claim token is never returned. Separate aggregate status authorization and the normal capability policy are checked before and after reading, and a changed gate fails the read. An authorized status does not prove a worker is dead or permit recovery; operators must still fence workers and reconcile provenance.

Set both `timeoutMs` (100 to 30000) and `maxPending` (1 to 100) to bound capability work per instance. A timed-out callback receives an aborted signal and retains its slot until it settles; saturation and timeouts return HTTP 503. This does not bound the registry's initial audit and authorization, forcibly cancel PostgreSQL queries, or establish an atomic snapshot with external authorization. Protect status access and production audit separately.

`registerRemoteRolloutRecoveryCapability` optionally exposes recovery for one fixed rollout scope through a separate operator-only capability. The authenticated actor supplies exactly `{reference}` identifying independently protected evidence. The host supplies separate `authorize`, `authorizeRecovery` and `verifyRecovery` callbacks. Verification must establish both that every previous worker is permanently stopped or fenced and that the target publication and provenance have been reconciled; the adapter cannot establish either fact itself. The callbacks receive copies of the actor, fixed scope, sanitized gate phase and versions, evidence reference and an `AbortSignal`; the claim token is not exposed. Authorization is rechecked after verification, and the coordinator's token-and-phase comparison rejects a changed gate. False verification leaves the gate unchanged.

Optional `timeoutMs` (100 to 30000) and `maxPending` (1 to 100) bound the authorization and verification inside recovery; timeouts fail closed and late approvals cannot clear the gate. Slots remain occupied until callbacks finish. The coordinator's initial database read and final update, and the registry's initial audit and authorization, are outside those bounds. A lost update response or failed success audit can make the outcome uncertain; inspect the separately authorized status and provenance before any retry. The capability writes an actor, evidence reference, previous phase and versions, and host clock time atomically with clearing the gate. Direct trusted callers may pass equivalent evidence as the second argument to `recover`; the legacy form without it remains unaudited. `listRecoveryEvidence({after?, limit?})` returns bounded pages for that coordinator, but does not authorize callers: the host must protect and authorize these reads. SQLite and PostgreSQL reject ordinary evidence updates and deletes, but database administrators can bypass those protections; the host still needs an independent protected operator audit. PostgreSQL hosts must rerun `initialize()` with the migration identity before enabling this capability, and earlier recoveries are not backfilled. Never let ordinary requesters choose or implement the verifier.

`registerRemoteRolloutEvidenceCapability` exposes this history through a separate fixed-scope, aggregate-authorized read capability. Configure a distinct `authorizeEvidence` policy and a stable, secret 32-byte `cursorKey`; requests accept `{cursor?, limit?}` with a limit of 1 to 100. Results omit internal event IDs and claim tokens. Encrypted continuation cursors are bound to the actor, rollout scope and operation, so they cannot be moved to another user or scope. Rotating or losing the key invalidates existing cursors. The policy is rechecked after each read; optional `timeoutMs` and `maxPending` bound the capability work as for status. The history contains operator IDs and references and can be sensitive; aggregate authorization covers the complete fixed scope.

`PostgresRemoteRollout` offers a shared journal for the same coordinator protocol. Enable it explicitly, supply a trusted PostgreSQL query function and call `initialize()` using a migration identity before starting workers. Its asynchronous `runOnce`, `getState` and `recover` methods use an atomic scoped claim and compare the claim token on transitions. It can be supplied to `RemoteRolloutPoller`. A database error can leave a claim in any non-idle phase, so operators must inspect it and reconcile before recovery. The journal has no lease expiry or automatic takeover: recovering a live worker can permit overlapping imports. Stop and fence every earlier worker before recovery.

All coordinators for a scope must target the same authoritative publication repository with atomic optimistic promotion and source-floor enforcement. A shared PostgreSQL journal does not make a local SQLite target shared or coordinate direct writers; use a target with the required cross-host consistency before operating across hosts. Hosts must authenticate and authorize operators, protect the journal and database connection, provision timeouts and monitoring, and preserve both journal and target backups consistently. Restoring or modifying either store can defeat the gate and freshness floor. Journal and publication commits are separate, so a lost response or failed audit requires inspection rather than blind retry.

`PostgresPromotionTarget` is an opt-in shared target for signed, version-bound remote promotions. Configure a tenant, application, source and target environment, trusted query and transaction functions, and a host `authorizeSignature` policy; call `initialize()` with a migration identity. The target verifies the package and signature evidence, requires the host policy to authorize the key before and inside the transaction, and serializes each target scope with a PostgreSQL row lock. It atomically records the immutable publication, source version, digest and signature evidence, rejects stale target versions and non-advancing source versions, and applies the publication guard. `getPublished`, `getPublicationProvenance`, and `getPromotionFloor` are asynchronous. The connector and both rollout coordinators accept this target. Each target scope is bound to one source environment; source migration needs a deliberate new scope or trusted migration. For Data Plane reads, the target provides `getPublishedWithSignal(version, signal)`. Hosts may configure `queryWithSignal(sql, parameters, signal)` to cancel a cooperative database operation; otherwise the regular query adapter is used and any late result is discarded after it settles. This hook applies to publication reads, not promotion transactions. The host must implement database cancellation safely and retain database-side timeouts. The PostgreSQL integration test exercises a delayed read, bounded Data Plane saturation, liveness and recovery; it does not establish that a particular database driver cancels active queries.

The signature policy must check the evidence against trusted keys and current host approval; a mathematically valid signature alone is insufficient. The callback and database are separate authorities, so policy can change after its final check and before commit. Protect the schema, scope rows and migration role, require durable transaction semantics, and configure bounded database timeouts. The target stores promotions only; it does not provide draft editing, arbitrary publishing, rollback, identity provisioning or independent rollback protection. `createDataPlane` and `createDataPlaneHttps` can read it directly, but then publication reads depend on PostgreSQL availability. A disconnected local replica requires a separate deployment mechanism.

Process-termination tests also stop SQLite recovery before evidence insertion, before commit and after commit, and stop PostgreSQL recovery before and after commit. Reopening verifies that the gate and evidence roll back or persist together, retry is safe, and another tenant remains isolated. These tests cover process death against local SQLite and one PostgreSQL instance, not database or node failure.

The PostgreSQL acceptance test kills a rollout worker before and after its promotion transaction commits. It checks the retained journal gate, another tenant's publication, and explicit reconciliation against the target's signed provenance before a later pass. This covers process death against a single PostgreSQL instance; it does not establish database high availability, node-failure recovery or backup rollback protection.

`RemoteRolloutPoller` is an optional, explicitly started in-process scheduler for one SQLite or PostgreSQL coordinator. Configure `rollout`, `intervalMs`, `maxBackoffMs`, `onResult` and `onError`. Intervals range from 100 ms to one hour; the maximum backoff must be at least the interval and at most one hour. After a successful pass it waits the interval; after an error leaving the journal idle it doubles the interval for each consecutive failure up to the maximum, resetting after success. This includes permanent errors such as authorization denial; the host must inspect errors and stop or alert as appropriate. Callback failures do not alter rollout state. `stop()` prevents another pass and signals the current coordinator to stop before starting an import. A late discovery or local-state read cannot start an import after shutdown. If import preflight is underway, shutdown cancels the remote export request and fences later preflight steps; the journal claim is released only when the built-in connector confirms cancellation before the local publication call. Once the publication call starts, the poller waits for its actual result and retains the normal uncertainty gate on failure. Direct coordinator callers can pass an `AbortSignal` to `runOnce` for the same pre-import fence. Discovery passes that signal to the HTTP request and checks it after discovery callbacks; stopping aborts an in-flight discovery request and prevents a late callback from starting one. Hosts may provide `discovery.authorizeWithSignal` and `discovery.auditWithSignal` to propagate cancellation to those callbacks; these take precedence over the legacy callbacks, whose original signatures remain unchanged. Optionally set both `discovery.callbackTimeoutMs` (100-30000) and `discovery.maxPendingCallbacks` (1-100) to bound each discovery authorization or audit callback. Timed-out or cancelled callbacks receive an abort signal and retain their slot until they settle; their late results cannot resume discovery. These limits apply per connector, not to database queries or import callbacks. Without the bounds, callbacks that ignore cancellation can still delay `stop()`; pending database queries can also delay it. Hosts can supply `authorizeWithSignal` and `auditWithSignal` to propagate shutdown to import preflight policy and audit callbacks; they take precedence over the legacy callbacks, whose signatures remain unchanged. Optionally set both `preflightTimeoutMs` (100-30000) and `maxPendingPreflightCallbacks` (1-100) to bound preflight policy and audit callbacks. A timed-out callback is signalled and keeps its slot until it settles; its late result cannot continue the import. The built-in connector reports `RemoteControlImportPreflightUnavailableError` only before the local publication call, allowing the coordinator to release its claim safely. Custom connectors must not report that error after a possible local write. Without the bounds, callbacks that ignore cancellation can delay shutdown. Completion and uncertainty audit callbacks are outside these bounds and receive a separate non-aborted signal; the local publication call itself is never cancelled. `RemoteControlImportCancelledError` denotes cancellation before that call and must not be used by custom connectors after a possible local write. Cancellation before import is reported to `onError` after the claim is released. Stop the poller before closing the coordinator or its database connections.

If a failed pass leaves any non-idle journal state, or the state cannot be read, the poller stops and reports `needsReview: true`. A `running` state may belong to another live process: investigate and stop all relevant workers before considering recovery. The poller never calls `recover` or restarts itself after review; an authorized host must reconcile, explicitly recover the coordinator, and start it again. Optional `jitterRatio` (0 to 0.5, default 0) shortens each wait, including backoff, by a random fraction up to that ratio, so a fleet of pollers does not contact the source in lockstep; waits never exceed `maxBackoffMs`. This process-local timer has no durable schedule, leader election or availability guarantee, and does not replace production orchestration, monitoring or identity.

The connector itself does not poll, distribute releases, migrate business data, or implement production identity. Its import is explicit and has no automatic retry. Once a local promotion is attempted, any exception or failed completion audit raises `RemoteControlImportUncertainError`: inspect the local publication and provenance before deciding whether to retry. Attempts and completion audit are not atomic with the publication. A source outage or a failed pre-import step leaves the local publication available, and a successful import survives a remote outage according to the local repository's durability. Use a persistent repository, backups and host-managed storage for production.

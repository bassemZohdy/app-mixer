# Durable agent approvals

`SqliteAgentApprovals` stores an approval request for one tenant, agent, run and action in the same SQLite database as the run registry and action journal. A running worker with a valid lease may request approval for an operation and exact canonical input. The request also binds the run's definition version, requester and expiration; expiration must be within the run deadline and at most 24 hours away. A repeated matching request returns the existing decision. An action ID cannot be reused with different input or operation.

The host must authenticate actors and provide an authorization callback for request, read, list, decision, cancellation, expiration and history access. The callback receives tenant, agent, run, action and operation identifiers. An authorized human can approve or reject a pending request; cancellation can revoke a pending or approved request before a later dispatch. Competing decisions are serialized, and expired approvals cannot authorize dispatch. Explicit expiration, accepted decisions and requests are appended to immutable local event records with actor IDs and timestamps. Hosts remain responsible for auditing denied attempts and protecting the database and backups.

A configured agent can opt in with an approval policy and an action journal. For a tool call the host policy must return an explicit boolean. When approval is required, the runtime creates or checks the request and stops that invocation until it is approved. The action journal verifies the approval, exact input, operation, definition version and expiry in the same transaction that records dispatch. Approval does not bypass the capability registry's authorization, validation or audit. Cancellation or expiry cannot undo a call already dispatched; external idempotency and reconciliation are still required.

Approval and notice listings recheck scope and item permissions before returning; approval pages capture their pagination settings before asynchronous authorization and read the latest decision state after those checks. An approval created during authorization of a previously missing lookup is rejected as changed rather than returned under the earlier check. Policy callbacks may run more than once and should be safe to repeat. These asynchronous checks cannot be atomic with external policy changes; hosts must enforce stricter revocation requirements separately.

A configured run emits `AGENT_APPROVAL_REQUIRED` when a request is pending, and `pendingApproval()` exposes the action ID to the host. After execution has stopped, a host that journals every external effect may return `{status: "approval_required", actionId}` from its durable worker callback. The worker records a paused run with `approvalWait` only if the matching request is still pending or approved, the lease is live, and no journaled action is dispatching or uncertain. Otherwise the run is uncertain and requires reconciliation. An already approved decision racing ahead of the pause is preserved. An authorized host must explicitly resume after a human approves; the run registry checks the exact approval, definition version and expiry before queueing it, and the action journal checks the exact input and authority again before dispatch. Rejection, cancellation or expiry cannot authorize resumption. A host must select a safe checkpoint or replay strategy and maintain stable action IDs before retrying. This is not automatic notification or execution after approval. The run deadline remains in force during review. The host must enforce human identity and decision authority, secure transport and storage, and ensure every protected operation is covered by its policy. Input and audit records are not encrypted. Production identity, durable notifications, and distributed approvals remain open.

## Local review interface

`createAgentApprovalServer` provides a local review page at `/review` and a scoped HTTP API. Bind it to `127.0.0.1`, not a public interface. Supply `authenticate(request)` to validate a reviewer credential and return the trusted tenant and principal, and `resolve(scope, runId)` to return the matching `SqliteAgentApprovals` instance. The server checks the returned store's binding; the store's authorization callback still controls list, read, history, decision and cancellation access. For example:

```js
const server = createAgentApprovalServer({
  authenticate: request => authenticateReviewer(request.headers.authorization),
  resolve: (scope, runId) => approvalStoreFor(scope, runId)
});
server.listen(8787, '127.0.0.1');
```

Open `http://127.0.0.1:8787/review`, enter the reviewer bearer token, agent ID and run ID, and load the requests. The page displays the exact input and operation and can approve, reject or cancel an eligible request. Tokens are kept in the page only, and all data responses are non-cacheable. Decisions require a matching local Origin and JSON content type. The server is intended for direct loopback access, not reverse proxies or production identity. The host must protect credentials and audit denied access. A decision does not resume a run; use the host-controlled resume or reconciliation workflow described above.


## Local request inbox

Approval creation and a delegation renewal wait each append a notice in the same SQLite transaction as the underlying change. `SqliteAgentNotices` provides a tenant- and agent-scoped inbox across runs. Hosts supply an authorization callback for list, individual read and acknowledgement, and must authenticate the actor. Notices contain only the run and action or grant identifiers, not approval inputs or credentials. The `actionable` flag is computed against the current approval, grant and run state; clients must still fetch and authorize the underlying record before acting. Acknowledgements are durable, per reviewer and independent of approval or renewal. Notices and acknowledgement receipts are immutable. Paginated listing may return an empty page with a `nextAfter` cursor when individual items are filtered by policy.

Optionally supply `resolveNotices(scope)` when constructing `createAgentApprovalServer` and open `/review`. Enter an agent ID and reviewer token, then load its notices; an approval notice can open the relevant run's approval list. Acknowledgement only marks the notice as seen. Existing requests created before this feature are not backfilled. The host remains responsible for identity, consent, denied-attempt auditing, database protection and retention. Notice and receipt history currently grows until the database is retired; production retention and distributed delivery remain open.

## Explicit external delivery

`SqliteAgentNoticeDelivery` optionally tracks host-initiated delivery of notices in the same SQLite database. The host supplies a scoped authorization callback for every queue, read, dispatch, recovery and reconciliation operation. The callback receives the authenticated actor, delivery metadata and notice metadata; it must authorize the specific destination and the actor's access to the underlying request. Listing also requires an explicit `authorizeList` callback and filters each entry through read authorization. Destination IDs are host-controlled names, not addresses or URLs supplied by an agent. The host maps them to permitted recipients, obtains consent, configures a secure transport and protects the database. No notifications are sent automatically.

`queue(actor, noticeId, destinationId)` creates at most one delivery per notice and destination. `dispatch(actor, deliveryId, send)` verifies that the request is still actionable, durably marks it sending, then invokes the host callback with notice metadata, destination ID and a stable idempotency key. The callback receives no approval input or credentials. The downstream transport must enforce that key if duplicate delivery matters. A successful callback records delivery, not human acknowledgement or approval. An error or lost response is uncertain and cannot be resent automatically. If the sender process crashes, a trusted host must first establish that it has stopped, call `recover` on the stranded sending record, verify the external outcome, and call `reconcile` with `delivered` or `not_delivered`. A confirmed non-delivery returns to pending with the same key; dispatch rechecks actionability. Attempts are limited to 100 per delivery. `get` and paginated `list` support authorized inspection and recovery.

Each state change appends an immutable event in the same SQLite transaction, recording the delivery revision, operation, initiating principal and host clock time. `history(actor, deliveryId, {after, limit})` requires read authorization and returns a bounded page without message content. A duplicate queue call adds no event. A failed event write prevents dispatch; if recording success after the transport call fails, the outbox attempts to mark the outcome uncertain. If that audit write also fails, it remains sending and needs recovery. The host must authenticate principals, protect audit data and the database, and account for clock accuracy. Existing delivery states created before this history feature are not backfilled, and denied operations are not recorded.

This is local coordination, not a distributed lease. Never recover a sending record while another process might still send it. A notice, recipient policy or authorization may change after the final local check and before an external service accepts the message; the host and downstream transport must handle revocation and stale notifications. The host must classify ambiguous delivery using independent evidence, not a timeout. Delivery records and history contain identifiers and are retained indefinitely; local state does not provide encrypted storage, automatic retry, external delivery guarantees or production scheduling.

`AgentNoticeDeliveryWorker` can be explicitly started by a host to dispatch already queued notices. Configure the outbox, a host-authenticated actor, a destination-aware `send` callback, `maxPerPass` (1–100), `pollMs` (100–3,600,000) and `onError`. Each pass scans one bounded page through the outbox's existing list and per-record authorization, then calls the outbox's dispatch for pending deliveries; dispatch separately checks authorization and actionability. `runOnce` runs a single pass without starting polling. The scan cursor is in memory, wraps after the last page and is lost on restart; newly queued deliveries are eventually seen on a later scan. Other processes can race, but the outbox's transactional state transition allows only one dispatch to claim a pending delivery. Sending and uncertain records are skipped; failures after dispatch require evidence-based reconciliation and are never automatically replayed. Pending deliveries that cannot be dispatched may be reconsidered on later scans, and errors are reported to the host.

`stop` prevents new sends from a started worker and waits for its current pass. If stop occurs after dispatch authorization has begun but before the host callback starts, the delivery is conservatively marked uncertain and must be reconciled even though the callback did not run. Stop cannot cancel a callback already running and can wait indefinitely for a stuck host transport; a standalone `runOnce` also runs to completion. Hosts must bound transport duration, authorize destinations, manage worker lifecycle and independently operate recovery for stranded or uncertain deliveries. This worker does not queue notices, resolve recipients, send any message by itself, or supply distributed scheduling or downstream idempotency.

## HTTPS delivery transport

`createAgentNoticeHttpsTransport({scope, destinations, timeoutMs?})` can be supplied as the worker's `send` callback or to explicit `dispatch`. Each host-configured destination has an `id`, a fixed HTTPS `url`, and either a static `bearerToken` or a host-owned `getBearerToken` callback. URLs cannot contain credentials, query strings or fragments. Tokens must be 32–4,096 printable non-space characters; use separate credentials for separate recipients. The adapter snapshots configuration, accepts messages only for the configured tenant and agent, and uses the destination ID solely to select a configured endpoint. The callback is invoked for each send or verification and may asynchronously supply a fresh short-lived token. Credential retrieval and the request share the timeout; a late credential cannot start a request after the timeout, although the host callback itself is not cancelled. A credential failure also leaves an outbox dispatch uncertain. Hosts must protect tokens, replace the adapter to rotate static credentials, authorize access to each destination and apply network egress policy; HTTPS alone does not prevent a host from configuring an internal address.

The adapter POSTs a versioned JSON object containing the notice ID, tenant, agent, run, kind, subject ID and subject revision. It does not send approval inputs or delegation credentials. It sends the outbox's stable key in `Idempotency-Key`, a bearer token in `Authorization`, rejects redirects and applies a 100–60,000 ms timeout (10 seconds by default). A 2xx response means the receiver accepted the request, not that a person received or read it. The receiver must authenticate the token, authorize the tenant and recipient, and durably deduplicate the idempotency key before acknowledging if duplicate notifications matter. Non-2xx responses, timeouts and connection failures are uncertain; this transport never retries, and the outbox requires independent outcome verification and explicit reconciliation before another attempt. Protect payloads in transit and at the receiver, manage retention, and do not treat a delivery acknowledgement as approval or consent. This generic protocol requires a compatible receiver; it is not a provider-specific integration or a distributed delivery guarantee.

`SqliteAgentNoticeReceiver(path, {scope, maxPending, authorize, clock?})` and `createAgentNoticeReceiverServer({receiver, authenticate})` provide an optional compatible local inbox. The server accepts POST `/notice`, requires a single idempotency key and JSON content type, and calls the host authenticator before accepting at most 8 KiB of JSON. The authenticator must verify the bearer credential and return a stable tenant and sender principal; the receiver's policy separately authorizes each receive, list, individual read and acknowledgement. A fixed tenant and agent scope is checked against every message. The host must provide TLS (for example, a trusted reverse proxy), protect the listener from direct access, and set request, connection and network limits. The provided HTTP listener does not itself encrypt traffic or authenticate credentials.

The existing `createJwtCapabilityAuthenticator` may be passed directly as the receiver's `authenticate` callback for RS256 access tokens; configure its issuer, audience, keys, actor mapping and optional revocation checks as described in [JWT capability authentication](jwt-capability-auth.md). Map rotated tokens for the same service to the same stable sender principal, and separately authorize that principal for the specific receiver and operations. Token verification does not grant access by itself. The host supplies token acquisition, refresh, issuer trust, revocation availability, TLS, audit and production identity provisioning; a token revoked after authentication may still be used by a request already in flight.

Each successful receipt commits the message and sender identity with its delivery key before returning 204. The same key, sender and message returns 204 again, including when the pending backlog is full; changed content or a different sender returns 409. New messages over the configured pending limit return 503 without insertion. Because the sender treats every non-2xx outcome as uncertain, an operator must verify and reconcile that outcome before another attempt. `list` offers bounded scoped pages with per-record authorization, and `acknowledge` records the authorized operator and time atomically. Acknowledgement frees pending capacity but does not approve the underlying request, prove a human saw it, or check that the source request is still actionable. Receipt and acknowledgement rows are immutable and retained indefinitely for deduplication. Hosts must provide storage protection, backups, retention strategy, stable sender identities across credential rotation, and independent policy and audit for denied requests. SQLite coordination depends on the same database and does not supply a distributed or highly available receiver; old binaries or privileged direct database access can bypass controls. Do not close the receiver while operations are in flight.

For a sender whose response was lost, the receiver also accepts authenticated POST `/notice/status` with the same key and exact message. A separate `verify` policy must authorize the sender; 204 confirms an immutable matching receipt, 404 means no matching key was observed, and a conflicting sender or message returns 409. Verification does not create a receipt. `createAgentNoticeHttpsVerifier` uses the same trusted destination configuration as the transport and calls the corresponding `/status` endpoint. Only a 204 is positive evidence; 404 is inconclusive, and other errors fail verification. The host can pass the verifier to `outbox.verifyAndReconcileDelivered(actor, deliveryId, verify)`. This rechecks reconciliation authorization and the delivery revision before atomically recording a delivered decision. A missing receipt or failed verification leaves the delivery uncertain and never authorizes a retry: the original request may still arrive later. The host must trust the configured TLS endpoint and its durable storage, maintain stable sender identity, and arrange independent evidence for any decision that a delivery was not made. Positive receipt proves only acceptance by that receiver, not human notification or approval.

Process-kill acceptance tests exercise a certificate-verified local HTTPS receiver with separate sender and receiver databases. They stop the sender before receiver commit and after receiver commit but before its HTTP response, reopen the stores and verify recovery and tenant isolation. Before commit the sender remains uncertain; after commit it can reconcile from the stored receipt without a second send. These tests do not establish production provider, node-failure or distributed-storage guarantees.

The kind acceptance workflow also runs the HTTPS sender and receiver in separate pods, deletes both at those two boundaries, remounts a single-node host-path volume and verifies the persisted state over TLS after receiver restart. The workflow uses temporary test-only certificates and credentials. It exercises pod replacement on one node, not node loss, production storage, high availability or a third-party notification service.

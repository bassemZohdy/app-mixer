# Local agent event ingress

`SqliteAgentTriggers` stores an event and creates its queued run in one transaction in the same SQLite database as `SqliteAgentRuns`. The host supplies tenant and agent scope, an authenticated source and principal, event ID and type, JSON payload, pinned definition version, retry limit, deadline and maximum outstanding backlog. Event IDs deduplicate within a tenant, agent and source. A matching repeat returns the original run; a changed principal, event type or payload returns a conflict. Duplicate requests are checked before the backlog limit. Payloads are bounded to 256 KiB and can be retrieved by scope and run ID for a trusted worker.

For explicit payload retention, initialize `SqliteAgentTriggers` first, then construct `SqliteAgentTriggerRetention(path, {scope, authorize})` for one tenant and agent. Its async `redact(actor, runId, now?)` checks host authorization and, in one transaction, replaces the payload with JSON null and records the actor and time only if the associated run is `succeeded`, `failed` or `cancelled`. Queued, paused, running and uncertain runs retain their inputs for execution or reconciliation. Repeated authorized redaction returns false. `getRedaction(actor, runId)` separately authorizes reading the immutable redaction record. The host controls scheduling, the actor, clock, authorization and retention policy. Upgrade every inbox reader before enabling redaction: older readers cannot distinguish the null placeholder from a real null payload and may reject subsequent duplicate deliveries.

Hosts may opt in to candidate discovery by providing `authorizeDiscovery(actor, scope)` when constructing the retention store. `listCandidates(actor, {after?, limit?})` returns up to 100 terminal, unredacted run IDs and statuses, ordered by run ID, with `nextAfter` when another page is available. This separate permission grants visibility of all eligible run IDs in that tenant and agent; it does not authorize redaction or expose payloads. Discovery checks permission again before returning, and `redact` independently rechecks its own permission and terminal state. Pages can change between calls, and a candidate may already have been redacted by the time it is acted on. For new event and schedule triggers, the inbox atomically records the host-supplied receipt time; repeated event delivery retains the original time, and schedules record actual firing time rather than the scheduled occurrence time. Pass `receivedBefore` to return only records received strictly before that timestamp, or `includeReceivedAt: true` to include known receipt times without filtering. Older records and records written by older binaries have no trustworthy receipt time and are omitted from filtered results; unfiltered results can still be reviewed. The receipt records reject ordinary updates and deletion, but a privileged database administrator can alter them. New terminal run transitions also atomically record the host-supplied completion time, including cancellation, expiry and reconciliation. Pass `completedBefore` to filter on completion time, or `includeCompletedAt: true` to include known completion times; either cutoff is exclusive and both can be combined. Existing terminal runs and transitions made by older writers do not have a completion time and are omitted from completion-filtered results. Receipt and completion times are distinct, and host clocks can be wrong or inconsistent. The host must choose its own retention policy and schedule, protect the database, and upgrade all writers before relying on timestamp coverage. Large histories may require database scanning.

For optional automatic cleanup, construct `AgentTriggerRetentionWorker` with the retention store, a trusted `actor`, per-candidate `authorize`, positive `minAgeMs`, `maxPerPass` (1–100), `pollMs` (100–3,600,000), and `onError`. Call `runOnce()` for one bounded page or `start()` for polling; call and await `stop()` before closing the store. By default the worker considers terminal records with known receipt times strictly older than its age threshold; set `ageFrom: 'completion'` to use known completion times instead. It checks the host policy, then the store checks discovery and redaction authorization and rechecks the selected timestamp after authorization and terminal state inside the mutation transaction. The worker passes an `AbortSignal` to its candidate policy, the store discovery policy and the store redaction policy; these callbacks can stop promptly when the worker stops. Direct callers can also pass a signal as the third argument to `listCandidates` or fourth argument to `redact`. Stopping fences late policy results, but waits for callbacks that ignore cancellation and cannot undo a completed redaction. Errors are reported to `onError`; failed or denied candidates can be reconsidered after the cursor wraps. Pass a trusted, consistent `clock` when appropriate. Receipt age is not time since completion, and records missing the selected timestamp are never automatically selected. Hosts must approve irreversible cleanup, choose a retention interval, control clock integrity and configure independent scheduling and monitoring. A local process-kill test stops the worker between payload clearing and its audit insert, and again after commit; reopening confirms transaction rollback or completion, deduplication and tenant isolation. A single-node kind test also deletes the worker and manager pods, remounts their host-path volume and checks the same recovery. These tests do not simulate node or storage failure.

After redaction, `get` returns `payload: null` and `payloadRedacted: true`; a genuine null input has no redaction flag. Deduplication still retains source, event ID, principal, event type, run ID and a SHA-256 hash of the canonical payload. Duplicate comparison uses that hash after redaction, so it depends on collision resistance and no longer compares the original bytes. Hashes of predictable payloads can reveal information through guessing. Redaction removes the logical payload from the live table, not necessarily from SQLite free pages, WAL files, replicas, logs, exported data or backups; it is not a secure-erasure guarantee. Protect and expire those copies separately. It does not delete the deduplication record or remove copies made by workers and downstream services.

`createAgentEventIngress` exposes `POST /events` with `{ "agentId": "...", "eventId": "...", "eventType": "...", "payload": ... }`. The host must provide `authenticate(request)`, returning a trusted tenant, principal and source, and `authorize(identity, event, definition)`. Identity fields in the body are rejected. The endpoint checks that the latest agent definition is enabled, rechecks its version after authorization, and enqueues a run with its retry and timeout settings. It returns 202 for a new event, 200 for a duplicate, 409 for a conflicting event, and 429 when the configured backlog is full. Authentication and authorization are repeated even for duplicates.

Set optional `maxInFlight` to an integer from 1 to 10,000 to limit concurrent `POST /events` handlers in one server instance. When full, new requests receive HTTP 503 before authentication or body reading; senders should retry with the same event ID. This is separate from `maxPending`, which limits durable queued work. A slot remains held until the handler finishes, including after a client disconnects, so callbacks that never settle can exhaust capacity. A disconnected request may still enqueue an event; retrying a previously accepted event is deduplicated. Optionally set `requestTimeoutMs` (100–30,000) together with `maxInFlight` to return HTTP 503 when processing exceeds the deadline, stop reading an incomplete body, and discard late callback results before enqueueing. The deadline cannot interrupt synchronous code or forcibly cancel a host callback; a stalled callback keeps its slot until it settles. The ingress passes an `AbortSignal` as the final argument to `authenticate`, `authenticateRaw`, `authorize` and `traceParent`, and aborts it on deadline expiry so cooperative callbacks can stop their work. The PostgreSQL definition view provides this method; a host may also supply `definitions.getWithSignal(tenantId, agentId, signal)` in addition to `get`; ingress uses the signal-aware method for both definition checks and snapshots its function at construction. Otherwise it calls `get(tenantId, agentId)` without a third argument, preserving stores whose third argument selects a version. The host must enforce the same authorization and latest-version semantics in either method. By default, client disconnect alone does not abort it; a disconnected event can still be accepted before its deadline. Set `abortOnDisconnect: true` to abort the same signal and discard late results when a client disconnects before the response finishes. A callback that ignores cancellation retains its in-flight slot until it settles. Disconnection cannot undo an event already enqueued, and disconnect detection races with synchronous work and commit, so senders must retry with the same event ID and handle duplicate acknowledgements. The timeout covers work after the handler starts and is subject to event-loop delays. Callbacks may have their own external side effects. This limit does not bound connections before the HTTP handler or coordinate multiple processes. The host must configure network limits, request deadlines and bounded callbacks separately.

Definition lookups can be asynchronous, including an authorized PostgreSQL definition view. A lookup failure prevents enqueueing. The definition recheck and the SQLite enqueue are not one transaction: a definition can change between them. Hosts must enforce current authorization and definition policy again when executing a queued run.

An optional `observe(observation)` callback receives one low-cardinality response observation per HTTP request: `outcome` is `accepted` (202), `completed` (200, including duplicates and challenges), `rejected` (other non-5xx responses), `unavailable` (5xx), or `disconnected` when the response closes before finishing. Completed responses include a numeric `status`; disconnected observations omit it. Unavailable responses also include a fixed `reason`: `busy` for the concurrency limit, `timeout` for a processing deadline, or `other` for another server failure. `durationMs` measures elapsed monotonic time until response completion or disconnect. The observation contains no tenant, principal, source, event ID, path or payload. A disconnected request may still enqueue later, so its observation is not an acceptance record. Observer exceptions and rejected promises are ignored; callbacks are not awaited or concurrency-limited. The trusted host should use a fast, bounded metrics sink and must not treat these observations as audit records or a complete account of server-side work.

`AgentIngressMetrics` is an optional process-local aggregate for these observations. Construct it with `authorize(actor)`, pass its bound `observe` function to the ingress, and pass the object as `metrics` to a separate `createAgentMetricsServer` with trusted scraper authentication. It emits fixed-outcome `app_mixer_agent_ingress_requests_total` counters, fixed-reason `app_mixer_agent_ingress_unavailable_total` counters, and `app_mixer_agent_ingress_response_seconds` sum and count. The aggregate covers every request observed by that ingress instance, potentially across tenants: authorize access to the entire process-wide aggregate, use a separate protected listener from tenant-scoped metrics, and do not infer tenant isolation from the scraper's identity. Counters reset on restart and are not a durable event journal. Response durations end on disconnect or response completion; `completed` combines duplicate and challenge responses. The host controls transport, authorization, retention and external collection.

An optional host `traceParent(request, identity, event)` callback may return a trusted W3C version-00 traceparent after authentication and authorization. Invalid values and callback failures are ignored, and the latest definition is checked again before enqueueing. No request trace header is trusted automatically; the host must establish that a proxy or other source supplies trustworthy context independently of request authentication. The first accepted context is retained on duplicates. See [durable agent runs](durable-agent-runs.md) for worker opt-in, storage and sampling considerations.

Optionally pass `tracing: {tracer, propagateToRun: true}` to create an OpenTelemetry `agent.event.enqueue` producer span after authentication, authorization and definition checks. The trusted callback's valid parent is used if present; otherwise the span starts a new trace. On successful creation, its span context is stored atomically with a new run so a worker configured with `tracing: {tracer, usePersistedParent: true}` can link its `agent.run` span across processes. A duplicate gets its own producer span but does not replace the original stored context. `propagateToRun` defaults to false; when false, existing callback-based storage remains unchanged. A missing or broken tracer context falls back to the trusted callback context, and telemetry failures do not block ingestion.

The producer span covers the synchronous enqueue operation, not the full HTTP request, authorization, or worker execution. It records only a fixed name and accepted/duplicate outcome, or a sanitized enqueue error; it does not record payload, event type, IDs, source, principal or exception details. Configure the SDK, sampler, exporter and collector separately, and protect persisted trace identifiers. Tracing is best effort, and even a successfully queued event may have no exported span. Do not treat trace data as an audit record or trust incoming trace headers without an independently authenticated boundary.

For signed webhook deliveries, configure `createSignedWebhookAuthenticator({sources, clock?, maxAgeSeconds?})` and pass the returned function as `authenticateRaw` instead of `authenticate` to `createAgentEventIngress`. Each trusted source has a unique `sourceId`, `tenantId`, `principalId` and secret `Uint8Array` of at least 32 randomly generated bytes. Source IDs select host-configured identity and keys; the request body never selects tenant or principal. For rotation, a source may include `previousSecrets` with up to two distinct prior keys alongside its current `secret`. Each must be 32 to 1024 bytes. Deploy the overlap, move senders to the new key, then deploy configuration without retired keys. Every accepted key grants the same source authority, so keep the overlap short and remove a compromised key immediately. The verifier snapshots all keys at construction; existing instances retain their old configuration until replaced. The host must deliver keys securely and coordinate rotation with senders.

Send the exact UTF-8 JSON bytes with `Content-Type: application/json`, `X-App-Mixer-Source`, `X-App-Mixer-Timestamp` (canonical decimal Unix seconds), and `X-App-Mixer-Signature`. The signature is `v1=` followed by lowercase hex HMAC-SHA256 using the source key over the UTF-8 bytes of `v1\n<timestamp>\n<sourceId>\n` followed immediately by the raw request body bytes. The verifier rejects duplicate security headers, unknown sources, invalid signatures and timestamps outside the configured symmetric clock window (300 seconds by default; maximum 3600). Keep clocks synchronized. Signatures are verified before JSON parsing; normal source authorization and definition checks still apply to each delivery, including duplicates. Persisted event-ID deduplication prevents the same source, agent and event ID from creating another run, including after the timestamp window; it does not prevent a sender with a valid key from signing new event IDs. Retain deduplication records for at least the desired replay horizon. Requests are limited to 256 KiB before authentication, so the host must enforce network-level rate, connection and request-time limits.

## Twilio incoming messages

`createTwilioMessageWebhookAdapter({identity, agentId, accountSid, url, authToken, previousAuthTokens?})` supplies form authentication, mapping and acknowledgement options for `createAgentEventIngress`. Configure a dedicated HTTPS POST incoming-message URL in Twilio and pass that exact public URL, including its query string, as `url`; the trusted proxy must forward that endpoint to `/events`. The URL and target identity are host configuration, never taken from the request's Host header or body. Supply the account's 32-character hexadecimal Auth Token; up to two distinct prior tokens can overlap during rotation. Replace the adapter to retire old keys. Twilio's official Node SDK validates the signature using all received form parameters, including unknown future fields. Duplicate fields and ambiguous signature headers are rejected. See [Twilio's incoming message webhook documentation](https://www.twilio.com/docs/messaging/guides/webhook-request) and [signature guidance](https://www.twilio.com/docs/usage/security).

Only authenticated incoming messages with the configured account SID and a valid message SID are mapped, with fixed event type `twilio.message`. The ingress authorization callback must still check sender, destination and other signed fields as appropriate. Successful durable enqueue and duplicate delivery return an empty TwiML response; errors return non-success HTTP status. Retain the signed message ID's deduplication record for the intended replay horizon: Twilio's signature has no freshness timestamp. Use TLS and rate limits, safeguard tokens and retained message contents, and do not use this adapter for outbound delivery status callbacks. Media URLs in the payload are untrusted inputs; fetching media requires separate authorization and network controls.

## GitHub webhooks

`createGithubWebhookAdapter({identity, agentId, eventType, secret, previousSecrets?})` returns `authenticateRaw` and `mapAuthenticatedBody` for `createAgentEventIngress`. Configure one host-selected source identity, target agent, and event type per endpoint. Configure the GitHub webhook to send JSON and use a high-entropy secret of 32 to 1024 bytes. Up to two previous keys can overlap during rotation; replace running instances to retire a key. The adapter follows [GitHub's HMAC-SHA256 body-signature protocol](https://docs.github.com/en/webhooks/using-webhooks/validating-webhook-deliveries), rejecting missing, malformed, duplicate or incorrect signature headers before decoding the body. The host must authorize the source and validate the signed payload's repository, action and other relevant fields in the ingress `authorize` callback.

GitHub signs the body, not `X-GitHub-Delivery` or `X-GitHub-Event`. The adapter ignores both headers, uses the configured event type, and derives an event ID from the raw body hash. A captured signed body therefore deduplicates even if its unsigned headers are changed. Identical bodies from distinct legitimate events also deduplicate, and GitHub's signature contains no timestamp; retained deduplication records are needed for replay protection for as long as the secret and captured signatures may remain valid. Key reuse across endpoints can permit cross-endpoint replay, so use a unique secret per webhook. The host must secure transport, limit requests, and plan deduplication retention. A trusted `mapAuthenticatedBody` callback is available for other raw-authenticated integrations; it runs only after authentication and must derive authorization-relevant fields from authenticated data or trusted configuration.

## GitLab signed webhooks

`createGitlabWebhookAdapter({identity, agentId, eventType, signingToken, previousSigningTokens?, clock?, toleranceSeconds?})` supplies authentication and mapping for `createAgentEventIngress`. Configure a GitLab project or group webhook with a signing token, a unique host-selected source identity, target agent and event type. GitLab's [signed webhook protocol](https://docs.gitlab.com/user/project/integrations/webhooks/#signing-tokens) signs the delivery ID, timestamp and exact raw body with HMAC-SHA256. Use a `whsec_` token containing a canonical base64-encoded 32-byte key. Up to two previous signing tokens can overlap during rotation; replace running instances to retire old keys. This adapter requires signed GitLab webhooks (GitLab 19.0 or newer), and does not fall back to the older plain-text `X-Gitlab-Token`.

The adapter checks a single instance of each security header, a bounded list of `v1` signatures, and a symmetric timestamp window (300 seconds by default, maximum 3600); synchronize clocks. It uses the signed `webhook-id` for durable retry deduplication, and rejects a different body for an existing ID. It ignores unsigned event-type and instance headers; the ingress authorization callback must inspect signed payload fields such as `object_kind`, project, group, user and action to ensure the delivery is appropriate for the tenant and agent. Use separate secrets per endpoint, retain deduplication records for the expected retry and replay horizon, enforce HTTPS and rate limits, and protect retained payloads, which are stored unencrypted. Authentication does not itself authorize agent actions.

The optional `mapAuthenticatedBody` callback receives the authenticated request as its third argument. Headers are not automatically authenticated: custom callbacks must use only values their authenticator verified. The GitLab adapter binds its verified ID and body to the same request before mapping, and does not share authenticated state across requests.

## Shopify HTTPS webhooks

`createShopifyWebhookAdapter({identity, agentId, eventType, secret, previousSecrets?})` supplies raw authentication and mapping for `createAgentEventIngress`. Shopify's [HTTPS webhook signature](https://shopify.dev/docs/apps/build/webhooks/verify-deliveries) is base64 HMAC-SHA256 over the exact request body using the app's client secret. Supply its UTF-8 bytes as `secret` (32–1,024 bytes); up to two distinct previous secrets may overlap during rotation. The adapter snapshots the keys, rejects duplicate or noncanonical signature headers, and verifies before parsing. Replace running instances to retire keys. Shopify notes that rotation can take time to propagate.

**The app secret is shared across shops, and the signature does not bind headers.** The adapter ignores shop domain, topic, delivery ID, timestamp and other headers; it cannot authenticate a merchant, topic or endpoint from them. Configure the fixed source identity, agent and event type at app scope. Do not create tenant-specific or topic-specific endpoints using the same app secret and assume the URL or headers isolate them: a captured valid body and signature can be replayed to another endpoint. The host's authorization callback must validate the signed payload and independently establish the resource's merchant and permitted action using a trusted source before enqueueing or performing any effect. If the body does not contain enough trustworthy information to establish that scope, reject it or use a separate authenticated integration. A signature does not establish business authorization.

The adapter derives an event ID from the raw body hash, so changing unsigned delivery headers cannot bypass deduplication. Identical bodies from distinct legitimate events are also deduplicated. Shopify's signature has no timestamp, so retain deduplication records for the intended replay horizon, protect secrets, enforce HTTPS and rate limits, and plan for encrypted storage where payloads are sensitive. This adapter accepts JSON HTTPS webhooks only; it does not support Pub/Sub or EventBridge delivery.

## Stripe webhooks

`createStripeWebhookAdapter({identity, agentId, secret, previousSecrets?, clock?, toleranceSeconds?})` supplies raw authentication and mapping for `createAgentEventIngress`. Configure one trusted identity and agent per endpoint, and provision the endpoint's Stripe `whsec_` signing secret. The adapter implements Stripe's [timestamped HMAC-SHA256 signature protocol](https://docs.stripe.com/webhooks#verify-manually): it checks the raw body and one or more `v1` signatures, rejects duplicate signature headers and ambiguous timestamps, and checks both past and future timestamps against a nonzero window (300 seconds by default, maximum 3600). Keep clocks synchronized. Up to two previous secrets may overlap during key rotation; replace the running adapter to remove retired keys. Use distinct secrets per endpoint and protect them like credentials.

The adapter accepts Stripe snapshot events with `object: "event"`, a valid `evt_` ID and event type. It derives both event ID and type from the signed body; retries with a fresh signature still deduplicate by event ID, while a changed payload for the same ID conflicts. Thin events are not supported by this adapter. The ingress authorization callback must restrict event type, Stripe account, live/test mode and any other relevant signed fields to the configured tenant and agent. Authentication does not grant permission to execute capabilities or confirm business outcomes. The host must enforce HTTPS, network limits, retention and secure storage; event payloads are stored unencrypted. Keep deduplication records for the full retry and replay horizon.


## Standard Webhooks

`createStandardWebhookAdapter({identity, agentId, secret, previousSecrets?, clock?, toleranceSeconds?})` verifies senders that implement the [Standard Webhooks](https://www.standardwebhooks.com/) symmetric signature scheme, used by Svix-based providers among others. Configure one trusted identity and agent per endpoint. Secrets use the `whsec_` prefix followed by canonical base64 for 24–64 key bytes; up to two distinct previous secrets can overlap during rotation. The adapter requires exactly one `webhook-id`, `webhook-timestamp` and `webhook-signature` header, computes HMAC-SHA256 over `id.timestamp.body` using the exact raw body, and accepts any matching space-separated `v1,<base64>` signature. Other signature versions, including asymmetric `v1a`, are ignored, so a header containing only them is rejected. Timestamps in the past or future outside the window (300 seconds by default, maximum 3600) are rejected. Tests check the specification's published reference vector.

The signed `webhook-id` becomes the event ID, so retried deliveries with fresh signatures deduplicate, while a changed payload for the same ID conflicts. The event type comes from the signed body's `type` field and must be a safe identifier; a body without one is rejected. The ingress authorization callback must restrict event types and any signed account or environment fields to the configured tenant and agent. Authentication does not grant permission to execute capabilities. Provider-specific payload envelopes, asymmetric signatures and secret provisioning are not handled. The host must enforce HTTPS, network limits, retention and secure storage, and keep deduplication records for the provider's full retry horizon.


## Slack Events API

`createSlackWebhookAdapter({identity, agentId, appId, teamId, secret, previousSecrets?, clock?, toleranceSeconds?})` supplies raw authentication, challenge handling and event mapping for `createAgentEventIngress`. Bind the configured app and workspace IDs to a trusted tenant and source identity. The adapter checks [Slack's timestamped request signature](https://docs.slack.dev/authentication/verifying-requests-from-slack/) over the exact raw body, rejects duplicate signature or timestamp headers, and enforces a symmetric clock window (300 seconds by default, maximum 3600). Signing secrets are UTF-8 strings of 32–1,024 printable ASCII characters; up to two distinct previous secrets can overlap during rotation. Replace running instances to retire a secret and keep clocks synchronized.

After successful authentication, a valid `url_verification` challenge receives a JSON 200 response without creating a run, as supported by [Slack's URL verification protocol](https://docs.slack.dev/reference/events/url_verification/). The general ingress `challengeAuthenticatedBody` hook is available only with raw authentication and returns a bounded printable challenge; it executes before event authorization and must be trusted host code used solely for a provider handshake. Ordinary `event_callback` envelopes must match the configured app and workspace and contain a signed event ID and inner event type. The deprecated top-level verification token is removed before the payload is stored. Event IDs deduplicate retries through the existing inbox, and conflicting content with the same ID is rejected. The host's authorization callback must still validate the event type, channel, user, organization and other relevant signed fields before accepting the event.

This adapter accepts JSON Events API callbacks for one workspace, not slash commands, interactions, enterprise-wide events without a workspace ID, or `app_rate_limited` notifications. Arrange a separate handler for unsupported deliveries and monitor provider delivery failures. Slack expects a timely 2xx response; configure suitable network and database timeouts and capacity, and use its delivery monitoring and retry policies. The host owns HTTPS, signing-secret management, ingress rate limits, tenant isolation, payload retention and event permissions. Slack event payloads may contain sensitive content and are stored unencrypted. A valid signature establishes request authenticity, not authorization to run an agent or its capabilities.

The host must configure HTTPS, validate event schemas and permissions in `authorize`, and derive source identities independently of request body data. This protocol requires a sender that can produce the specified signature; provider-specific signing formats require a separate verifier. It is not an identity provider. It does not start a worker or automatically retry events. Separately configured timers and cron are described in [agent schedules](agent-schedules.md). Event payloads are stored unencrypted and may be sensitive; protect the database and backups. Idempotency records are retained indefinitely and need a host-managed retention policy appropriate to source replay windows.

Run claims enforce a per-tenant, per-agent concurrency limit within the same SQLite transaction. The host-driven worker uses the current manifest's `maxConcurrentRuns`; direct registry callers must supply their trusted limit (the default is 1). Running, pause-requested and cancel-requested attempts count until settled or explicitly recovered, including expired leases. This is local SQLite coordination; hosts must not bypass it with old binaries or direct writes and must reconcile an expired worker before retrying. Daily/token quotas and distributed coordination remain open.

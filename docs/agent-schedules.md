# Local agent schedules

`SqliteAgentSchedules` stores tenant- and agent-scoped schedule configurations and their next due time in the same SQLite database as the run registry and trigger inbox. A trusted host uses `save(scope, scheduleId, config, expectedRevision, now)` to create or update a schedule. Configuration has `enabled`, a host-approved `principalId`, and either `{kind: "interval", intervalMs}` or `{kind: "cron", expression}`. Intervals are 1 second to 30 days. A new or changed configuration, including a misfire policy change, starts its schedule from the supplied current time; previously queued runs are not changed.

Cron uses five fields: minute, hour, day of month, month and weekday (0 or 7 is Sunday). Month and weekday fields also accept case-insensitive three-letter names (`JAN`-`DEC`, `SUN`-`SAT`) in lists and ranges, such as `MON-FRI` or `jan,jul`; full names, names in steps on a bare value, and name arithmetic are rejected. `*` and steps on `*` still cover Sunday through Saturday once, and `5-7` means Friday through Sunday. Fields support numeric values, `*`, comma lists, ranges, and steps on `*` or ranges. When both day-of-month and weekday are restricted, either may match. A bare `*` is unrestricted. Unsupported syntax and expressions with no occurrence within nine years are rejected. By default these fields use UTC. Set `rule.timeZone` to a host-approved IANA time zone, such as `America/New_York`, to match local wall-clock time. Nonexistent local times during forward offset changes are skipped; repeated times during backward changes fire once for each matching instant. Occurrences, `scheduledAt` and `coalescedThrough` remain UTC epoch milliseconds. Coalescing skips all other occurrences through observation time, including a repeated local time. The runtime's ICU time-zone database defines offsets; keep deployments consistent and plan for time-zone rule updates, which can change future calculations. A computed `nextAt` is persisted and is not recalculated until the schedule fires or is reconfigured. Zone calculations use the Temporal polyfill and can take more CPU than UTC calculations, especially for dense schedules. Benchmark workload and configure polling capacity accordingly.

Cron rules can also specify `excludeDates`, an array of up to 366 distinct ISO dates (`YYYY-MM-DD`). Every occurrence whose calendar date matches is skipped in the configured time zone, or in UTC if none is configured; this includes both occurrences of a repeated local time. The host owns the calendar and must update future dates explicitly. These one-off dates apply only to cron schedules. Invalid dates, duplicates and rules with no occurrence within the bounded search horizon are rejected. Updating the list creates a new schedule generation and computes a new next occurrence from the update time; it does not cancel already queued runs. Excluded dates and other schedule configuration are retained in schedule history. Coalescing covers only scheduled, non-excluded occurrences and advances past the observation time.

Cron rules may also set `excludeDateRanges` to up to 100 inclusive `{start: 'YYYY-MM-DD', end: 'YYYY-MM-DD'}` ranges. A range excludes each local calendar date from start through end, including both instances of a repeated daylight-saving time; ranges combine with individual and annual excluded dates. Overlapping ranges are allowed. Configuration is copied and retained in immutable history, and the same nine-year search bound, update generation and coalescing behavior apply. Interval schedules do not accept this option. Upgrade all readers and schedulers before writing it because older versions reject the new field.

Cron rules can also set `excludeAnnualDates` to up to 366 distinct `MM-DD` values. These dates are excluded every year in the schedule's configured time zone, or UTC when no zone is set, and combine with one-off `excludeDates`. February 29 is allowed and applies only in leap years. Both occurrences of a repeated local time are excluded. The same bounded search, configuration generation, audit history and coalescing behavior apply. Optionally set `observeAnnualWeekends: true` with a nonempty annual list to also exclude the preceding Friday when an annual date falls on Saturday, or the following Monday when it falls on Sunday. The actual holiday remains excluded; observance can cross a year boundary and is evaluated in the schedule time zone. This is one fixed observance rule, not a jurisdiction-aware calendar or cascading substitute-day calculation; the host owns the calendar. Upgrade all readers and schedulers before writing this option: older versions reject the unrecognized rule field.

`fire` checks the expected schedule revision, due time and backlog in an immediate SQLite transaction, then creates the trigger, queued run and next cursor together. A stale competing scheduler fails; a host can use `getOccurrence(scope, scheduleId, generation, scheduledAt)` to recover the run ID after a lost response. Each configuration update increments the generation, so a reconfigured occurrence is distinct. Backpressure leaves the cursor unchanged. By default, missed occurrences are processed one per schedule per polling pass in due-time and schedule-ID order, so a long outage can create a backlog. Hosts may set `misfire: 'coalesce'` in the schedule configuration to enqueue one run representing all occurrences through the trusted fire time and advance to the first occurrence after that time. The trigger payload contains `scheduledAt` for the earliest missed occurrence and `coalescedThrough` for the observation time; agents must be designed to process that entire interval. Interval schedules retain their original phase, and cron uses the first matching instant after observation. Explicit `misfire: 'catchUp'` has the same behavior as omitting the option. Each selected policy is persisted with schedule configuration and history. Only the earliest occurrence has a run and can be recovered with `getOccurrence`; suppressed occurrences do not have individual records or runs. Use catch-up when every individual occurrence must execute. Backpressure, failed audit insertion or failed run creation roll back the coalesced run and cursor together. Hosts must choose polling and backlog limits for their workload. `duePage(scope, now, limit, after)` exposes a bounded keyset scan with a continuation cursor. Each page is a current snapshot; restart the scan to observe schedules inserted or moved before the cursor.

A trusted host may pass `wakeup: {runId, revision}` in the `fire` policy to resume that specific paused run instead of creating a new run. The schedule occurrence, retained wakeup payload, run transition, next schedule time and schedule history commit in one SQLite transaction. The target must be in the same tenant and agent, match the policy definition version, and satisfy the existing revision, deadline, retry, approval and delegation checks. A full new-run backlog does not block this path because it does not create a run. `getOccurrence` recovers the target run ID after a lost response. Coalescing retains the earliest scheduled time and observation time in the wakeup payload. The run's existing trace parent is preserved; `traceParent` is rejected for this path. The host must authenticate and authorize the scheduler, select and authorize the target, deliver retained wakeups to the worker, and manage payload retention as described in [durable runs](durable-agent-runs.md). The schedule worker can optionally select wakeup targets as described below.

`AgentScheduleWorker` is explicitly started by a trusted host or invoked with `runOnce`. It scans one bounded page per pass, checks the current enabled agent definition, calls host authorization for each occurrence, rechecks the definition and authorizes the occurrence again immediately before enqueueing, and uses its version, retry limit and timeout when creating the run. The worker advances its in-memory scan cursor even when authorization denies or fails, so later due schedules can be considered; it restarts at the beginning after reaching the end. Denied schedules are reconsidered on the next scan. Worker configuration values and callback references are captured at construction; replace the worker to change them. Referenced definition stores and callback-owned policy state remain live. New or changed schedules before the cursor wait until that scan completes. Restarting the worker loses the cursor, and pagination is not a consistent cross-page snapshot. `stop` stops polling and waits for an in-flight pass, including a manual `runOnce` pass; an authorization or definition lookup still in progress cannot enqueue after stop. The worker passes an `AbortSignal` to `authorize` and uses the optional `definitions.getWithSignal(tenantId, agentId, signal)` for both definition reads when provided, falling back to `get` otherwise. By default, `stop` aborts the signal and waits for callbacks; callbacks that ignore it can delay shutdown indefinitely. A later pass retries the interrupted occurrence. Optionally set both `callbackTimeoutMs` (100 to 30000) and `maxPendingCallbacks` (1 to 100) to bound individual definition and authorization callbacks per worker. Each receives a signal that aborts on timeout or stop, including signal-aware definition lookups. A timed-out or stopped callback keeps its capacity slot until it settles; late results cannot enqueue a run. The pass can finish and `stop` can return even if the callback ignores cancellation. Saturation and timeouts fail that occurrence and report an error, with later scans retrying it. The limit is per worker instance and does not interrupt synchronous work or undo callback side effects. Without these options, shutdown continues to wait for callbacks. Policy can still change between the final authorization callback and the SQLite commit; hosts needing atomic policy enforcement must coordinate that separately. Hosts must authorize schedule creation, updates and each activation, validate the schedule principal, and operate a separate durable run worker. The HTTP ingress reserves source IDs beginning with `schedule.` for internal schedules.

To route scheduled occurrences to paused runs, configure `AgentScheduleWorker` with `wakeup: {runs, select, authorize}`. The run registry and schedules must use the same on-disk SQLite database. `select(schedule, definition, signal)` returns a host-selected run ID or `undefined` for normal new-run creation. The separate wakeup authorizer receives the schedule, definition, a target containing only run ID, revision, definition version and status, and a signal; it must approve the specific resume. The worker checks the selection twice, rechecks definition and both policies, and passes the target revision into the atomic schedule transaction. A changed route or run, wrong definition, denied authorization, or a lifecycle gate leaves the occurrence due for a later pass. The existing callback timeout and capacity settings also cover these callbacks. The target's existing trace parent is preserved even when producer tracing is enabled. A host must authorize selection and payload reads, explicitly deliver retained wakeups to the resumed run and manage checkpoint cursors. A local test exercises selection, tracing and a configured worker consuming the payload.

Definition lookups can be asynchronous, including an authorized PostgreSQL definition view. Lookup failures prevent activation; stopping waits for an in-flight lookup and prevents a subsequent enqueue. The definition recheck and SQLite transaction are not atomic across stores, so hosts must enforce current authorization and definition policy again when executing a queued run.

## Schedule history

Each successful `save` or `fire` appends an immutable schedule event in the same SQLite transaction as its configuration change or occurrence and run creation. Events include the schedule revision, generation, configuration, next time and host-supplied operation time; fired events also include the run ID and scheduled time. A failed history insert rolls back the entire operation. Hosts may pass an authenticated, authorized principal ID as the final `actorId` argument to `save` or `fire`; `AgentScheduleWorker` accepts a host-configured `auditActorId` for its activations. Omitted actors are recorded as null. The schedule's configured principal is a separate field and is not proof of who made the change.

`SqliteAgentScheduleHistory(path, {scope, authorize})` provides tenant- and agent-scoped, paginated access, with optional filtering by schedule ID. It separately authorizes listing and each event read. Hosts must authenticate callers and authorize the write operations and actor IDs; the schedule registry does not authenticate them. History contains configuration and identifiers and must be protected. Failed or denied attempts are not recorded, earlier changes are not backfilled, and older binaries or direct database writes can bypass this history. The supplied clock is not independently verified. Events are retained indefinitely and are not a substitute for production audit.

This is a local SQLite scheduler. Time must come from a trusted, consistent clock; process downtime delays firing, and concurrency with old binaries or direct database writes is unsupported. It does not supply distributed leader election, production identity, or calculated holiday calendars. Schedule and trigger records require host-managed retention. Timer/cron activation does not itself retry an uncertain external effect.

Process-termination tests stop a separate SQLite schedule writer before inserting the trigger receipt, before inserting the fired audit event, and after commit. They reopen the database and verify rollback or persistence of the run, inbox, receipt, schedule cursor and history; retry produces one occurrence and leaves another tenant unchanged. The same crash points also exercise a cron schedule spanning an excluded date range, verifying the post-recovery next occurrence, retained configuration and history, retry deduplication, and tenant isolation. Additional termination tests cover scheduled wakeups before receipt insertion, before schedule history insertion and after commit; they verify that the run state, wakeup, cursor and history roll back or persist together, with retry and tenant isolation. These tests cover a local SQLite database, not node failure or a distributed scheduler.

An optional `AgentScheduleWorker` setting `tracing: {tracer, propagateToRun: true}` emits a root `agent.schedule.enqueue` producer span for an authorized firing and stores its valid trace context with the run in the same SQLite transaction. A `DurableAgentWorker` configured with `tracing: {tracer, usePersistedParent: true}` can link its run span after a restart; an acceptance test closes the stores and verifies the link from a separate worker process. The producer span contains no schedule, tenant, principal, run or payload identifiers; enqueue failures use a fixed error type. Tracing is disabled by default, and propagation is separately opt-in. Tracer failures do not prevent activation; a database failure while storing enabled trace context rolls back the entire occurrence. Hosts control trace exporters, access and retention. Direct trusted callers of `fire` may supply a validated version-00 `traceParent` in the fire policy; it is immutable once stored. Tracestate and baggage are not persisted.

`SqliteAgentScheduleMetrics` opens the existing schedule database read-only for one host-selected tenant and agent. Supply `scope`, an aggregate `authorize(actor, scope)` policy and optionally a trusted `clock`. `snapshot(actor)` returns the number of enabled schedules due at the sampled time, enabled schedules not yet due, disabled schedules, and the age in seconds of the oldest due schedule. `render(actor)` exposes fixed-label Prometheus gauges `app_mixer_agent_schedules` and `app_mixer_agent_oldest_schedule_due_seconds`; no tenant, agent, schedule or principal identifiers are emitted. The policy is checked before and after the read and must authorize the complete selected aggregate. Invalid clock or database values fail the read. The count is schedules, not missed occurrences, and does not prove that any worker is alive or authorized. It can be used with `createAgentMetricsServer`; the host must authenticate scrapers, secure transport and coordinate production collection. Alternatively, set `includeScheduleBacklog: true` on `SqliteAgentRunMetrics` to include these gauges in the same scrape as run and optional action gauges. The schedule table must already exist, and the run-metrics policy must authorize the entire run and schedule aggregate. A combined render reads all enabled gauges in one SQLite read transaction and samples the clock once; separate reads and scrapes may differ.

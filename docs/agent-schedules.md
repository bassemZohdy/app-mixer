# Local agent schedules

`SqliteAgentSchedules` stores tenant- and agent-scoped schedule configurations and their next due time in the same SQLite database as the run registry and trigger inbox. A trusted host uses `save(scope, scheduleId, config, expectedRevision, now)` to create or update a schedule. Configuration has `enabled`, a host-approved `principalId`, and either `{kind: "interval", intervalMs}` or `{kind: "cron", expression}`. Intervals are 1 second to 30 days. A new or changed configuration starts its schedule from the supplied current time; previously queued runs are not changed.

Cron uses five UTC fields: minute, hour, day of month, month and weekday (0 is Sunday). Fields support numeric values, `*`, comma lists, ranges, and steps on `*` or ranges. When both day-of-month and weekday are restricted, either may match. A bare `*` is unrestricted. Unsupported syntax and expressions with no occurrence within nine years are rejected. No local timezone or daylight-saving conversion is applied.

`fire` checks the expected schedule revision, due time and backlog in an immediate SQLite transaction, then creates the trigger, queued run and next cursor together. A stale competing scheduler fails; a host can use `getOccurrence(scope, scheduleId, generation, scheduledAt)` to recover the run ID after a lost response. Each configuration update increments the generation, so a reconfigured occurrence is distinct. Backpressure leaves the cursor unchanged. Missed occurrences are processed one per schedule per polling pass in due-time and schedule-ID order, so a long outage can create a backlog; hosts must choose polling and backlog limits for their workload. `duePage(scope, now, limit, after)` exposes a bounded keyset scan with a continuation cursor. Each page is a current snapshot; restart the scan to observe schedules inserted or moved before the cursor.

`AgentScheduleWorker` is explicitly started by a trusted host or invoked with `runOnce`. It scans one bounded page per pass, checks the current enabled agent definition, calls host authorization for each occurrence, rechecks the definition after authorization, and uses its version, retry limit and timeout when creating the run. The worker advances its in-memory scan cursor even when authorization denies or fails, so later due schedules can be considered; it restarts at the beginning after reaching the end. Denied schedules are reconsidered on the next scan. New or changed schedules before the cursor wait until that scan completes. Restarting the worker loses the cursor, and pagination is not a consistent cross-page snapshot. `stop` stops polling and waits for an in-flight pass; an authorization still in progress cannot enqueue after stop. Hosts must authorize schedule creation, updates and each activation, validate the schedule principal, and operate a separate durable run worker. The HTTP ingress reserves source IDs beginning with `schedule.` for internal schedules.

## Schedule history

Each successful `save` or `fire` appends an immutable schedule event in the same SQLite transaction as its configuration change or occurrence and run creation. Events include the schedule revision, generation, configuration, next time and host-supplied operation time; fired events also include the run ID and scheduled time. A failed history insert rolls back the entire operation. Hosts may pass an authenticated, authorized principal ID as the final `actorId` argument to `save` or `fire`; `AgentScheduleWorker` accepts a host-configured `auditActorId` for its activations. Omitted actors are recorded as null. The schedule's configured principal is a separate field and is not proof of who made the change.

`SqliteAgentScheduleHistory(path, {scope, authorize})` provides tenant- and agent-scoped, paginated access, with optional filtering by schedule ID. It separately authorizes listing and each event read. Hosts must authenticate callers and authorize the write operations and actor IDs; the schedule registry does not authenticate them. History contains configuration and identifiers and must be protected. Failed or denied attempts are not recorded, earlier changes are not backfilled, and older binaries or direct database writes can bypass this history. The supplied clock is not independently verified. Events are retained indefinitely and are not a substitute for production audit.

This is a local SQLite scheduler. Time must come from a trusted, consistent clock; process downtime delays firing, and concurrency with old binaries or direct database writes is unsupported. It does not supply distributed leader election, production identity, arbitrary timezones or calendar exclusions. Schedule and trigger records require host-managed retention. Timer/cron activation does not itself retry an uncertain external effect.

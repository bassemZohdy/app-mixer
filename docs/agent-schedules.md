# Local agent schedules

`SqliteAgentSchedules` stores tenant- and agent-scoped schedule configurations and their next due time in the same SQLite database as the run registry and trigger inbox. A trusted host uses `save(scope, scheduleId, config, expectedRevision, now)` to create or update a schedule. Configuration has `enabled`, a host-approved `principalId`, and either `{kind: "interval", intervalMs}` or `{kind: "cron", expression}`. Intervals are 1 second to 30 days. A new or changed configuration, including a misfire policy change, starts its schedule from the supplied current time; previously queued runs are not changed.

Cron uses five fields: minute, hour, day of month, month and weekday (0 or 7 is Sunday). Month and weekday fields also accept case-insensitive three-letter names (`JAN`-`DEC`, `SUN`-`SAT`) in lists and ranges, such as `MON-FRI` or `jan,jul`; full names, names in steps on a bare value, and name arithmetic are rejected. `*` and steps on `*` still cover Sunday through Saturday once, and `5-7` means Friday through Sunday. Fields support numeric values, `*`, comma lists, ranges, and steps on `*` or ranges. When both day-of-month and weekday are restricted, either may match. A bare `*` is unrestricted. Unsupported syntax and expressions with no occurrence within nine years are rejected. By default these fields use UTC. Set `rule.timeZone` to a host-approved IANA time zone, such as `America/New_York`, to match local wall-clock time. Nonexistent local times during forward offset changes are skipped; repeated times during backward changes fire once for each matching instant. Occurrences, `scheduledAt` and `coalescedThrough` remain UTC epoch milliseconds. Coalescing skips all other occurrences through observation time, including a repeated local time. The runtime's ICU time-zone database defines offsets; keep deployments consistent and plan for time-zone rule updates, which can change future calculations. A computed `nextAt` is persisted and is not recalculated until the schedule fires or is reconfigured. Zone calculations use the Temporal polyfill and can take more CPU than UTC calculations, especially for dense schedules. Benchmark workload and configure polling capacity accordingly.

Cron rules can also specify `excludeDates`, an array of up to 366 distinct ISO dates (`YYYY-MM-DD`). Every occurrence whose calendar date matches is skipped in the configured time zone, or in UTC if none is configured; this includes both occurrences of a repeated local time. The host owns the calendar and must update future dates explicitly. This is a fixed list of dates, not a recurring holiday calendar, and it applies only to cron schedules. Invalid dates, duplicates and rules with no occurrence within the bounded search horizon are rejected. Updating the list creates a new schedule generation and computes a new next occurrence from the update time; it does not cancel already queued runs. Excluded dates and other schedule configuration are retained in schedule history. Coalescing covers only scheduled, non-excluded occurrences and advances past the observation time.

`fire` checks the expected schedule revision, due time and backlog in an immediate SQLite transaction, then creates the trigger, queued run and next cursor together. A stale competing scheduler fails; `AgentScheduleWorker` treats that revision conflict as a lost race rather than an error, so several worker processes on one host may share one SQLite file and each occurrence still becomes exactly one run. SQLite does not coordinate across hosts; firing from several nodes needs a shared store, which is not provided. a host can use `getOccurrence(scope, scheduleId, generation, scheduledAt)` to recover the run ID after a lost response. Each configuration update increments the generation, so a reconfigured occurrence is distinct. Backpressure leaves the cursor unchanged. By default, missed occurrences are processed one per schedule per polling pass in due-time and schedule-ID order, so a long outage can create a backlog. Hosts may set `misfire: 'coalesce'` in the schedule configuration to enqueue one run representing all occurrences through the trusted fire time and advance to the first occurrence after that time. The trigger payload contains `scheduledAt` for the earliest missed occurrence and `coalescedThrough` for the observation time; agents must be designed to process that entire interval. Interval schedules retain their original phase, and cron uses the first matching instant after observation. Explicit `misfire: 'catchUp'` has the same behavior as omitting the option. Each selected policy is persisted with schedule configuration and history. Only the earliest occurrence has a run and can be recovered with `getOccurrence`; suppressed occurrences do not have individual records or runs. Use catch-up when every individual occurrence must execute. Backpressure, failed audit insertion or failed run creation roll back the coalesced run and cursor together. Hosts must choose polling and backlog limits for their workload. `duePage(scope, now, limit, after)` exposes a bounded keyset scan with a continuation cursor. Each page is a current snapshot; restart the scan to observe schedules inserted or moved before the cursor.

`AgentScheduleWorker` is explicitly started by a trusted host or invoked with `runOnce`. It scans one bounded page per pass, checks the current enabled agent definition, calls host authorization for each occurrence, rechecks the definition after authorization, and uses its version, retry limit and timeout when creating the run. The worker advances its in-memory scan cursor even when authorization denies or fails, so later due schedules can be considered; it restarts at the beginning after reaching the end. Denied schedules are reconsidered on the next scan. New or changed schedules before the cursor wait until that scan completes. Restarting the worker loses the cursor, and pagination is not a consistent cross-page snapshot. `stop` stops polling and waits for an in-flight pass; an authorization still in progress cannot enqueue after stop. Hosts must authorize schedule creation, updates and each activation, validate the schedule principal, and operate a separate durable run worker. The HTTP ingress reserves source IDs beginning with `schedule.` for internal schedules.

Definition lookups can be asynchronous, including an authorized PostgreSQL definition view. Lookup failures prevent activation; stopping waits for an in-flight lookup and prevents a subsequent enqueue. The definition recheck and SQLite transaction are not atomic across stores, so hosts must enforce current authorization and definition policy again when executing a queued run.

## Running workers in one process

`AgentWorkerHost` runs a fixed set of workers that share the `start()`/`stop()` contract, such as `AgentScheduleWorker`, `AgentActionRecoveryWorker` and `AgentNoticeDeliveryWorker`, and drains them together:

```js
const host = new AgentWorkerHost({workers: {schedules, recovery, notices}, stopTimeoutMs: 20000, onError: (name, error) => log(name, error)});
host.handleSignals(process, result => process.exit(result.timedOut.length || result.failed.length ? 1 : 0));
await host.start();
// readiness probe: host.ready()
```

Workers start in the order given. If one throws while starting, those already started are stopped and the error is rethrown, so the process does not run with a partial set. `stop()` stops every started worker in parallel, bounds each with `stopTimeoutMs` (100 ms to 10 minutes), and resolves with the names that stopped, timed out or failed; repeated calls return the same result. `ready()` is true only while all workers run, and becomes false as soon as shutdown begins. `handleSignals` stops on the first SIGTERM or SIGINT and removes its handlers; the host decides whether and how to exit. Set `stopTimeoutMs` below the platform's termination grace period (for example Kubernetes `terminationGracePeriodSeconds`) so the result is reported before the process is killed.

A schedule pass interrupted by shutdown does not fire after the stop request; the occurrence stays due and the next worker fires it. A worker that times out may still be running its pass when the process exits, so the fencing and reconciliation each worker already relies on still apply. Windows does not deliver SIGTERM to Node.js handlers. The host does not restart failed workers, choose replica counts or coordinate firing across hosts; that remains the deployment's job.

## Schedule history

Each successful `save` or `fire` appends an immutable schedule event in the same SQLite transaction as its configuration change or occurrence and run creation. Events include the schedule revision, generation, configuration, next time and host-supplied operation time; fired events also include the run ID and scheduled time. A failed history insert rolls back the entire operation. Hosts may pass an authenticated, authorized principal ID as the final `actorId` argument to `save` or `fire`; `AgentScheduleWorker` accepts a host-configured `auditActorId` for its activations. Omitted actors are recorded as null. The schedule's configured principal is a separate field and is not proof of who made the change.

`SqliteAgentScheduleHistory(path, {scope, authorize})` provides tenant- and agent-scoped, paginated access, with optional filtering by schedule ID. It separately authorizes listing and each event read. Hosts must authenticate callers and authorize the write operations and actor IDs; the schedule registry does not authenticate them. History contains configuration and identifiers and must be protected. Failed or denied attempts are not recorded, earlier changes are not backfilled, and older binaries or direct database writes can bypass this history. The supplied clock is not independently verified. Events are retained indefinitely and are not a substitute for production audit.

This is a local SQLite scheduler. Time must come from a trusted, consistent clock; process downtime delays firing, and concurrency with old binaries or direct database writes is unsupported. It does not supply distributed leader election, production identity, recurring holiday calendars. Schedule and trigger records require host-managed retention. Timer/cron activation does not itself retry an uncertain external effect.

## Shared schedules across nodes

`SqliteAgentSchedules` coordinates only the processes that share one SQLite file. `PostgresAgentSchedules({enabled: true, query, transaction})` keeps schedules on one PostgreSQL primary so workers on separate nodes can poll them. Call `initialize()` once. It uses the same configuration rules, next-time calculation and misfire handling (`catchUp` or `coalesce`) as the SQLite store. When `now` is omitted, it uses the database clock, so node clock skew does not matter.

- **`save(scope, scheduleId, config, expectedRevision, now?, actorId?)`** creates or replaces a schedule with optimistic concurrency. Every change starts a new generation.
- **`fire(scope, scheduleId, expectedRevision, policy, {nodeId, now?, actorId?})`** fires one due occurrence. It locks the schedule row, advances it, and inserts one durable run request with a new run ID, all in one transaction. Another node firing the same revision gets `Schedule revision conflict`. The run request's primary key (schedule, generation, scheduled time) rejects a second request for an occurrence even if the lock were bypassed. `policy.maxPending` bounds the shared backlog of unstarted requests.
- **`fireDue(scope, policy, {nodeId, maxFires?, authorize?})`** is one polling pass. It fires every due occurrence, catching up missed ones in order, and counts the races it lost to other nodes.
- **`claimRun(scope, workerId, leaseMs)`** claims the oldest unstarted run request for a lease of database time. A claim that expired can be taken over. `markStarted(scope, runId, token)` records the hand-off and returns false if the claim expired or was taken over.
- **`runs(scope, scheduleId)`** lists fired occurrences with their status and claim count. **`history(scope, scheduleId)`** lists the change and fire events.

Firing is exactly once per occurrence. The hand-off to an executor is at least once: if a node creates the run and dies before `markStarted`, another node can claim the same request after the lease expires. The run ID is stable, so create the run under that ID in a registry that refuses duplicates. `PostgresAgentRuns.create` refuses an existing run ID across nodes ([durable-agent-runs.md](durable-agent-runs.md#shared-run-registry-across-nodes)); two nodes with separate SQLite run registries could both start a reclaimed request.

The host must authorize schedule changes and firing (`authorize` on `fireDue`), authenticate nodes, protect the primary connection, and prune old run requests and events. Unlike the SQLite store, history rows are not protected by triggers.

`packages/agent/test/postgres-schedule-nodes.test.mjs` (run in the PostgreSQL CI job) starts two processes, each with its own pool, polling four one-second schedules. After about 3.5 seconds, one node is killed with SIGKILL. When the run ends, every schedule has one occurrence per second with none missing or repeated, the fire history matches the run requests, both nodes fired occurrences and lost firing races, and every request was started. Only a claim held by the killed node may be taken over. Without the row lock in `fire`, the nodes collide on the occurrence key and the test fails.

# OpenAPI and capability registry: local foundation

`importOpenAPI` discovers operation IDs, methods and paths from an already parsed OpenAPI 3.0 or 3.1 JSON document. It produces candidates only. Discovery performs no HTTP calls, does not resolve path-item `$ref`, does not trust server URLs or credentials, and grants no permission to invoke an operation. Missing or duplicate operation IDs and unsupported path items are rejected. The importer does not yet interpret request/response schemas, security schemes, YAML, external references or operation-specific servers.

`CapabilityRegistry` requires a host-supplied audit sink and explicit authorization function, input validator and executor for each operation. It records attempts and outcomes without input or result payloads; a failed attempt audit blocks execution. A failed success audit occurs after execution and leaves the result uncertain, so callers must not automatically retry side-effecting operations. An unregistered capability cannot be invoked. Every invocation requires a tenant ID and principal ID from the trusted server; the same policy and validation run for UI and agent origins before execution. Input is cloned before validation and execution. These functions are trusted application code, not values supplied by a client or model.

This is a local foundation, not a production authorization solution. The caller must authenticate the actor and derive the invocation context server-side; never accept tenant or principal IDs from an untrusted client as proof of identity. A restricted GET binding validates supported primitive path/query parameters from an OpenAPI document. General OpenAPI schema validation, write operations, credential management and approval are not implemented. The provided local invocation server requires trusted host callbacks for authentication and authentication-failure audit. The initial P1-06 scope covers a restricted GET sample through both UI and agent paths; broader OpenAPI support and production security remain roadmap work.


## Local invocation endpoint

`createCapabilityServer(registry, authenticate, auditFailure)` creates a server with `POST /capabilities/:operationId/invoke`. The host authentication callback derives `{tenantId, principalId}` from trusted credentials; clients cannot supply those fields in the request body. The body contains `{ "origin": "ui" | "agent", "input": ... }`. Both origins reach the same registry policy and validator. Authentication failures are sent to the required `auditFailure` callback; if that audit fails, access is blocked. Bind to loopback for development. The host must supply a secure authentication mechanism and durable audit sink for production.

The integration test binds an imported GET candidate to a local sample REST service via an explicitly registered trusted executor. It does not automatically execute arbitrary OpenAPI URLs. Integration into the default runtime agent remains open.

`SqliteCapabilityAudit` offers an opt-in local durable sink: construct it with a database path and pass `audit.record` to `CapabilityRegistry`. Host-authorized code can read a tenant's events with `audit.list(tenantId, {after, limit})`, using the last sequence as the next cursor. It records timestamps, tenant, principal, operation, invocation ID and outcome, but no input or result. Each attempt and its outcome share a generated invocation ID, including when requests overlap. The host must secure the database and backups, authorize reads, provision storage and retention, and protect the clock. It is not tamper-proof or a distributed audit service; authentication failures still require a separate sink. Attempt and outcome are separate writes, so a crash or failed outcome write can leave an attempt without an outcome. An uncertain invocation must be reconciled before retrying side effects. Close the sink only after stopping invocations.

`PostgresCapabilityAudit` is an optional shared sink for instances using the same PostgreSQL primary. Provide a host-owned async `query(sql, parameters)` adapter returning `rows` and `rowCount`, run `initialize()` through a trusted migration connection before accepting traffic, and pass `audit.record` to each registry. `await audit.list(tenantId, {after, limit})` returns a tenant's events in per-tenant sequence order. Each insert atomically advances a locked per-tenant counter and writes its event, so a later committed event cannot be paged past an earlier uncommitted event from another writer. The adapter must use autocommitted statements against the same primary; do not return before commit or read from a lagging replica. Sequences are scoped to a tenant and are not globally ordered. The host owns and closes connections, authenticates callers, authorizes every read and protects audit metadata, backups and the clock.

Use a trusted schema and restricted `search_path`, TLS, limited database roles and bounded connection and statement timeouts. Restrict event updates and deletions through database permissions and maintain independent backups and audit controls: this sink is not tamper-proof against a privileged database administrator. Attempt and outcome remain separate writes, so an interrupted or failed outcome audit can leave an uncertain external effect. Database errors block an invocation before execution when the attempt cannot be recorded; a failure after execution must be reconciled before retry. Authentication failures still need a separate sink. The PostgreSQL CI test covers concurrent writers and a held transaction on a real service; production failover, retention, rollout and audit integrity remain host responsibilities.


## Restricted OpenAPI GET binding

`createOpenAPIGetBinding(document, operationId, {baseURL, authorize, headers})` creates a candidate and registry binding for one explicitly selected GET operation. The host supplies the trusted base URL, authorization policy and optional fixed headers. HTTPS is allowed for trusted configured hosts; plain HTTP is restricted to loopback. Imported server URLs and credentials are ignored. Redirects are rejected, the upstream request has a timeout, and JSON responses are limited to 1 MiB. No write operation or retry is performed.

The binding supports only primitive `string`, `integer`, `number`, and `boolean` path and query parameters with basic length or numeric bounds. Path strings are restricted to letters, digits, underscores and hyphens. Unsupported schemas, references, styles, request bodies, unknown input fields and invalid parameters are rejected. It is not a general OpenAPI validator or executor. Register the returned binding in a `CapabilityRegistry` with a durable audit sink and invoke through a host-authenticated boundary. Production DNS/network policy, credentials, tenant isolation and complete schema support remain future work.


## UI and agent adapters

`createCapabilityActionHandler` maps explicitly named A2UI events to host-provided capability invocations. `createCapabilityTool` creates a LangChain tool for a host-selected operation. Both must be connected by trusted host code to the same authenticated capability boundary; the model and UI do not supply the principal or tenant identity. Browser code must use a same-origin authenticated proxy and must not contain server credentials. The optional LangGraph tool-calling mode can execute explicitly configured tools. Generated applications do not yet configure these adapters automatically; tool bindings must be scoped by trusted host code to the authenticated actor and tenant.

An optional `authorizeInput(context, input)` registration callback provides an additional authorization check after input validation. It receives copies of the actor context and validated input, and must return true to permit execution. A denial records the usual denied outcome; exceptions record failure. It does not replace the required initial actor authorization. Policies that depend on mutable resource state must enforce their invariants atomically with the resource operation.

Internal capability dispatch may use the `service` invocation origin; the HTTP endpoint still accepts only `ui` and `agent`. Origin does not alter authorization or audit identity.

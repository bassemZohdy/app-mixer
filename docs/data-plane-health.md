# Data Plane health probes

Publication lookups may be asynchronous. Readiness shares one in-flight publication/dependency check and applies its configured timeout; a timed-out lookup occupies that slot until it settles. Hosts must bound database operations, since the adapter cannot cancel a repository lookup itself. If the first lookup finishes after the check times out or draining starts, the adapter does not start the subsequent dependency check or recheck. A Data Plane reading a shared repository depends on that repository's availability.

`createDataPlane(repository, {health: {timeoutMs, check?}})` enables `GET /health/live` and `GET /health/ready` on the same HTTP server as `/application`. Without this option both routes return 404. Liveness responds 200 when the server can handle a request. Readiness responds 200 only when a local publication exists and the optional host-supplied dependency check resolves to `true`; missing publications, false results, errors and timeouts return 503. Responses expose only a generic status and use `Cache-Control: no-store`. Neither probe contacts the optional Control Plane unless the host explicitly adds such a check.

The readiness timeout must be between 100 and 30,000 milliseconds. The optional check receives an `AbortSignal`; it should stop promptly when aborted. Concurrent readiness requests share one dependency check. If it ignores cancellation, subsequent readiness requests remain unavailable without starting additional checks until it settles. The local repository is synchronous, so a blocked repository call or blocked event loop cannot be interrupted by this timeout. A liveness response does not prove downstream business operations will succeed. The host must select checks that represent its serving dependencies, secure the listener with appropriate network policy, configure probe intervals and thresholds, and test deployment-specific failure and restart behavior. This provides probe endpoints, not complete telemetry, distributed health coordination or Kubernetes deployment.

A host can call `server.beginDrain()` on the returned Data Plane server before stopping it. This irreversible, idempotent action makes readiness return 503 immediately, including readiness checks already waiting on a dependency. It aborts the dependency signal and prevents new checks; a callback that ignores abort can still remain active. Liveness stays 200 and publication reads continue during the handoff. Allow time for the load balancer to remove the instance, then call `server.close()` and wait for active connections before closing the repository. A host must impose its own termination deadline and decide how to handle lingering connections. The method does not itself stop the server, delay shutdown, terminate connections or coordinate load balancers. Health routes must be enabled for an orchestrator to observe readiness.

The local Data Plane service calls `beginDrain()` on SIGTERM or SIGINT. Set `DATA_DRAIN_DELAY_MS` to 0–30,000 to keep serving while readiness is unavailable before closing; a nonzero delay requires `DATA_HEALTH_ENABLED=true`. The Compose profile passes this optional setting, defaulting to zero. Set the container termination grace period longer than the delay plus time for active requests and resource cleanup. This local profile is not a production deployment.

For host-supplied publication authorization, pass `authorizePublication(request, version)` to `createDataPlane`. It is called before looking up a publication or evaluating a conditional response; only `true` permits the read. A denial returns 403 and an exception returns a sanitized 503. Health probes do not call it. The callback also receives an `AbortSignal` as its third argument, aborted on client disconnect or an optional authorization timeout. Set `publicationAuthorizationLimits: {timeoutMs, maxPending}` to bound concurrent authorization checks per Data Plane instance; the timeout is 100–30,000 ms and the maximum pending count is 1–100. Timeout or saturation returns 503, and a late authorization result cannot start a publication read. A callback that ignores cancellation holds its slot until it settles. These limits cover the authorization callback, not the subsequent repository read, synchronous blocking code or other processes. The host must authenticate and authorize the request, supply audit and repository timeouts, and secure HTTP transport; the callback is optional and does not by itself establish identity.

`createDataPlaneHttps(repository, {cert, key, clientCa?}, options?)` provides the same publication, authorization, health, tracing and draining behavior over TLS 1.2 or later. `cert` and `key` are host-provided PEM strings or buffers. Supplying `clientCa` requires every connection to present a valid client certificate; it does not automatically authorize publication access. Clients must validate the server certificate and hostname. Hosts own certificates, key rotation, client authorization, revocation and network controls.

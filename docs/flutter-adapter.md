# Flutter renderer: initial subset

`adapters/flutter` contains a Flutter package with an initial A2UI v0.9.1 renderer for Text, Column, Row, Card, TextField and Button. It accepts create, incremental component and data-model updates, and delete surface messages for the App Mixer catalog or the basic catalog identifier. Accepting a catalog identifier does not imply support for the full catalog.

A host supplies `AppMixerA2UI` with `subscribe`, a function that receives a message callback and may return an unsubscribe callback, `onError`, and an optional `onAction` handler. The host must authorize and route actions. Text fields and buttons use Material widgets, so the host needs a Material ancestor and bounded horizontal constraints. Built-in children of a Row share its available width, allowing nested text, fields and buttons to wrap; root rows, columns and cards fill the bounded host width. A new subscription must replay the current state. The widget unsubscribes on replacement or disposal and ignores late messages. Unsubscribe failures are sent to `onError` without blocking a replacement source. Updates are validated and applied atomically, with limits on surfaces, components, tree depth and expanded size; component, surface and action identifiers are limited to 256 Unicode code points. Incoming text is rendered as text and never executed.

Text supports literal values up to 10,000 Unicode code points and absolute path bindings. In this A2UI subset, both an empty path and `/` refer to the root; `/` cannot address an empty-named root property on its own, unlike RFC 6901. Text variants use browser-default-sized text (body 16, h1ï¿½h5 32/24/18.72/16/13.28, caption 13.33 logical pixels), with bold headings and header semantics. Heading-styled text inside buttons keeps its appearance and button label without a separate heading role or level. Standalone text directly in a row has a separate semantics node so it does not become part of a neighboring field label. On Flutter web, heading semantics also expose levels 1–5; Flutter ignores heading levels on native platforms. Font family and color come from the host Material body theme and user text scaling remains enabled; exact rendering and margins can differ from web typography. Model updates reject prototype-sensitive paths and keys, cycles, unsupported values, and structures over 10,000 nodes or 100 levels deep. TextField updates a non-root data path; Built-in Button and TextField components are rejected inside a Button, including when a later update resolves a child; trusted extensions must enforce their own composition rules. Button sends only explicitly selected context to the host and is disabled without an action handler. Input and button callbacks from replaced surfaces are rejected. Incrementally adding or reordering siblings preserves the editing state of an existing field while its component remains in the same parent. External value updates retain the current selection where possible and clamp it to the new text length. During input-method composition, external updates do not replace the composing text; the completed composition is written to the model. Other bound views may reflect external changes while composition is active. Rebinding the field to a different data path creates a fresh editing state, so composition cannot carry into the new path. These cases are covered by widget tests. The composition scenario also passed the [Flutter browser workflow](https://github.com/bassemZohdy/app-mixer/actions/runs/41451242957) and the [Android emulator](https://github.com/bassemZohdy/app-mixer/actions/runs/41451243188), using simulated text input; real input methods still need device verification. The full web catalog is not yet supported. The model uses JSON values; array updates reject noncanonical or out-of-range indices, including intermediate paths; deleting an array element preserves its index while distinguishing it from an explicit null. Typography and layout parity are not complete: default and explicit `stretch` alignment use Flutter intrinsic sizing when the cross-axis constraint is loose, limited to four nested intrinsic layouts along a path. Same-axis nested stretch layouts can avoid this limit when their parent supplies a tight cross-axis constraint. Intrinsic sizing may affect performance and exact dimensions differ from web flex layout. Broader Android integration, iOS integration and accessibility parity testing remain future work. P2-01 remains open until Flutter and React Native cover the supported web catalog and cross-platform parity is verified.

The Flutter workflow runs only for pull requests changing the Flutter package or its workflow. It downloads the pinned Flutter SDK and verifies its published SHA-256, then runs `flutter analyze`, widget tests, and an interaction test on headless Chrome. Shared layout, binding, action-context and invalid-message fixtures are also checked against the web and React Native implementations. On a machine with Flutter 3.35.5 installed, run `flutter pub get`, `flutter analyze`, and `flutter test` from `adapters/flutter`.

The separate Android and iOS integration workflows generate temporary Flutter host applications, attach this package, and run `integration_test/renderer_device_test.dart` on an Android emulator and iOS simulator. The iOS workflow retries a bounded number of times only if Flutter stalls while discovering the simulator VM service; test failures are not retried. The tests check a bound text field and action context on each mobile runtime, together with heading, field and button semantics, the field's accessible value, and the button's disabled state. They also verify a cross-language signed extension plan, reject tampered, expired and wrong-tenant plans, render the approved widget and reject an unapproved widget. Text entry uses Flutter's simulated text input to avoid a race with the device's real keyboard. The web test also checks heading, field and button semantics, including heading-styled button labels. Enabled and disabled semantics assertions use the named flag list shared by Flutter 3.35 and newer SDKs, preserving the distinction between disabled controls and controls without an enabled state. A shared web and device scenario exercises a nested bound field inside a card and row, externally supplied data updates, rejection of invalid component batches and nested interactive controls, continued field and button use after rejection, action context, isolation when a second surface is removed and recreated, and multiline editing, accessibility value and action context. A second shared scenario checks narrow-row field and button bounds, semantics, editing and action context on the VM, browser and device workflows. A third checks narrow nested row, column and card bounds and text wrapping on those targets. Shared layout scenarios check all six row justification modes and four row and column cross-axis alignment modes in the VM suite and are included in the browser and mobile suites. The row spacing and alignment scenarios passed in the [browser](https://github.com/bassemZohdy/app-mixer/actions/runs/41452201536), on [Android](https://github.com/bassemZohdy/app-mixer/actions/runs/41452201168) and on [iOS](https://github.com/bassemZohdy/app-mixer/actions/runs/41452201349). The column alignment scenario also passed in the [browser](https://github.com/bassemZohdy/app-mixer/actions/runs/41459699300) and on [Android](https://github.com/bassemZohdy/app-mixer/actions/runs/41459699448); the iOS run remains queued. An additional shared scenario checks field labels and adjacent direct or nested text in both row and column orders. The browser-only `test/browser_parity_test.dart` runs these shared scenarios directly and can be used with `flutter test --platform chrome test/browser_parity_test.dart`. The narrow-row, nested-layout and adjacent-field scenarios passed on the [Android emulator](https://github.com/bassemZohdy/app-mixer/actions/runs/41435287120) and [iOS simulator](https://github.com/bassemZohdy/app-mixer/actions/runs/41436271685). These checks do not replace testing with real keyboards, screen readers or broader cross-platform parity checks.

## Trusted extension components

A host can register static leaf widgets with `FlutterComponentRegistry.register(name, builder, validate)` and pass the registry as `extensions` to `AppMixerA2UI`. Names are lowercase identifiers. The synchronous validator receives an isolated copy of the full component and must return true; it must validate every property the builder relies on. Protocol fields `id` and `component` are removed before the remaining properties reach the builder; `key`, `ref`, and `children` are rejected. Properties are static values, with no automatic binding or action dispatch. Registered builders are trusted host code.

For direct registration, the host must select a validated published definition, verify compatibility and approval, and register only the components declared by that definition and their exact extension owners. Flutter does not run the TypeScript `ExtensionRegistry`. Registrations are captured when a subscription starts; replace the registry object to reconnect and replay when the selected publication or approvals change. The builder and validator must be supplied by the host, never by a definition.

For a control-plane-checked plan, create `createFlutterExtensionPlan` in the TypeScript host using trusted manifests and Flutter-targeted approvals, then authenticate delivery of its JSON to the Flutter host. `FlutterComponentRegistry.fromPlan(plan, installed, applicationId: id, revision: revision)` matches each declared component to exactly one `FlutterInstalledExtension` with the same ID, version and scope, using host-provided `FlutterExtensionComponent` builders and validators. Extra installed components are not registered. The host must select the published definition and expected revision, secure the plan transport, and rebuild the registry on publication or approval changes. The plan contains metadata only and is not a signed authorization token.


`signFlutterExtensionPlan` can create a short-lived Ed25519-signed plan after the same manifest and approval checks. The signer binds tenant, environment, application ID, definition revision, key ID, issue time and expiration (at most 24 hours). `FlutterComponentRegistry.fromSignedPlan` verifies the exact signed bytes against host-provisioned raw Ed25519 public keys, checks the expected tenant, environment, application and revision and trusted clock, then resolves only locally installed components. It snapshots the installed registrations and key material before asynchronous verification. The Flutter host must protect key provisioning and rotation, derive the expected target and clock from trusted sources, and treat unsigned `fromPlan` as a separate trusted-transport API.

A valid signature does not prove a current approval has not since been revoked, prevent replay within the validity window, provide a monotonic publication floor, or authorize extension operations. Replace registries when approval or publication changes, and use authenticated transport and an authoritative revocation or version policy where required. The signer holds a private key and must run only in a trusted host.

Flutter retains a surface's widget state when other surfaces are removed. Deleting and recreating a surface gives it fresh widget state, even when both messages arrive before the next frame; a shared VM, browser and device test covers focus and selection for these cases. This scenario passed on the [Android emulator](https://github.com/bassemZohdy/app-mixer/actions/runs/41441590366) and [iOS simulator](https://github.com/bassemZohdy/app-mixer/actions/runs/41441595726).

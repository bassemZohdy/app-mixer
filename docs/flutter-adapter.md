# Flutter renderer: initial subset

`adapters/flutter` contains a Flutter package with an initial A2UI v0.9.1 renderer for Text, Column, Row, Card, TextField and Button. It accepts create, incremental component and data-model updates, and delete surface messages for the App Mixer catalog or the basic catalog identifier. Accepting a catalog identifier does not imply support for the full catalog.

A host supplies `AppMixerA2UI` with `subscribe`, a function that receives a message callback and may return an unsubscribe callback, `onError`, and an optional `onAction` handler. The host must authorize and route actions. Text fields and buttons use Material widgets, so the host needs a Material ancestor and bounded horizontal constraints. Rows share available width among child subtrees containing text fields. A new subscription must replay the current state. The widget unsubscribes on replacement or disposal and ignores late messages. Unsubscribe failures are sent to `onError` without blocking a replacement source. Updates are validated and applied atomically, with limits on surfaces, components, tree depth and expanded size. Incoming text is rendered as text and never executed.

Text supports literal values and absolute JSON pointer bindings. Text variants use the host Material text theme, and headings carry header semantics; their appearance can differ from web typography. Model updates reject prototype-sensitive paths and keys, cycles, unsupported values, and structures over 10,000 nodes or 100 levels deep. TextField updates a non-root data path; Button sends only explicitly selected context to the host and is disabled without an action handler. Input and button callbacks from replaced surfaces are rejected. The full web catalog is not yet supported. The model uses JSON values; deleting an array element preserves its index while distinguishing it from an explicit null. Typography and layout parity are not complete: explicit `stretch` alignment uses Flutter intrinsic sizing (limited to four nested stretch layouts), while the default cross-axis alignment remains centered. Intrinsic sizing may affect performance and exact dimensions differ from web flex layout. Broader Android integration, iOS integration and accessibility parity testing remain future work. P2-01 remains open until Flutter and React Native cover the supported web catalog and cross-platform parity is verified.

The Flutter workflow runs only for pull requests changing the Flutter package or its workflow. It downloads the pinned Flutter SDK and verifies its published SHA-256, then runs `flutter analyze`, widget tests, and an interaction test on headless Chrome. Shared layout, binding, action-context and invalid-message fixtures are also checked against the web and React Native implementations. On a machine with Flutter 3.35.5 installed, run `flutter pub get`, `flutter analyze`, and `flutter test` from `adapters/flutter`.

The separate Android and iOS integration workflows generate temporary Flutter host applications, attach this package, and run `integration_test/renderer_device_test.dart` on an Android emulator and iOS simulator. The test checks a bound text field and action context on each mobile runtime, together with heading, field and button semantics, the field's accessible value, and the button's disabled state. Text entry uses Flutter's simulated text input to avoid a race with the device's real keyboard. The web test also checks heading, field and button semantics. These checks do not replace testing with real keyboards, screen readers or broader cross-platform parity checks.

## Trusted extension components

A host can register static leaf widgets with `FlutterComponentRegistry.register(name, builder, validate)` and pass the registry as `extensions` to `AppMixerA2UI`. Names are lowercase identifiers. The synchronous validator receives an isolated copy of the full component and must return true; it must validate every property the builder relies on. Protocol fields `id` and `component` are removed before the remaining properties reach the builder; `key`, `ref`, and `children` are rejected. Properties are static values, with no automatic binding or action dispatch. Registered builders are trusted host code.

For direct registration, the host must select a validated published definition, verify compatibility and approval, and register only the components declared by that definition and their exact extension owners. Flutter does not run the TypeScript `ExtensionRegistry`. Registrations are captured when a subscription starts; replace the registry object to reconnect and replay when the selected publication or approvals change. The builder and validator must be supplied by the host, never by a definition.

For a control-plane-checked plan, create `createFlutterExtensionPlan` in the TypeScript host using trusted manifests and Flutter-targeted approvals, then authenticate delivery of its JSON to the Flutter host. `FlutterComponentRegistry.fromPlan(plan, installed, applicationId: id, revision: revision)` matches each declared component to exactly one `FlutterInstalledExtension` with the same ID, version and scope, using host-provided `FlutterExtensionComponent` builders and validators. Extra installed components are not registered. The host must select the published definition and expected revision, secure the plan transport, and rebuild the registry on publication or approval changes. The plan contains metadata only and is not a signed authorization token.

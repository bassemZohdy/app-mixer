# Publication rollback

Both `ApplicationStore` and `SqliteApplicationStore` implement `rollback(sourceVersion, expectedVersion)`. It copies an earlier immutable definition into a new publication whose version is greater than the current latest version. It does not alter historical publications or the current draft. A later normal publish can therefore publish that draft again. The operation validates the definition and reruns the current publication guard before committing. Hosts must make that guard check the compatibility of the target runtime and installed extensions; built-in validation supports schema version 1.

`expectedVersion` is an optimistic concurrency precondition, and `sourceVersion` must be a positive earlier version. SQLite checks and inserts within one immediate transaction, so separate connections cannot both successfully roll back from the same expected latest version. The data plane and its version-aware cache observe the new version on their next latest read, and conditional HTTP requests receive a new ETag.

The local-development control plane exposes `POST /rollback` with JSON `{ "sourceVersion": 1, "expectedVersion": 2 }` and requires the same control token as `/publish`. It returns 201 with the new publication, 409 for a stale latest version or a non-earlier target, 404 for a missing source, and 400 for malformed input. Repositories without rollback return 501. The data plane has no rollback endpoint. A lost response should be resolved by reading the latest version before retrying; retrying the same precondition cannot create a second rollback.

This restores application definitions only. It does not migrate or undo business data, submit staged operations, promote between environments, maintain a durable rollback provenance record, or implement production identity and audit. The control plane is a loopback development prototype; hosts must authorize and audit rollback separately. Schema migration and environment promotion remain open.

# Data Plane request observations

Pass `observe: event => ...` as an option to `createDataPlane` to receive a best-effort observation after each response completes or the client disconnects. Each event contains a fixed route class (`application`, `version`, `live`, `ready`, or `other`), outcome (`completed` or `aborted`), response status class (`2xx`, `3xx`, `4xx`, `5xx`, `other`, or `none` for an aborted response), and monotonic elapsed milliseconds from request handling to response finish or disconnect. Route classes depend on method, exact supported path, and whether health probes are enabled. Raw URLs, publication versions, headers, tokens and actor identifiers are not emitted. A closed connection is recorded at most once.

The callback runs in the server process and must be fast and nonblocking. Synchronous errors and rejected promises are ignored so telemetry failure does not break serving; the host must bound and monitor its exporter queue. An observation is not a durable audit record. Request completion measures server response completion, not confirmation that a client received the response, and excludes work done before the handler begins. An aborted request is separate from an HTTP status and should not automatically be counted as a server error.

`DataPlaneRequestMetrics` provides an optional process-local aggregator: construct it, pass `metrics.observe` to the Data Plane, and call `metrics.render()` for Prometheus text exposition. It reports request counters and cumulative duration histograms in seconds using fixed buckets from 5 ms through 10 seconds and `+Inf`. It accepts only the fixed route, outcome and status classes above, with at most 30 label combinations; invalid observations are rejected. Series appear only after an observation, counters reset on process restart, and overflow is rejected rather than producing invalid metrics. The host must monitor telemetry loss, supply service and deployment attributes from trusted configuration, and aggregate histogram buckets rather than averaging percentiles. Configure SLOs, retention and alerts at the host and collector with appropriate privacy, cardinality and operational ownership.

## Optional distributed tracing

Pass `tracing: {tracer}` to `createDataPlane` with a host-configured OpenTelemetry tracer to create a server span for each request. The host must configure an SDK, context manager, sampling, exporter and collector; the API's default no-op tracer does not export spans. A configured context manager makes the server span active for repository and readiness work so host instrumentation can create children. Spans end on response completion or client disconnect. The adapter records a bounded method (`GET` or `_OTHER`), a fixed route template for supported routes, the HTTP response status, and a sanitized error status for 5xx responses or disconnects. It does not record raw URLs, query strings, headers, publication IDs, tokens or exception details. Exporters and other host instrumentation may record additional information and must be configured separately for privacy.

Incoming trace context is ignored by default. Set `trustRemoteParent: true` only when the upstream is trusted and install a W3C trace-context propagator in the host to link a valid `traceparent` to the server span. The adapter ignores duplicate or oversized `traceparent` headers and starts a root span in those cases; it does not extract `tracestate` or baggage. Incoming trace IDs and sampling flags can be controlled by the sender, so boundary policy, sampling and rate limits remain the host's responsibility. Instrumentation errors are isolated from request handling. Do not also enable automatic HTTP server instrumentation for this listener unless duplicate server spans are intended. Tracing is optional and is not a durable audit trail; collector availability, export queues, retention, redaction and cross-service instrumentation remain deployment responsibilities.

For the remote Control Plane path, the host may supply `tracing: {tracer, propagate: true}` to `createRemoteControlConnector` and pass `{tracer, trustRemoteParent: true}` as the eighth argument to the source's `createControlPlane`. With a configured context manager and W3C propagator, discovery and promotion export create client spans linked to Control Plane server spans. Propagation is disabled by default, and only `traceparent` is sent to the configured source; baggage and `tracestate` are not forwarded. The connector's spans cover response-body reading, use fixed endpoint names, and record status or a sanitized failure, not credentials, payloads, source origins or actor identity. Control Plane spans use fixed templates for these three endpoints and a generic name for others. This does not instrument the generated workspace or other services; configure those separately. Only propagate to a trusted endpoint and accept trace parents from trusted callers, and avoid duplicate automatic HTTP instrumentation.

`createMetricsServer({metrics, authorize, timeoutMs, maxPending})` optionally exposes `GET /metrics` on a separate HTTP server. The host-supplied authorization callback receives the request and an abort signal; only an explicit `true` permits a scrape. Errors deny access without returning their details. Authentication and authorization policy, audit, network restrictions and TLS termination are the host's responsibility; bind to loopback or a protected network and never expose this HTTP listener directly to the public internet. The timeout is 100–30,000 ms and `maxPending` is 1–1,000. Timed-out or disconnected authorization is aborted and continues to consume a pending slot until it settles, preventing unbounded stuck callbacks; callbacks must honor cancellation. A timeout or exhausted limit returns 503. Scrape responses are `no-store` Prometheus text and are not themselves recorded by the Data Plane observer.

# Durable agent action journal

`SqliteAgentActionJournal` records one action per tenant, agent, run and action ID in the same SQLite database as the run registry. Construct it with the current run lease. `invoke(actionId, operationId, input, maxAttempts, dispatch)` records the canonical input and a generated idempotency key before dispatching. Reusing the action ID with a different operation, input or attempt limit fails. A confirmed result is stored and returned on later matching calls without dispatching again. Inputs and results must be bounded JSON. Writes, including result recording, require the current live run lease.

A dispatch error or invalid result becomes `uncertain` when the lease is still valid. A crash or lost lease can leave `dispatching`; after stopping the old worker and moving the run to `uncertain`, the host must call `markUncertain`. The host then verifies the external outcome and calls `reconcile`: `applied` records a verified result, `not_applied` permits a later attempt with the same idempotency key, and `failed` records a terminal failure. Attempt limits are enforced. Reconcile the action before authorizing the run to retry. The journal never automatically replays ambiguous effects.

If a journaled action is `dispatching` or `uncertain`, settling the run records `uncertain` even when the worker reports success, failure or a cooperative stop. An uncertain run cannot transition to any other state until every such action is reconciled. The check and transition share a SQLite transaction and are scoped to the tenant, agent and run. A `ready` action does not block recovery: it has not been dispatched, or a host has verified non-application. The host must establish that the old worker has stopped before resolving a `dispatching` action; the local lease cannot stop an external call. Older terminal runs with unresolved journal records are not automatically repaired.

For an uncertain action, a trusted host can call `await journal.reconcileWith(actionId, verify)`. The verifier receives the run scope, run ID, action metadata including the stable idempotency key, a copy of the original input, and the action authority when present. It may return `{outcome: 'applied', result}`, `{outcome: 'not_applied'}`, `{outcome: 'failed'}`, or `{outcome: 'unknown'}`. Unknown and verifier errors leave the action uncertain; a confirmed not-applied outcome is rejected when attempts are exhausted. The run revision and action state are checked again after the external lookup, so a concurrent recovery or reconciliation prevents stale evidence from being recorded. The caller must authenticate and authorize access to the action and verifier, stop the old worker, and ensure the verifier's source can conclusively establish the outcome for that idempotency key. Do not treat a missing or delayed upstream response as proof of non-application. The method never dispatches or resumes the run; the host separately reconciles the run after reviewing all effects.

For host-driven recovery, `journal.list({status, after, limit})` lists scoped action metadata in action-ID order, with up to 100 entries and an optional `next` cursor. Input and result bodies are not included; idempotency keys are included, so the host must authorize and protect access. `await journal.reconcilePending(verify, {after, limit})` makes one sequential pass over a page of uncertain actions for a run already marked uncertain. It returns an outcome or error per action and an optional next cursor. Each action is independently fenced by `reconcileWith`; a verifier failure or concurrent change leaves that action unresolved and does not stop the page. Restart from the beginning on later passes to revisit unknown or failed lookups, and do not treat a paginated scan as a consistent snapshot. A host may schedule these passes, but must stop the old worker and explicitly mark any stranded `dispatching` actions uncertain first. The pass does not dispatch actions or resume the run.


`AgentActionRecoveryWorker` can run bounded, repeated verification passes for one host-selected journal. Configure `authorize(action)`, `evidence(action)`, `verify(request)`, `maxPerPass`, `pollMs` and `onError`, then explicitly call `start()` or `runOnce()`. The host must stop the old worker and mark stranded dispatches uncertain first. It authorizes each action before verification and again after the verifier returns, requires a principal and evidence reference for every decision, and uses the journal's atomic evidence-bearing reconciliation and stale-result checks. Evidence references may identify a pre-established case containing independently verified provider evidence. Unknown outcomes produce no decision record. Denied, unknown and failed actions are reconsidered after the scan wraps; pagination is not a consistent snapshot. The worker passes an `AbortSignal` as the final argument to `authorize`, `evidence` and `verify`. Stopping aborts the signal, waits for the active pass and prevents a late result from being committed; a later pass can retry the unresolved action. Cooperative callbacks can stop promptly, but the worker cannot force an external lookup to stop, and a callback that ignores the signal can delay shutdown indefinitely.

The worker does not mark dispatches uncertain, dispatch actions, or resume a run. Its callback authorization is host policy, not authentication; the host must authenticate operators, protect verifier credentials and evidence, use a provider-specific conclusive verifier, and arrange production scheduling and independent audit. Authorization can change after the final callback unless the host's policy store provides transactional enforcement. Only evidence-bearing decisions made through this worker are recorded; other journal APIs can bypass the record.

A host can use `createActionHttpsVerifier` as the recovery worker verifier for a trusted HTTPS lookup endpoint. Configure a fixed `scope`, `runId`, `operationId` and HTTPS `url`, either a fixed bearer token or `getBearerToken(signal)`, a `timeoutMs`, `maxPending`, and a trusted `interpret(body, context, signal)` callback. The POST contains only the scoped run and action identifiers, operation and idempotency key; it does not send the action input or authority. The endpoint must authenticate the request and return HTTP 200 with bounded JSON. The interpreter must validate provider-specific evidence and return a valid `ActionVerification`; a missing record, 404, error, malformed response or timeout is never automatically treated as `not_applied`. The lookup does not dispatch the action.

The endpoint and interpreter are trusted host configuration, not model input. The host must verify that the provider can conclusively establish outcomes for the key and recovery horizon, configure TLS trust, DNS and egress controls, protect credentials, and authorize access to the action and evidence. Redirects are rejected. Responses default to 64 KiB and can be limited between 1 KiB and 256 KiB; parsed JSON is also limited to 10,000 values and 40 levels and rejects prototype-sensitive keys. Deadlines cannot interrupt synchronous callbacks. A timed-out or cancelled callback that ignores its signal retains a pending slot until it settles; `maxPending` bounds such work but does not forcibly terminate it. Tests include a certificate-validated local endpoint and simulated outcomes, including process termination before and after the provider commits. An absent record remains uncertain; a verified committed result resumes without another dispatch. These tests do not establish a real provider contract.

For local actor-attributed decisions, pass `{principalId, reference}` as the third argument to `reconcileWith`, or call `reconcileWithEvidence(actionId, outcome, result, evidence)` for a manual decision (use `undefined` as the result for non-applied or failed outcomes). The host must authenticate and authorize the principal and verify that the reference identifies independently protected supporting evidence. Both identifiers are bounded non-secret strings. The action transition and evidence record commit in the same SQLite transaction; a failed evidence write leaves the action uncertain. Unknown outcomes, verifier errors and stale results produce no record. `listReconciliations({after, limit})` returns up to 100 records for the journal's tenant, agent and run, ordered by record ID; authorize the entire run and protect evidence references before exposing them. Records contain action ID, principal, reference, decision, manual/verifier method and host-clock timestamp, but not input, result, authority or idempotency key. IDs are global database sequence values, so gaps can expose approximate activity to an authorized reader.

SQLite triggers prevent ordinary updates, replacement and deletion of these records; a privileged database administrator can alter the schema or database, and backups may be restored. This is not an independent tamper-proof audit service, legal-hold system or automatic retention policy. Existing `reconcile`, `reconcileWith` without evidence and `reconcilePending` remain unaudited for compatibility. Hosts requiring complete audit must expose only evidence-bearing paths, secure the database and preserve independent audit evidence. Coordinate migrations and stop older writers before enforcing that policy.

A configured agent may opt in with `actionJournal: {journal, maxAttempts, prepareInput}`. The LangGraph tool-call ID becomes the action ID; the model provider must give every distinct action a unique ID within a run and preserve it across checkpoint replay. `prepareInput(operationId, input, idempotencyKey)` maps the key into the registered capability's input; the capability binding must actually pass it to an external service that honors it. The normal capability registry authorizes, validates and audits each actual dispatch. On a cached-result replay no dispatch occurs, so the host's `authorizeCapability` callback must also check current permission to read that result; the registry does not reauthorize or audit that cached read. Run and capability authorization are checked before journal access.

The journal and checkpoints are not a distributed transaction with external systems. Idempotency requires downstream support and retention sufficient for recovery; an external service that ignores the key can still duplicate effects. Hosts must authenticate and authorize journal administration, protect lease tokens, verify that the old worker has stopped before reconciliation, and secure the database and backups. Stored input and results may contain sensitive information and are not encrypted. This local primitive does not provide a scheduler or provider-specific outcome verification, independent tamper-proof audit, cross-system transactions or automatic retention.

Protected actions can require a matching approval as described in [agent approvals](agent-approvals.md). The host must configure the approval policy; unprotected journal calls do not automatically require approval.


The automated process-crash acceptance test terminates a separate Node worker before an external dispatch, after a simulated HTTP service commits but before it returns, and after the journal records the result. It reopens SQLite, confirms that lease expiry alone does not replay an action, explicitly reconciles the external outcome, and checks the stable key and tenant isolation. The service is a local idempotent test double; these tests do not establish the behavior of a real provider, distributed storage, pod termination, or production key retention.

## Downstream idempotency check

`checkIdempotencyContract({dispatch, countEffects, input, conflictingInput, concurrency?})` exercises how a downstream operation handles idempotency keys before a host relies on it for journaled actions. `dispatch(input, key)` must call the operation exactly as the capability binding would, against a sandbox or staging target; `countEffects(key)` must read the number of applied effects for that key independently, for example from the provider's records. The check sends a sequential replay, `concurrency` simultaneous attempts (5 by default) with one key, the reused key with `conflictingInput`, and a fresh key. It returns `{passed, findings, keys}`; findings name the check and problem, such as more than one effect for one key, replays returning different results, or a reused key accepted for different content, including silently returning the original result.

A passing report is evidence about that target, input and timing only. It does not establish key retention across the recovery horizon, behavior after provider failover, or production configuration. Run it against isolated test accounts, since it creates real effects, and repeat it when the provider or binding changes.

# Durable agent action journal

`SqliteAgentActionJournal` records one action per tenant, agent, run and action ID in the same SQLite database as the run registry. Construct it with the current run lease. `invoke(actionId, operationId, input, maxAttempts, dispatch)` records the canonical input and a generated idempotency key before dispatching. Reusing the action ID with a different operation, input or attempt limit fails. A confirmed result is stored and returned on later matching calls without dispatching again. Inputs and results must be bounded JSON. Writes, including result recording, require the current live run lease.

A dispatch error or invalid result becomes `uncertain` when the lease is still valid. A crash or lost lease can leave `dispatching`; after stopping the old worker and moving the run to `uncertain`, the host must call `markUncertain`. The host then verifies the external outcome and calls `reconcile`: `applied` records a verified result, `not_applied` permits a later attempt with the same idempotency key, and `failed` records a terminal failure. Attempt limits are enforced. Reconcile the action before authorizing the run to retry. The journal never automatically replays ambiguous effects.

A configured agent may opt in with `actionJournal: {journal, maxAttempts, prepareInput}`. The LangGraph tool-call ID becomes the action ID; the model provider must give every distinct action a unique ID within a run and preserve it across checkpoint replay. `prepareInput(operationId, input, idempotencyKey)` maps the key into the registered capability's input; the capability binding must actually pass it to an external service that honors it. The normal capability registry authorizes, validates and audits each actual dispatch. On a cached-result replay no dispatch occurs, so the host's `authorizeCapability` callback must also check current permission to read that result; the registry does not reauthorize or audit that cached read. Run and capability authorization are checked before journal access.

The journal and checkpoints are not a distributed transaction with external systems. Idempotency requires downstream support and retention sufficient for recovery; an external service that ignores the key can still duplicate effects. Hosts must authenticate and authorize journal administration, protect lease tokens, verify that the old worker has stopped before reconciliation, and secure the database and backups. Stored input and results may contain sensitive information and are not encrypted. This local primitive does not provide automatic reconciliation, delegated identity, actor-level audit, cross-system transactions or automatic retention.

# Local business-data schema migration

`SqliteDataProvider` supports an explicit migration of one tenant, application and collection at a time. Existing collections start at schema version 0. A trusted host obtains `previewMigration(scope, collection)`, then passes its digest to `migrateCollection(scope, collection, {fromVersion, toVersion, digest, transform, validate})`. Versions advance one at a time. Both callbacks must be synchronous; the transform receives a copy of each live JSON object and its record ID, and the validator must return exactly `true` for each transformed value.

A preview binds the collection scope, schema version, ordered records and revisions to a SHA-256 digest. Migration opens an immediate SQLite transaction, recomputes the preview, rejects changes, transforms and validates every live record, increments their revisions, updates the collection version, and records immutable migration history. An error rolls back all of those changes. Existing deleted-record tombstones stay intact. By default, previews and migrations are limited to 1,000 live records and 16 MiB of stored JSON, and each transformed value remains subject to the normal 1 MiB limit. Trusted hosts can pass `{migrationLimits: {maxRecords, maxBytes}}` as the second `SqliteDataProvider` constructor argument, with limits from 1 to 10,000 records and 1 to 134,217,728 bytes; omitted fields use the defaults. Both the input snapshot and the transformed output must fit the configured byte limit. These limits are per provider instance, not stored in the database. Separate connections cannot write while the migration transaction is active.

After migration, `put` and `delete` require the current `expectedSchemaVersion` argument; omission means version 0. Data capabilities accept an optional `expectedSchemaVersion` field and pass it through. Hosts must update their clients and their authorization and validation policies for the new shape. The generated record editor can send a trusted host-configured `expectedSchemaVersion` as described in [business data](business-data.md). The provider checks the version, not the schema of subsequent writes; a host must validate every write. Optional guarded reads take `expectedSchemaVersion` and check it in the same SQLite snapshot as the record or list page. Unguarded reads remain available for legacy callers and do not check the version. A revision obtained before migration cannot update a transformed record.

The API is a local primitive and does not authenticate or authorize callers. Only trusted host code may supply migration callbacks. Before migration, stop or upgrade every writer: older application binaries or direct SQLite access do not enforce the new version check. Rehearse with representative data, verify a backup, and plan rollback or forward repair. Restoring an old backup after post-migration writes can lose those writes; reconciliation or replay is required. Migration history is not an actor-level audit and the digest is not a signature. Large collections, online multi-stage migrations, distributed stores, business-schema management, and general application-definition schema evolution remain open. The supported definition migration is described in [definition migration](definition-migration.md). Publication and rollback of application definitions do not invoke business-data migration.


## Rollback through a new generation

`rollbackCollection(scope, collection, {fromVersion, targetVersion, digest, transform, validate})` restores an earlier schema shape by applying a host-supplied inverse transform to every current live record. Obtain a fresh `previewMigration` first; the rollback checks that digest and current version inside the same write transaction. `targetVersion` must refer to an earlier recorded generation, or 0 for the original shape. The host's synchronous validator must confirm the intended shape for each transformed record.

A rollback creates the next schema version rather than reusing the old version number: for example, returning from generation 1 to the shape of generation 0 creates generation 2. This keeps stale version-0 and version-1 writers and schema-bound cursors fenced. Revisions increment, tombstones remain, and the transformed records, new generation and immutable rollback provenance commit atomically. `rollbackHistory` reads bounded pages of source and target generations, the input digest and record count. It does not identify an actor and is not independent audit storage.

This is a host-defined compensating migration, not restoration of an earlier data snapshot. Post-migration writes are included, and an incorrect or lossy inverse transform can destroy data. Rehearse and validate with representative data and a protected backup, update clients to the new generation, stop legacy writers, and reconcile changes as needed. Collection size and transactional limits are the same as forward migration; online, distributed and larger migrations remain open.


## Operator evidence and fixed-plan capabilities

Trusted hosts may supply `evidence: {principalId, reference, observedAt}` to a forward migration or rollback. The provider snapshots it and records an actor-attributed event in the same transaction as the data, schema generation and migration history. `migrationAudit(scope, collection, {after?, limit?})` returns bounded pages. Audit events omit record values but their actor IDs and references may be sensitive. Existing and unaudited migrations are not backfilled, and direct callers must authenticate and authorize both mutations and audit reads. SQLite triggers prevent ordinary update, delete and replacement of audit events; database administrators can alter the schema or files, so this is not independent tamper-proof audit storage.

Hosts can register `registerDataMigrationPreview`, `registerDataMigrationApply` and `registerDataMigrationAudit` on `CapabilityRegistry`. Each registration fixes the tenant, application, collection and trusted migration functions; callers cannot supply code or select another target. The preview and audit use GET candidates and accept `{query: {}}` and `{query: {after?, limit?}}` respectively. The POST apply accepts `{query: {digest, reference, outputDigest?}}`, and its separate `authorizeApply` policy must approve the input. The capability checks that policy again after the final scope authorization, so callbacks must tolerate repeated calls. External policy changes are not atomic with the subsequent SQLite transaction. The authenticated capability actor and host clock become the transactional evidence. Forward and rollback plans are selected by the host when registering; each must match the current schema generation and fresh preview digest.

The host must authenticate operators, enforce separate preview, apply and audit policies, protect evidence and trusted plan code, use a reliable clock, and manage backups and maintenance windows. Capability audit can fail after a migration commits, leaving an uncertain response; inspect schema, records and migration audit before retrying. Authorization checks and database mutation do not form a transaction with an external policy service, and older writers can still bypass schema fencing. This is a bounded local SQLite operation, not online or distributed migration.

Trusted host code can call `rehearseMigration(scope, collection, {fromVersion, transform, validate})` to run the same bounded transformation, validation, and transformed-size checks against a consistent snapshot without committing the transaction. It returns the input snapshot preview and digest plus an output digest, with no record values. Supply both digests to forward migration or rollback to reject changed input or a different transformed output before any records are written. The output digest is also accepted by the apply capability and passed to its authorization policy; omitting it retains the earlier behavior by default. Set `requireOutputDigest: true` on a fixed-plan apply capability to reject requests that omit it. This requires a matching output digest, but the host must still approve the plan and independently establish that the digest came from an appropriate rehearsal. Digest conflicts return HTTP 409 through the capability server. The callbacks run again during apply and must be deterministic for rehearsal to predict the result. They are trusted synchronous host code and can still cause external side effects; the database rollback cannot undo those. `rehearseMigration` does not check rollback-target history or authorize a later migration. For rollback, `rehearseRollback(scope, collection, {fromVersion, targetVersion, transform, validate})` checks the target history in the same read snapshot before exercising the plan. The rehearsal capability does the same when its host-fixed plan has `kind: "rollback"` and a target version; plans without a kind retain the forward-style behavior. A later apply rechecks target history inside its write transaction.

`registerDataMigrationRehearsal` optionally exposes a host-fixed rehearsal through a POST capability accepting exactly `{query: {}}`. Configure the fixed scope, collection and trusted plan, plus separate `authorize` and `authorizeRehearsal` policies; the capability rechecks both after the rehearsal before returning the input snapshot preview. It does not expose records, does not authorize applying the plan, and does not prove the identity of the plan implementation: different code can produce the same output. Policy callbacks may run repeatedly, and external policy changes are not atomic with the response. The existing rehearsal limitations, including external callback side effects and the need for deterministic transforms, still apply.

When an audited migration or rollback supplies `outputDigest`, the same transaction stores it in the immutable migration audit event. Older events and calls without the check omit that field; it is not backfilled. Opening an existing store adds a nullable audit column under a SQLite write lock. Stop older binaries before upgrading: their audited migration inserts use the old table shape and are incompatible with the upgraded store. As with the rest of the local audit, database administrators can alter the file or schema.

Process-kill tests cover forward migration and rollback immediately before the audit insert and after commit. Reopening verifies atomic record, schema and output-digest evidence recovery, stale retry rejection and isolation of another tenant. This tests local SQLite process failure, not storage loss or distributed recovery.

Larger limits increase memory use, callback execution time and the duration of the SQLite write lock; choose them based on measured capacity and a maintenance window. They do not make migrations online or distributed. A test exercises 1,001 records; the maximum is a guardrail, not a throughput guarantee.

Generated apps can opt in to `mountDataMigration(root, {rehearsalOperation, applyOperation, auditOperation, targetLabel})` from `offline-runtime.mjs`. The trusted host supplies an accurate target label and separately registered, fixed-scope capabilities for the same plan and collection. The view displays both rehearsal digests, requires an evidence reference, and sends those exact digests for apply; it also pages through authorized audit events. After a failed or ambiguous apply it clears the rehearsal and disables another rehearsal until the operator reaches the last audit page and acknowledges checking the audit and schema. The acknowledgement is local to the mounted view, resets on reload, and does not prove that the operator checked the schema or that an in-flight operation has settled; the host remains responsible for reconciliation. The label is descriptive and does not enforce scope. The host must secure the proxy, authorize each capability, ensure the rehearsal and apply registrations use the same intended plan, and handle review and backup procedures. A generated-app integration test covers the authenticated proxy, successful apply and evidence display.

The apply capability can bound its asynchronous authorization work with both `policyTimeoutMs` (100–30000 ms) and `maxPendingPolicies` (1–100). Optional `authorizeWithSignal` and `authorizeApplyWithSignal` callbacks receive an abort signal and take precedence over their legacy counterparts, which remain required. A timed-out policy retains its slot until it settles; late approval cannot start a migration. Saturation and timeouts return HTTP 503. The bounds apply to each initial scope check and the full subsequent scope/action check sequence, not the registry audit, synchronous transforms, SQLite transaction or callbacks that ignore cancellation.

`registerDataMigrationStatus` exposes the current schema generation for one fixed collection through a GET capability accepting `{query: {}}`. Configure separate scope and `authorizeStatus` policies. Both are checked again around two generation reads, and a change during the check fails the request. Optional paired `policyTimeoutMs` and `maxPendingPolicies` bound each asynchronous authorization sequence; a timeout signals the status policy, retains its slot until the callback settles and returns HTTP 503. The scope policy has its original signature and must cooperate separately if it can block. This is a point-in-time observation, not proof that a previous migration has stopped or settled.

The generated migration view accepts an optional `statusOperation` for that fixed collection. It displays the independently authorized generation. After an uncertain apply, when the status operation is configured, the operator must load it and reach the end of the audit before acknowledging review. Neither reading a generation nor acknowledging review proves that a previous request has settled.

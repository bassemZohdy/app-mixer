# Local business-data schema migration

`SqliteDataProvider` supports an explicit migration of one tenant, application and collection at a time. Existing collections start at schema version 0. A trusted host obtains `previewMigration(scope, collection)`, then passes its digest to `migrateCollection(scope, collection, {fromVersion, toVersion, digest, transform, validate})`. Versions advance one at a time. Both callbacks must be synchronous; the transform receives a copy of each live JSON object and its record ID, and the validator must return exactly `true` for each transformed value.

A preview binds the collection scope, schema version, ordered records and revisions to a SHA-256 digest. Migration opens an immediate SQLite transaction, recomputes the preview, rejects changes, transforms and validates every live record, increments their revisions, updates the collection version, and records immutable migration history. An error rolls back all of those changes. Existing deleted-record tombstones stay intact. Previews and migrations are limited to 1,000 live records and 16 MiB of stored JSON, and each transformed value remains subject to the normal 1 MiB limit. Separate connections cannot write while the migration transaction is active.

After migration, `put` and `delete` require the current `expectedSchemaVersion` argument; omission means version 0. Data capabilities accept an optional `expectedSchemaVersion` field and pass it through. Hosts must update their clients and their authorization and validation policies for the new shape. The generated record editor can send a trusted host-configured `expectedSchemaVersion` as described in [business data](business-data.md). The provider checks the version, not the schema of subsequent writes; a host must validate every write. Optional guarded reads take `expectedSchemaVersion` and check it in the same SQLite snapshot as the record or list page. Unguarded reads remain available for legacy callers and do not check the version. A revision obtained before migration cannot update a transformed record.

The API is a local primitive and does not authenticate or authorize callers. Only trusted host code may supply migration callbacks. Before migration, stop or upgrade every writer: older application binaries or direct SQLite access do not enforce the new version check. Rehearse with representative data, verify a backup, and plan rollback or forward repair. Restoring an old backup after post-migration writes can lose those writes; reconciliation or replay is required. Migration history is not an actor-level audit and the digest is not a signature. Large collections, online multi-stage migrations, distributed stores, business-schema management, and general application-definition schema evolution remain open. The supported definition migration is described in [definition migration](definition-migration.md). Publication and rollback of application definitions do not invoke business-data migration.


## Rollback through a new generation

`rollbackCollection(scope, collection, {fromVersion, targetVersion, digest, transform, validate})` restores an earlier schema shape by applying a host-supplied inverse transform to every current live record. Obtain a fresh `previewMigration` first; the rollback checks that digest and current version inside the same write transaction. `targetVersion` must refer to an earlier recorded generation, or 0 for the original shape. The host's synchronous validator must confirm the intended shape for each transformed record.

A rollback creates the next schema version rather than reusing the old version number: for example, returning from generation 1 to the shape of generation 0 creates generation 2. This keeps stale version-0 and version-1 writers and schema-bound cursors fenced. Revisions increment, tombstones remain, and the transformed records, new generation and immutable rollback provenance commit atomically. `rollbackHistory` reads bounded pages of source and target generations, the input digest and record count. It does not identify an actor and is not independent audit storage.

This is a host-defined compensating migration, not restoration of an earlier data snapshot. Post-migration writes are included, and an incorrect or lossy inverse transform can destroy data. Rehearse and validate with representative data and a protected backup, update clients to the new generation, stop legacy writers, and reconcile changes as needed. Collection size and transactional limits are the same as forward migration; online, distributed and larger migrations remain open.


## Operator evidence and fixed-plan capabilities

Trusted hosts may supply `evidence: {principalId, reference, observedAt}` to a forward migration or rollback. The provider snapshots it and records an actor-attributed event in the same transaction as the data, schema generation and migration history. `migrationAudit(scope, collection, {after?, limit?})` returns bounded pages. Audit events omit record values but their actor IDs and references may be sensitive. Existing and unaudited migrations are not backfilled, and direct callers must authenticate and authorize both mutations and audit reads. SQLite triggers prevent ordinary update, delete and replacement of audit events; database administrators can alter the schema or files, so this is not independent tamper-proof audit storage.

Hosts can register `registerDataMigrationPreview`, `registerDataMigrationApply` and `registerDataMigrationAudit` on `CapabilityRegistry`. Each registration fixes the tenant, application, collection and trusted migration functions; callers cannot supply code or select another target. The preview and audit use GET candidates and accept `{query: {}}` and `{query: {after?, limit?}}` respectively. The POST apply accepts exactly `{query: {digest, reference}}`, and its separate `authorizeApply` policy must approve the input. The authenticated capability actor and host clock become the transactional evidence. Forward and rollback plans are selected by the host when registering; each must match the current schema generation and fresh preview digest.

The host must authenticate operators, enforce separate preview, apply and audit policies, protect evidence and trusted plan code, use a reliable clock, and manage backups and maintenance windows. Capability audit can fail after a migration commits, leaving an uncertain response; inspect schema, records and migration audit before retrying. Authorization checks and database mutation do not form a transaction with an external policy service, and older writers can still bypass schema fencing. This is a bounded local SQLite operation, not online or distributed migration.

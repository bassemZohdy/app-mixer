# Extension compatibility foundation

`checkExtensionCompatibility` from `@app-mixer/core` checks metadata for trusted, statically installed extensions. A version 1 manifest declares an ID, exact extension version, scope (`platform`, `development`, or `application`), exact supported runtime versions, renderer IDs, component/tool/provider names, and requested permission names. IDs are lowercase ASCII identifiers. Versions use numeric `major.minor.patch` without ranges or prereleases. Lists are bounded and cannot contain duplicates; unknown fields are rejected. An optional `configSchema` declares keys with a `type` (`string`, `number`, `boolean`, `object`, or `array`) and `required` flag. Objects declare `properties`; arrays declare an `items` rule and optional `maxItems`. Strings can specify `minLength` and `maxLength`, numbers can specify inclusive `minimum` and `maximum`, and primitives can specify a bounded `enum`. Optional rules may specify a `default`; required rules cannot. Defaults are validated and materialized into a fresh configuration at registration, including nested defaults. Objects reject undeclared or unsafe keys. Schemas are limited to 256 rules and 10 nesting levels; objects have at most 64 keys, arrays at most 256 items, and configurations at most 10,000 values. This is a small custom schema, not JSON Schema.

The caller supplies its runtime and renderer, an explicit approval for each extension ID, version and scope, and the permissions approved for that extension. It also supplies the registrations needed by the application. The check rejects missing approvals, excess requested permissions, unsupported runtime or renderer, duplicate registrations, and missing requirements. It returns a compatibility result and diagnostic strings; malformed input throws. A host must treat any error as a failure.

An application definition may declare `extensions` as a bounded list of exact `{id, version, scope}` references. The `setExtensions` patch replaces that list, including through the development proposal workflow. A page can declare an extension component as `{id, type: 'Extension', extensionId, name, props?}`. The standard guard requires its owning extension to be referenced and that exact manifest to declare the component name. A repository refuses to publish a definition with references or extension components unless its host supplies a publication guard. The standard `createExtensionPublicationGuard(manifests, host, requirementsFor)` checks every reference against installed metadata, then checks compatibility, host approval, page components, and the requirements returned by a host-owned selector. Metadata and approvals are snapshotted at guard creation, and the selector receives a cloned draft. The repositories require a synchronous guard to return `true` before creating a publication; hosts providing a custom guard must enforce equivalent policy themselves. SQLite runs the guard inside its write transaction, after checking the revision. The control plane returns HTTP 409 when this extension check fails. Updating approvals requires creating a new guard and repository instance.

Generated apps include an initially empty `extensions.mjs` file for trusted host-owned static registrations. Each installed entry has `id`, `version`, `scope`, and a `components` map whose entries contain a trusted `render` function and optional `validate` function matching the web `ComponentRegistry` contract. The generated workspace accepts only an exact installed reference and an explicitly supplied component; missing versions or names fail rendering and cache compatibility. The host must align these registrations with publication approvals and replace the app when approvals change. The definition never supplies executable code or module URLs. The extension module is delivered to the browser and must not contain secrets.

The control-plane review UI can use the same module source via the `extensionModule` preview option described in [development proposals](development-proposals.md). Preview approval is disabled when an extension or component is missing or invalid. This is a rendering check; publication still requires the host's compatibility guard.

Applications can declare `extensionOperations` as `{extensionId, kind: 'tool' | 'provider', name}` entries using the `setExtensionOperations` patch. The standard publication guard requires each operation's exact owning extension reference and checks the name in that manifest's corresponding list. `registerDeclaredExtensionCapability` binds a declared tool or provider to a host-selected capability candidate with the same operation ID. It requires host authorization and input validation, and calls through `CapabilityRegistry` so its audit behavior applies. Provider implementations are trusted functions receiving `(input, {tenantId, principalId})`; they do not receive an implied authorization grant. Names must also be unique within the target capability registry. Hosts must use a validated published definition and rebuild bindings when it or approvals change.

`createExtensionRuntime(definition, extensionRegistry, audit, bindings)` constructs fresh web component and capability registries from a host-selected published definition. It verifies every reference, registers the page's declared extension components, and binds each declared operation using an explicitly supplied candidate, authorization function and input validator in `bindings.operations`, keyed by operation name. Optional `bindings.componentValidators` supplies component validators. Missing implementations, incompatible references, missing policies and collisions fail the entire construction; no partially built registry is returned. The host must still choose the published definition, protect its audit sink and authorization policy, and recreate the runtime when the publication or approvals change. This assembly is a server/host API; generated browser apps continue to use their separately supplied trusted static module.

An integration test exercises an approved extension through SQLite publication, process-style repository reopening, runtime assembly and an authorized capability call. It also verifies that rebuilding with revoked approval rejects registration and republication. Existing runtime instances do not automatically receive approval changes unless the host supplies the live invocation check below; rendering registrations must still be replaced when policy changes. This test covers the local repository and trusted in-process implementation, not package distribution or production deployment.

`ExtensionRegistry` accepts trusted, statically supplied functions for components, tools, and providers. Registration checks the manifest against the host approvals and target, requires exactly the declared names, validates the optional configuration, and rejects conflicts before installing anything. Numbers must be finite and strings are limited to 4,096 characters; a missing schema permits only empty configuration. `getConfiguration` returns a copy of the in-memory values. Do not put secrets in manifests or configuration; use a host-managed secret mechanism. `getForApplication` resolves a registration only from exact installed references and fails if any declared reference is unavailable. `registerExtensionComponent` connects a selected component to a web `ComponentRegistry`; the host must provide a trusted renderer and, when needed, its validator. `registerExtensionCapability` connects a selected tool to `CapabilityRegistry`, requiring the host to supply authorization and input validation; capability invocation continues to use the registry's audit and isolation behavior. The host must select references from a validated published definition, supply implementations with the correct contracts, and replace the target registries when that definition or its approvals change. Manifests returned by `getManifests()` are cloned and can be used when constructing a publication guard after registration. There is no dynamic loading, unregistration, or automatic registration of extensions.

This foundation does not load code from definitions or enforce extension permissions during execution. Package integrity and the opt-in signed-manifest policy are described below. The configuration schema does not support secret handling or JSON Schema. Approval data must come from a trusted host; extension code and registration implementations remain trusted. Do not use metadata checks as an authorization boundary. Flutter hosts must use the trusted policy and transport described below.

React Native hosts can use `registerDeclaredNativeExtensionComponent` with a `NativeComponentRegistry` to install a trusted renderer only for a component declared by the selected application and its exact extension reference. The host supplies a synchronous validator, and the native factory snapshots registrations. Native extension properties are static; binding and action behavior is not supplied automatically. See [React Native](react-native-adapter.md) for the contract. Flutter has a host-supplied registry described below.

For Flutter, `createFlutterExtensionPlan(definition, manifests, host)` validates a host-selected published definition against trusted manifests and a Flutter host's compatibility and approvals. It produces JSON metadata containing only declared component names and exact owner references. `FlutterComponentRegistry.fromPlan` resolves those entries against trusted static Dart implementations, requiring the expected application ID and definition revision and rejecting missing or ambiguous matches. Hosts can alternatively sign the plan and verify it in Flutter as described in [Flutter](flutter-adapter.md); both paths still require trusted publication selection, protected approvals and registry replacement when policy changes. The plan does not transfer executable code or runtime authorization. See [Flutter](flutter-adapter.md).


For live tool and provider approval, a host may pass `authorizeExtension(actor, reference, operation)` to `createExtensionRuntime`, or provide it on an individual declared capability policy. The runtime passes copies of the authenticated actor, exact extension reference and declared operation. It checks the regular capability policy and each configured approval callback before input validation and again after validation, immediately before invoking the trusted implementation. Both runtime-wide and operation-specific checks must allow the invocation. Revoked or unavailable approvals fail closed and are reflected in the normal capability audit. Policy callbacks must consult the host's current approval authority and enforce tenant and principal access; static manifest metadata is not an execution grant.

These are asynchronous checks, not a transaction with the extension's side effects: approval can change after the final check, and the implementation or downstream service must enforce any stronger commit-time policy. They do not revoke a component already delivered to a browser or native app. Hosts still need authenticated policy storage, update propagation, cache control and runtime replacement for component changes.


## Shared operation approvals

`PostgresExtensionApprovals` provides an optional shared approval source for declared tool and provider invocations. The host supplies a PostgreSQL primary query function, a clock, and an `authorize(actor, action, applicationScope, reference, operation)` callback. Call `initialize()` with a migration identity. Approvals are bound to tenant, application, exact extension ID/version/scope, and declared operation kind/name. `decide` creates or changes one approval using `expectedRevision` (0 for a new record) and an explicit expiry; a revocation uses `allowed: false` and `expiresAt: 0`. Successful changes append an actor-attributed audit event in the same database statement. Stale decisions fail rather than overwriting another administrator's decision.

Use `store.forRuntime({tenantId, applicationId})` as `createExtensionRuntime`'s `authorizeExtension` callback. It reads the primary database and checks the host's `invoke` policy, current approval and expiry on each check. `history` requires separate `audit` permission and returns bounded pages. The host must authenticate actors, authorize administration and invocation, align the approval with installed manifests and approved permissions, protect the primary connection, handle availability failures and audit growth, and prevent stale replicas from being used for approval decisions. Denied or failed decisions are not recorded by this mutation audit. Database triggers reject audit update, delete and truncate, but database administrators can bypass them; they are not an independent tamper-proof log.

The approval read, validation, authorization callback and extension execution are not one transaction with the extension's side effects. A revocation can race after the final check. Downstream commit-time enforcement is necessary where immediate revocation is required. This store does not revoke already delivered component code or provide production identity, package integrity, secrets, high availability or a policy administration UI.


`registerExtensionApprovalDecision`, `registerExtensionApprovalStatus` and `registerExtensionApprovalHistory` expose optional fixed-target administrative capabilities through `CapabilityRegistry`. The host fixes the tenant, application, exact extension reference and declared operation at registration; callers cannot select a different target. The decision capability uses POST and accepts exactly `{query: {allowed, expiresAt, expectedRevision}}`, with a separate input-aware `authorizeDecision` callback. Status and history use GET: status accepts `{query: {}}`, and history accepts `{query: {after?, limit?}}`. Status returns the current revision, allowed flag, expiry and whether it is currently active, or null when absent. The store independently enforces `manage`, `inspect` and `audit` permissions, and both capability and mutation audit apply. Authenticate administrators, restrict these capabilities, validate any business approval requirements, and configure a current primary database. The decision response can be lost after commit; inspect current state and audit before retrying rather than assuming it failed.

## Package integrity

A manifest may declare `integrity` as an SRI-style SHA-256 digest, `sha256-<base64>`, of the trusted package bytes the host installs. `computeExtensionIntegrity(bytes)` produces that value and `verifyExtensionIntegrity(integrity, bytes)` compares it in constant time. When a manifest declares a digest, `ExtensionRegistry.register(manifest, bindings, configuration, {packageBytes})` requires the bytes and rejects a missing or different digest before installing anything. Supplying bytes for a manifest without a digest also fails, so a host cannot believe a package was checked when it was not. Packages are limited to 64 MiB.

A host approval may pin the same `integrity` value. The manifest must then declare exactly that digest, or compatibility reports the extension as not approved; this applies to the registry, publication guard and Flutter plans. Without a pinned approval, an unpinned manifest remains valid, so require pins in host policy where integrity is mandatory.

The host must read the bytes it actually loads, from storage it controls, and supply the implementations built from them. The registry hashes the supplied bytes; it does not prove that the supplied functions came from those bytes, establish provenance, or check the package after registration. The separate opt-in signed-manifest policy below can authenticate the manifest and its digest. The digest in the manifest is only as trustworthy as the manifest and approval sources.


## Opt-in signed manifests

A trusted publisher can use `signExtensionManifest(manifest, keyId, privateKey)` with an Ed25519 private `KeyObject`. The validated manifest must contain the SHA-256 `integrity` digest of the package bytes. The returned version-1 envelope includes the key ID, manifest and signature. The signature covers a domain-separated key ID and a deterministic serialization of the complete manifest, including the digest. Object keys are sorted and array order is retained; this is the App Mixer format, not a claim of RFC 8785 compatibility. The signed serialization is limited to one million UTF-16 code units and rejects sparse arrays and negative zero.

A host can construct `new ExtensionRegistry(host, {trustedKeys: {publisher: publicKey}})` with one to 100 host-selected Ed25519 public `KeyObject`s. It must then call `registry.registerSigned(envelope, bindings, configuration, packageBytes)` for every registration; the ordinary `register` method rejects unsigned registrations under this policy. Verification checks the signature, selected key and package digest before the normal host approval, compatibility, configuration and binding checks. Failed checks do not install the extension. `verifySignedExtensionManifest(envelope, {trustedKeys}, packageBytes)` is also available for a host that needs to verify an envelope separately. Both return or retain snapshots rather than the caller's mutable manifest.

`registry.createPublicationGuard(requirementsFor)` builds a guard from the registry's installed manifests and snapshotted host approvals. On a signed registry, those manifests entered through verified registration. The guard is itself a snapshot: create and install a new guard when registrations or policy change, and rebuild the registry and runtime after key or approval changes. A SQLite lifecycle test covers signed registration, guarded publication, reopening, runtime assembly and rejection after a trusted-key change. This is a host-selected publication guard; other guards and unsigned registries remain available and do not inherit the signing policy automatically.

For Flutter, `createFlutterExtensionPlanFromRegistry(application, registry)` derives a plan from the registry's installed manifests and snapshotted host approvals. `signFlutterExtensionPlanFromRegistry(application, registry, options)` signs that checked plan using the existing tenant- and environment-bound Flutter plan format. The registry must target Flutter; if it was constructed with the signed-manifest policy, its installations were verified under that policy. A deterministic test fixture is produced from a publisher-verified registry and checked by the Flutter VM verifier, including target rejection and component resolution. The Flutter web suite also verifies that fixture in headless Chrome. The mobile integration test uses the same fixture and requires a connected device or simulator to execute. The plan-signing key is a separate host trust decision from the publisher keys. Flutter receives the signed plan, not the publisher manifest or proof that Dart implementations were built from package bytes. The original manifest-list plan APIs remain available and do not automatically enforce a registry signing policy.

Without additional restrictions, every trusted key can sign any extension accepted by the separate host approvals. To restrict publishers, set `allowedExtensions` on the signing policy to a map from every trusted key ID to a nonempty list of exact `{id, version, scope}` references. A signature is accepted only when its key is allowed for that exact reference; the same extension can appear under multiple distinct keys for rotation, and one key can list multiple versions. Restricted policies reject missing or unknown key entries, duplicate references and aliases for the same public key. The host must maintain these lists and the separate host approvals. Keys, restrictions and approvals are snapshotted when the registry is constructed. Replace the registry to change or revoke keys or approvals; a signature has no built-in expiry, version floor or revocation service. Existing generated and other host registrations continue to be unsigned unless the host explicitly uses this policy. Signature verification authenticates the provided manifest and package bytes; it does not prove that the provided JavaScript functions were built from those bytes or sandbox the code. Protect private keys, trusted key distribution, package storage and the loaded implementations, and use live authorization and audit for extension operations.

Declared extension capability bindings can set both `policyTimeoutMs` (100–30000 ms) and `maxPendingPolicies` (1–100). When live approval or bounds are configured, scope and live approval are rechecked before execution and after each other; callbacks may run repeatedly. A timeout or saturated pending limit returns HTTP 503, and a late approval cannot invoke the extension. Timed-out callbacks retain their slot until they settle and are not forcibly cancelled; input validation, registry audit and extension execution are outside these bounds. External approval changes are not atomic with execution, so the host still owns policy and production isolation.

Hosts can optionally supply `authorizeWithSignal` and `authorizeExtensionWithSignal` on a declared capability binding. `createExtensionRuntime` also accepts a global `authorizeExtensionWithSignal`; signal-aware callbacks take precedence over their legacy equivalents at the same level. On a policy deadline, the signal is aborted and the runtime will not start the next approval callback or invoke the extension after a late result. Callbacks must cooperate to stop their own external work; their slots remain occupied until they settle. Legacy callback signatures are unchanged.

`PostgresExtensionApprovals.forRuntimeWithSignal(scope)` provides a cancellation-aware live approval hook for `authorizeExtensionWithSignal`. The store checks cancellation after each policy and query and will not start the next check after cancellation. Hosts may provide `authorizeInvokeWithSignal` and `queryWithSignal` to pass the signal to their own policy and database adapter; the existing callbacks remain required and are used as fallbacks. A driver or callback that ignores cancellation can continue its current operation, but its late result cannot trigger subsequent checks or extension execution. The existing PostgreSQL integration test exercises this hook with the normal query fallback.

The fixed-target `registerExtensionApprovalDecision` capability rechecks both scope and decision policies before starting the store mutation. Hosts may supply paired `policyTimeoutMs` and `maxPendingPolicies` and optional `authorizeWithSignal` and `authorizeDecisionWithSignal` callbacks, which take precedence over the legacy callbacks. Timed-out callbacks retain their slot until settlement; a late result cannot start a decision. Timeouts and saturation return HTTP 503. These bounds do not cover the store’s separate manage authorization, database operation or registry audit after execution starts. A lost response after a write can be uncertain; inspect the fixed-target status and history before retrying.

Generated apps can opt in to `mountExtensionApproval(root, {statusOperation, decisionOperation, historyOperation, targetLabel})` from `offline-runtime.mjs` for a single host-fixed extension operation. The host must configure the three separately authorized capabilities for the same scope and supply an accurate label. The view refreshes status before a decision, sends its revision as the optimistic precondition, and displays paginated audit history. Expiration is entered in the operator’s local time and displayed in UTC. After a lost or malformed decision response the view clears its status and disables further decisions until the operator refreshes status, reviews history and acknowledges the review. This state is local to the mounted view and resets on reload; status is only a point-in-time observation. With `historyNewestFirst: true` and a compatible history capability, the latest page is shown first and suffices for acknowledgement; otherwise the operator must reach the last page. The label is descriptive, not an authorization boundary, and the host remains responsible for authentication, audit protection and recovery. A generated-app integration test exercises a lost response, status refresh, revocation and history through the authenticated proxy and PostgreSQL.

The shared approval store treats a failed or malformed database write response as an uncertain outcome because the transaction may have committed. The capability returns HTTP 503 with `CAPABILITY_OUTCOME_UNCERTAIN`; operators must inspect status and immutable history before retrying. A confirmed stale expected revision returns HTTP 409, and a store authorization denial returns HTTP 403. A PostgreSQL integration test simulates losing the response after commit and verifies the recorded decision, audit history and rejection of the stale retry. Database administrators can still modify the store and its schema.

A PostgreSQL process-kill test stops an approval writer after the decision and audit statement but before commit, then after commit. Reopening verifies that both records roll back or persist together, stale retry is rejected, and another tenant’s approval remains isolated. This covers a single PostgreSQL instance and worker-process failure, not database-node failure or high availability.

Extension approval history also supports `order: "desc"` with an optional exclusive `before` event ID and returns `nextBefore` when older events remain. Ascending `after` and `nextAfter` remain the default. New events added between descending pages appear only after refreshing the first page. History access remains scoped and separately authorized.

The fixed-target approval status and history capabilities accept paired `readTimeoutMs` (100–30000 ms) and `maxPendingReads` (1–100), plus optional `authorizeWithSignal`. The bound covers capability authorization and the store read; the store can use `authorizeReadWithSignal` and `queryWithSignal` to propagate cancellation. A timed-out read retains its slot until underlying callbacks settle, returns HTTP 503, and cannot continue into further checks or return a late result. Drivers and callbacks that ignore cancellation may continue their current external work. The existing scope, audit and post-read authorization checks still apply.

Declared extension capability bindings can separately set `validationTimeoutMs` and `maxPendingValidations` (the same ranges as policy limits) and optionally provide `validateWithSignal`, which takes precedence over the required legacy `validate` callback. A timed-out validation retains its slot until it settles and returns HTTP 503; late results cannot invoke the extension. Scope and live approval are checked again after validation. The signal cannot forcibly stop host callback side effects, synchronous work or extension execution; registry audit remains outside the limit.

`ExtensionApprovalMetrics(store, {scope, reference, operation, authorize, timeoutMs?, maxPending?})` provides a separately authorized snapshot and Prometheus gauges for one fixed approval: presence, active state, revision and expiration time. The actor must also pass the store’s independent inspection policy. It reads twice and rejects a changing state, including an expiry transition between reads; later changes are not atomic with delivery. Optional paired timeout and pending limits fence late results and propagate cancellation to signal-aware store callbacks. The gauges contain no identifier labels, so deploy and secure each scrape endpoint with trusted target labels; do not combine multiple sources with the same metric names on one listener. It can be used with `AgentCombinedMetrics` and `createAgentMetricsServer`; denied access returns HTTP 403 and unavailable reads return 503. Tests cover the authenticated endpoint and PostgreSQL absent, active and expired states. These are point-in-time values, not proof that every worker has observed a revocation.

The shared approval store optionally accepts paired `writeTimeoutMs` (100–30000 ms) and `maxPendingWrites` (1–100) and a `queryWriteWithSignal` adapter. A timed-out database write may already have committed, so it returns `CAPABILITY_OUTCOME_UNCERTAIN` and holds its per-instance slot until the underlying query settles. Saturation is also reported conservatively as uncertain. The signal is advisory: neither a timeout nor driver cancellation proves rollback, and no automatic retry occurs. The limit covers the write callback only, not the earlier store manage policy or registry audit. Operators must reconcile status and history before retrying. A PostgreSQL test commits before delaying the response and verifies that reconciliation and stale-revision fencing prevent a duplicate decision.

The shared approval store separately supports paired `manageTimeoutMs` and `maxPendingManage` for its pre-write manage authorization. `authorizeManageWithSignal` optionally replaces the legacy manage callback and receives an abort signal. The store checks manage permission twice; timed-out callbacks retain their slot until they settle, and a late decision cannot dispatch the write. A timeout or saturated limit returns HTTP 503 before dispatch. This bound is independent of capability policy and database-write limits; external policy changes are not atomic with a later commit.

The approval view limits new expirations to the next 365 days using the browser clock; the store independently enforces its own clock and remains authoritative. At the maximum safe revision, the view permits only permanent revocation and disables renewal. A terminally revoked approval cannot be reapproved through the normal store API.

At the maximum JavaScript-safe revision, a currently allowed extension operation can be terminally revoked. PostgreSQL writes the revocation and its audit event atomically using an internal sentinel revision; public status and history expose the maximum safe revision with `terminal: true`. The decision capability returns the same safe revision and the terminal marker. Repeated revocation conflicts, and reapproval under that fixed identity is rejected. Older store versions fail closed when reading the sentinel; deploy compatible readers before relying on terminal status or audit interpretation. The `app_mixer_extension_approval_terminal` gauge reports the terminal state. Privileged direct database changes can still bypass the API. Tests cover competing revocations, tenant isolation, the authenticated operator view, and process death before and after commit.

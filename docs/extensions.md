# Extension compatibility foundation

`checkExtensionCompatibility` from `@app-mixer/core` checks metadata for trusted, statically installed extensions. A version 1 manifest declares an ID, exact extension version, scope (`platform`, `development`, or `application`), exact supported runtime versions, renderer IDs, component/tool/provider names, and requested permission names. IDs are lowercase ASCII identifiers. Versions use numeric `major.minor.patch` without ranges or prereleases. Lists are bounded and cannot contain duplicates; unknown fields are rejected. An optional `configSchema` declares up to 64 lowercase keys with a `type` (`string`, `number`, or `boolean`) and `required` flag. Strings can specify `minLength` and `maxLength`, numbers can specify inclusive `minimum` and `maximum`, and all types can specify a bounded `enum`. Constraints and enumerated values are checked when the manifest is validated and again against registration configuration. This is a small custom schema, not JSON Schema.

The caller supplies its runtime and renderer, an explicit approval for each extension ID, version and scope, and the permissions approved for that extension. It also supplies the registrations needed by the application. The check rejects missing approvals, excess requested permissions, unsupported runtime or renderer, duplicate registrations, and missing requirements. It returns a compatibility result and diagnostic strings; malformed input throws. A host must treat any error as a failure.

An application definition may declare `extensions` as a bounded list of exact `{id, version, scope}` references. The `setExtensions` patch replaces that list, including through the development proposal workflow. A page can declare an extension component as `{id, type: 'Extension', extensionId, name, props?}`. The standard guard requires its owning extension to be referenced and that exact manifest to declare the component name. A repository refuses to publish a definition with references or extension components unless its host supplies a publication guard. The standard `createExtensionPublicationGuard(manifests, host, requirementsFor)` checks every reference against installed metadata, then checks compatibility, host approval, page components, and the requirements returned by a host-owned selector. Metadata and approvals are snapshotted at guard creation, and the selector receives a cloned draft. The repositories require a synchronous guard to return `true` before creating a publication; hosts providing a custom guard must enforce equivalent policy themselves. SQLite runs the guard inside its write transaction, after checking the revision. The control plane returns HTTP 409 when this extension check fails. Updating approvals requires creating a new guard and repository instance. The generated app and development preview do not yet render extension components.

`ExtensionRegistry` accepts trusted, statically supplied functions for components, tools, and providers. Registration checks the manifest against the host approvals and target, requires exactly the declared names, validates the optional configuration, and rejects conflicts before installing anything. Configuration permits only declared primitive values, finite numbers, and strings of at most 4,096 characters; a missing schema permits only empty configuration. `getConfiguration` returns a copy of the in-memory values. Do not put secrets in manifests or configuration; use a host-managed secret mechanism. `getForApplication` resolves a registration only from exact installed references and fails if any declared reference is unavailable. `registerExtensionComponent` connects a selected component to a web `ComponentRegistry`; the host must provide a trusted renderer and, when needed, its validator. `registerExtensionCapability` connects a selected tool to `CapabilityRegistry`, requiring the host to supply authorization and input validation; capability invocation continues to use the registry's audit and isolation behavior. The host must select references from a validated published definition, supply implementations with the correct contracts, and replace the target registries when that definition or its approvals change. Manifests returned by `getManifests()` are cloned and can be used when constructing a publication guard after registration. There is no dynamic loading, unregistration, or automatic registration of extensions.

This foundation does not load code, verify signatures or package integrity, or enforce extension permissions during execution. The configuration schema does not support nested values, defaults, secret handling, or JSON Schema. Approval data must come from a trusted host; extension code and registration implementations remain trusted. Do not use metadata checks as an authorization boundary. Automatic registration and tool/provider requirement derivation, provider integration, generated-app support, and other platform renderers remain P2-02 work.

# Extension compatibility foundation

`checkExtensionCompatibility` from `@app-mixer/core` checks metadata for trusted, statically installed extensions. A version 1 manifest declares an ID, exact extension version, scope (`platform`, `development`, or `application`), exact supported runtime versions, renderer IDs, component/tool/provider names, and requested permission names. IDs are lowercase ASCII identifiers. Versions use numeric `major.minor.patch` without ranges or prereleases. Lists are bounded and cannot contain duplicates; unknown fields are rejected.

The caller supplies its runtime and renderer, an explicit approval for each extension ID, version and scope, and the permissions approved for that extension. It also supplies the registrations needed by the application. The check rejects missing approvals, excess requested permissions, unsupported runtime or renderer, duplicate registrations, and missing requirements. It returns a compatibility result and diagnostic strings; malformed input throws. A host must treat any error as a failure.

A host can opt into publication checks by passing `createExtensionPublicationGuard(manifests, host, requirementsFor)` as the publication guard to `ApplicationStore` or `SqliteApplicationStore`. The host-owned selector derives extension requirements from a cloned draft; metadata and approvals are snapshotted at guard creation. The repositories require a synchronous guard to return `true` before creating a publication. SQLite runs the guard inside its write transaction, after checking the revision. The control plane returns HTTP 409 when this extension check fails. Hosts must supply the guard to every publishing repository; the default remains unguarded, and the current application definition does not itself declare extension requirements. Updating approvals requires creating a new guard and repository instance.

`ExtensionRegistry` accepts trusted, statically supplied functions for components, tools, and providers. Registration checks the manifest against the host approvals and target, requires exactly the declared names, and rejects conflicts before installing anything. Lookup returns the supplied function; callers are responsible for applying the appropriate implementation contract and enforcing authorization. Manifests returned by `getManifests()` are cloned and can be used when constructing a publication guard after registration. There is no dynamic loading, unregistration, or automatic connection to renderer and capability registries.

This foundation does not load code, verify signatures or package integrity, enforce permissions during execution, or validate extension configuration. Approval data must come from a trusted host; extension code and registration implementations remain trusted. Do not use this check as an authorization boundary. Configuration schemas, renderer and capability integration, explicit application extension references, and default publication integration remain P2-02 work.

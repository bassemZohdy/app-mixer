# Extension compatibility foundation

`checkExtensionCompatibility` from `@app-mixer/core` checks metadata for trusted, statically installed extensions. A version 1 manifest declares an ID, exact extension version, scope (`platform`, `development`, or `application`), exact supported runtime versions, renderer IDs, component/tool/provider names, and requested permission names. IDs are lowercase ASCII identifiers. Versions use numeric `major.minor.patch` without ranges or prereleases. Lists are bounded and cannot contain duplicates; unknown fields are rejected. An optional `configSchema` declares keys with a `type` (`string`, `number`, `boolean`, `object`, or `array`) and `required` flag. Objects declare `properties`; arrays declare an `items` rule and optional `maxItems`. Strings can specify `minLength` and `maxLength`, numbers can specify inclusive `minimum` and `maximum`, and primitives can specify a bounded `enum`. Optional rules may specify a `default`; required rules cannot. Defaults are validated and materialized into a fresh configuration at registration, including nested defaults. Objects reject undeclared or unsafe keys. Schemas are limited to 256 rules and 10 nesting levels; objects have at most 64 keys, arrays at most 256 items, and configurations at most 10,000 values. This is a small custom schema, not JSON Schema.

The caller supplies its runtime and renderer, an explicit approval for each extension ID, version and scope, and the permissions approved for that extension. It also supplies the registrations needed by the application. The check rejects missing approvals, excess requested permissions, unsupported runtime or renderer, duplicate registrations, and missing requirements. It returns a compatibility result and diagnostic strings; malformed input throws. A host must treat any error as a failure.

An application definition may declare `extensions` as a bounded list of exact `{id, version, scope}` references. The `setExtensions` patch replaces that list, including through the development proposal workflow. A page can declare an extension component as `{id, type: 'Extension', extensionId, name, props?}`. The standard guard requires its owning extension to be referenced and that exact manifest to declare the component name. A repository refuses to publish a definition with references or extension components unless its host supplies a publication guard. The standard `createExtensionPublicationGuard(manifests, host, requirementsFor)` checks every reference against installed metadata, then checks compatibility, host approval, page components, and the requirements returned by a host-owned selector. Metadata and approvals are snapshotted at guard creation, and the selector receives a cloned draft. The repositories require a synchronous guard to return `true` before creating a publication; hosts providing a custom guard must enforce equivalent policy themselves. SQLite runs the guard inside its write transaction, after checking the revision. The control plane returns HTTP 409 when this extension check fails. Updating approvals requires creating a new guard and repository instance.

Generated apps include an initially empty `extensions.mjs` file for trusted host-owned static registrations. Each installed entry has `id`, `version`, `scope`, and a `components` map whose entries contain a trusted `render` function and optional `validate` function matching the web `ComponentRegistry` contract. The generated workspace accepts only an exact installed reference and an explicitly supplied component; missing versions or names fail rendering and cache compatibility. The host must align these registrations with publication approvals and replace the app when approvals change. The definition never supplies executable code or module URLs. The extension module is delivered to the browser and must not contain secrets.

The control-plane review UI can use the same module source via the `extensionModule` preview option described in [development proposals](development-proposals.md). Preview approval is disabled when an extension or component is missing or invalid. This is a rendering check; publication still requires the host's compatibility guard.

Applications can declare `extensionOperations` as `{extensionId, kind: 'tool' | 'provider', name}` entries using the `setExtensionOperations` patch. The standard publication guard requires each operation's exact owning extension reference and checks the name in that manifest's corresponding list. `registerDeclaredExtensionCapability` binds a declared tool or provider to a host-selected capability candidate with the same operation ID. It requires host authorization and input validation, and calls through `CapabilityRegistry` so its audit behavior applies. Provider implementations are trusted functions receiving `(input, {tenantId, principalId})`; they do not receive an implied authorization grant. Names must also be unique within the target capability registry. Hosts must use a validated published definition and rebuild bindings when it or approvals change.

`createExtensionRuntime(definition, extensionRegistry, audit, bindings)` constructs fresh web component and capability registries from a host-selected published definition. It verifies every reference, registers the page's declared extension components, and binds each declared operation using an explicitly supplied candidate, authorization function and input validator in `bindings.operations`, keyed by operation name. Optional `bindings.componentValidators` supplies component validators. Missing implementations, incompatible references, missing policies and collisions fail the entire construction; no partially built registry is returned. The host must still choose the published definition, protect its audit sink and authorization policy, and recreate the runtime when the publication or approvals change. This assembly is a server/host API; generated browser apps continue to use their separately supplied trusted static module.

An integration test exercises an approved extension through SQLite publication, process-style repository reopening, runtime assembly and an authorized capability call. It also verifies that rebuilding with revoked approval rejects registration and republication. Existing runtime instances do not automatically receive approval changes unless the host supplies the live invocation check below; rendering registrations must still be replaced when policy changes. This test covers the local repository and trusted in-process implementation, not package distribution or production deployment.

`ExtensionRegistry` accepts trusted, statically supplied functions for components, tools, and providers. Registration checks the manifest against the host approvals and target, requires exactly the declared names, validates the optional configuration, and rejects conflicts before installing anything. Numbers must be finite and strings are limited to 4,096 characters; a missing schema permits only empty configuration. `getConfiguration` returns a copy of the in-memory values. Do not put secrets in manifests or configuration; use a host-managed secret mechanism. `getForApplication` resolves a registration only from exact installed references and fails if any declared reference is unavailable. `registerExtensionComponent` connects a selected component to a web `ComponentRegistry`; the host must provide a trusted renderer and, when needed, its validator. `registerExtensionCapability` connects a selected tool to `CapabilityRegistry`, requiring the host to supply authorization and input validation; capability invocation continues to use the registry's audit and isolation behavior. The host must select references from a validated published definition, supply implementations with the correct contracts, and replace the target registries when that definition or its approvals change. Manifests returned by `getManifests()` are cloned and can be used when constructing a publication guard after registration. There is no dynamic loading, unregistration, or automatic registration of extensions.

This foundation does not load code from definitions, verify signatures or package integrity, or enforce extension permissions during execution. The configuration schema does not support secret handling or JSON Schema. Approval data must come from a trusted host; extension code and registration implementations remain trusted. Do not use metadata checks as an authorization boundary. Flutter hosts must use the trusted policy and transport described below.

React Native hosts can use `registerDeclaredNativeExtensionComponent` with a `NativeComponentRegistry` to install a trusted renderer only for a component declared by the selected application and its exact extension reference. The host supplies a synchronous validator, and the native factory snapshots registrations. Native extension properties are static; binding and action behavior is not supplied automatically. See [React Native](react-native-adapter.md) for the contract. Flutter has a host-supplied registry described below.

For Flutter, `createFlutterExtensionPlan(definition, manifests, host)` validates a host-selected published definition against trusted manifests and a Flutter host's compatibility and approvals. It produces JSON metadata containing only declared component names and exact owner references. `FlutterComponentRegistry.fromPlan` resolves those entries against trusted static Dart implementations, requiring the expected application ID and definition revision and rejecting missing or ambiguous matches. The plan is not signed or a token: the host must authenticate its transport, select the correct publication, protect approvals, and rebuild the registry when the publication or approvals change. The plan does not transfer executable code or runtime authorization. See [Flutter](flutter-adapter.md).


For live tool and provider approval, a host may pass `authorizeExtension(actor, reference, operation)` to `createExtensionRuntime`, or provide it on an individual declared capability policy. The runtime passes copies of the authenticated actor, exact extension reference and declared operation. It checks the regular capability policy and each configured approval callback before input validation and again after validation, immediately before invoking the trusted implementation. Both runtime-wide and operation-specific checks must allow the invocation. Revoked or unavailable approvals fail closed and are reflected in the normal capability audit. Policy callbacks must consult the host's current approval authority and enforce tenant and principal access; static manifest metadata is not an execution grant.

These are asynchronous checks, not a transaction with the extension's side effects: approval can change after the final check, and the implementation or downstream service must enforce any stronger commit-time policy. They do not revoke a component already delivered to a browser or native app. Hosts still need authenticated policy storage, update propagation, cache control and runtime replacement for component changes.


## Shared operation approvals

`PostgresExtensionApprovals` provides an optional shared approval source for declared tool and provider invocations. The host supplies a PostgreSQL primary query function, a clock, and an `authorize(actor, action, applicationScope, reference, operation)` callback. Call `initialize()` with a migration identity. Approvals are bound to tenant, application, exact extension ID/version/scope, and declared operation kind/name. `decide` creates or changes one approval using `expectedRevision` (0 for a new record) and an explicit expiry; a revocation uses `allowed: false` and `expiresAt: 0`. Successful changes append an actor-attributed audit event in the same database statement. Stale decisions fail rather than overwriting another administrator's decision.

Use `store.forRuntime({tenantId, applicationId})` as `createExtensionRuntime`'s `authorizeExtension` callback. It reads the primary database and checks the host's `invoke` policy, current approval and expiry on each check. `history` requires separate `audit` permission and returns bounded pages. The host must authenticate actors, authorize administration and invocation, align the approval with installed manifests and approved permissions, protect the primary connection, handle availability failures and audit growth, and prevent stale replicas from being used for approval decisions. Denied or failed decisions are not recorded by this mutation audit. Database triggers reject audit update, delete and truncate, but database administrators can bypass them; they are not an independent tamper-proof log.

The approval read, validation, authorization callback and extension execution are not one transaction with the extension's side effects. A revocation can race after the final check. Downstream commit-time enforcement is necessary where immediate revocation is required. This store does not revoke already delivered component code or provide production identity, package integrity, secrets, high availability or a policy administration UI.


`registerExtensionApprovalDecision`, `registerExtensionApprovalStatus` and `registerExtensionApprovalHistory` expose optional fixed-target administrative capabilities through `CapabilityRegistry`. The host fixes the tenant, application, exact extension reference and declared operation at registration; callers cannot select a different target. The decision capability uses POST and accepts exactly `{query: {allowed, expiresAt, expectedRevision}}`, with a separate input-aware `authorizeDecision` callback. Status and history use GET: status accepts `{query: {}}`, and history accepts `{query: {after?, limit?}}`. Status returns the current revision, allowed flag, expiry and whether it is currently active, or null when absent. The store independently enforces `manage`, `inspect` and `audit` permissions, and both capability and mutation audit apply. Authenticate administrators, restrict these capabilities, validate any business approval requirements, and configure a current primary database. The decision response can be lost after commit; inspect current state and audit before retrying rather than assuming it failed.

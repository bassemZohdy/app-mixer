# Published-definition cache

`PublishedDefinitionCache` stores cloned, validated immutable published versions in memory with a bounded size and TTL. Its key includes tenant ID, a host-derived authorization scope/version, application ID, schema version, and publication version. Callers must authenticate and authorize before selecting a scope; a cache key is not an authorization check. Change the authorization key or invalidate the relevant scope when permissions change. Do not put credentials in the key.

`CachedPublishedRepository` wraps a repository for one trusted scope and can be passed to `createDataPlane`. Version-specific reads can use the cache. Latest reads always consult the authoritative repository to discover the current version, so a publication made by another process is observed without relying on a local invalidation event. Missing entries are not cached. `invalidate` removes entries for an exact scope and optional version; `clear` discards all entries. The repository remains authoritative and can repopulate the cache after eviction.

This is a local server-cache foundation. The Data Plane supports optional host-supplied publication authorization but does not derive cache tenant or permission scopes. The caller must enforce those boundaries before using the wrapper. Cross-process invalidation for permission changes, durable/offline storage, and production authorization are not implemented.

## Client revalidation

`ClientPublishedCache` in `@app-mixer/web` holds one cloned publication in memory. Its host supplies a trusted scope, a publication compatibility validator, and a loader. The loader must authenticate and authorize every request, send the previous ETag as `If-None-Match`, and return either a 200 publication with its ETag or a 304. Both data-plane publication routes support this conditional request and return `Cache-Control: no-store`; caching is explicit and in memory rather than delegated to a shared HTTP cache. Every refresh revalidates against the server; failures do not return a cached fallback.

When tenant, application, schema, or permissions change, call `setScope` with a newly authenticated scope, or `clear` on logout. These calls discard the entry and reject older in-flight responses. Concurrent refreshes also reject responses superseded by a later request. The server's `invalidate` or `clear` remains necessary when its trusted authorization scope changes. There is no cross-process permission invalidation bus; each host is responsible for enforcing authorization and clearing affected caches.

A generated app can opt into the published data plane by setting `DATA_PLANE_URL` to a loopback HTTP URL ending in `/application`. Set `PUBLICATION_SCHEMA_VERSION` to the published schema version (1 by default, or 2) and restart the local server when changing it. Its local server proxies publication reads and conditional requests; the workspace renders supported published Text, Input, static Card and matching host-installed extension components and offers a refresh button. With no URL configured it uses the scaffold definition. If a URL is configured but invalid or unavailable, it reports an error rather than falling back to the scaffold. The data plane may wrap its repository with `CachedPublishedRepository` to enable the server cache. The local integration is independent of the runtime agent.

This integration uses a fixed local scope and an unauthenticated loopback data plane. It is for single-user local development, not tenant isolation, production authorization, offline storage, or automatic cross-process permission invalidation. Hosts implementing identity must derive and enforce trusted scopes and invalidate caches on permission changes. Other built-in manifest components remain unsupported.

## Encrypted offline publication store

`EncryptedPublicationCache` from `@app-mixer/web/offline-publications` is an opt-in IndexedDB store for a single published definition. A host must supply `enabled: true`, a non-extractable AES-GCM key, a maximum age (up to 30 days), a compatibility validator, and an authorization callback. Its scope includes tenant, principal, authorization version, application, and schema. Use a non-secret authorization version, change it when permissions change, and clear the relevant cache on logout. The host owns key provisioning and lifecycle and must authorize every read and write; the store does not authenticate users or persist credentials.

Store only a publication obtained through an authenticated and authorized server response, together with its quoted SHA-256 ETag. The store checks the publication's content against that ETag and the scope, encrypts it with AES-GCM, and rejects incompatible, altered, or older versions. The ETag is an integrity check, not a signature or proof of authorization. Reads enforce the configured age and authorization callback. A clear invalidates competing writes through a revision tombstone and is allowed even after read or write access is revoked, so a host can remove local content on logout. Clearing also removes the saved publication version: a later authorized store can accept an older version. Database snapshots can still be rolled back unless the optional host rollback anchor below is configured.

### Publication rollback anchor

A host can pass `rollbackAnchor: {read, advance}` to `EncryptedPublicationCache.open`. `read()` returns a nonnegative safe-integer floor, and `advance(counter)` must durably retain the maximum received value even when calls arrive out of order. The host must protect this floor outside the browser storage being checked and bind it to the exact tenant, principal, authorization key, application and schema scope. An existing cache has a local counter of zero until its first anchored mutation; the external floor for that scope must initially be zero.

The cache authenticates an encrypted counter with the publication key and advances it in the same IndexedDB transaction as each store, clear and key rotation. New counters bind the exact encrypted publication or clear marker, so selective replacement or deletion is detected when the counter is checked. On open and during each read, store, clear and key rotation, an invalid or unauthenticated counter fails closed; a missing counter below a positive host floor or a lower local counter reports `Offline publication rollback detected`. A local counter ahead of the host floor is advanced during these checks. Anchor unavailability can therefore prevent reads and mutations, including clear, until recovery. If the post-commit `advance` fails, the change remains committed and `hasPendingRollbackAnchor()` returns true; call `syncRollbackAnchor()` to recheck the external floor and retry, or reopen when the host anchor is available. A failed advance leaves a window in which restoration at or above the old floor is not detected. On rotation, the counter is re-encrypted with the new key; a failed advance can be reconciled when the new key is reopened.

These checks detect whole-cache snapshot restoration and counter deletion observed at operation boundaries, including while the cache is open. The browser and host anchor do not share an atomic transaction, so a restore between a check and an operation can still race. The checks do not protect a reset or compromised host floor or enforce a publication-version floor after an intentional clear. Existing v1 counters remain readable but do not bind a publication until the next anchored store, clear or key rotation advances them to v2. Older anchored clients cannot read v2 counters; update every client before relying on the new binding. Every writer and key-rotation client for the scope must use the anchor; older or unanchored clients can bypass it. Concurrent changes can fail with `Offline publication cache changed`; retry only after rechecking authorization and current state. The host is responsible for storage recovery, anchor availability, trusted key management and any stronger anti-rollback policy.

### Rotating a publication key

`await cache.rotateKey(nextKey)` re-encrypts an existing publication under a new non-extractable AES-GCM key. It requires both read and write authorization, checks them again before committing, and uses the existing revision as a compare-and-swap guard. Publication content, ETag and saved time are preserved; rotation does not extend its offline lifetime. The method returns `true` and closes the old cache handle after a committed rotation. It returns `false` when no publication was present; this still commits a key marker and closes the old handle. Reopen the cache with the new key after any successful rotation.

The host must provision and durably retain the new key before rotation and coordinate the key switch with its own key-management system. The authenticated marker fences reads, writes and clears by other current-version cache instances after rotation; opening the current store upgrades its IndexedDB database to version 3, requests that existing version-1 and version-2 connections close, and prevents App Mixer clients that explicitly open those older versions from reopening it. Both offline stores may use the same database name; their separate object stores and keys remain independent. An uncooperative connection can block the upgrade; close it and retry. Other code that opens the current database version but ignores the marker is not fenced and must be stopped before rotation. Before a scope has been rotated, no marker authenticates its key on open. A crash after the IndexedDB commit but before the host records success can leave the outcome unknown; retain both keys until the host has reconciled which key can authenticate the entry. Authorization changes are not atomic with IndexedDB commits. Rotation does not securely erase prior ciphertext from browser storage or backups, and the host remains responsible for key revocation, recovery and disposal. Offline queue keys are independent and are not rotated by this operation.

The store does not perform network requests or select an offline fallback. In particular, a host must not use it to bypass authentication or authorization failures. The generated app can integrate this store as described below; its service worker caches only the static shell.

## Generated-app integration

Generated apps include `offline-publication-host.mjs`, which defaults to returning `null` and leaves this feature disabled. A trusted host may implement `initializeOfflinePublication()` to unlock a key and return the store options, plus `fetchPublication`, `isOffline` and `onReady`. `fetchPublication` must authenticate and authorize the request and return its response; the runtime accepts a 200 with an ETag and checks the content before saving. It requests a full response on each refresh. `isOffline` must return `true` only when the host has established a network outage. Only a rejected fetch followed by that explicit confirmation permits a saved copy; HTTP errors, including 401 and 403, never do. The page labels a saved copy as offline.

`onReady` receives `{lock, clear, hasPendingRollbackAnchor, syncRollbackAnchor}`. The last two expose anchor recovery when configured; `syncRollbackAnchor()` fails if no anchor was configured. Call `lock()` when the key is locked or the identity changes: it clears the displayed publication and invalidates in-flight results. Call and await `clear()` when deleting that scope's stored publication; it also clears the display. Reload and initialize a new host session after locking or changing scope. The app verifies its own application ID and schema version and supplies its workspace compatibility check. The host must still enforce current access in the `authorize` callback, including when offline, and own key protection, permission-version changes, expiry and revocation. Do not embed keys or credentials in the static host module.

Enable the static shell separately with `enableOfflineShell(revision)` and change the revision after changing any shell or host module. The host initialization code must be able to unlock the key while disconnected. The default generated data plane remains an unauthenticated local development integration; it does not establish production identity or authorization. Browser eviction and expired entries can make an offline copy unavailable.

# Local agent memory

## Optional mutation audit

Set `audit: true` when constructing `SqliteAgentMemory` to append an actor-attributed event in the same SQLite transaction as each successful write, delete, or nonempty expiration purge. If the audit insert fails, the memory change rolls back. Events contain the scoped actor ID, action, memory ID and resulting revision for individual changes, or a count for a purge, and the host clock time. They do not contain memory values or provenance. Failed and denied operations, reads, empty purges and older changes are not recorded.

Call `auditHistory(actor, scope, {after?, limit?})` for a bounded page. The host authorization callback must permit `audit` for the scope and again for each event's memory ID; purge events use an undefined ID. Filtered pages may be empty while still returning `nextAfter`. Audit records are immutable through SQLite triggers, but a database administrator can alter the database or schema; this is not independent or tamper-proof storage. IDs and actors can themselves be sensitive. The history grows indefinitely, and host-managed storage protection, retention, clock accuracy, denied-access audit and external monitoring remain necessary.

Auditing is opt-in per store instance. Upgrade all writers and enable it consistently before relying on complete coverage: old or non-auditing instances can change memories without recording an event. Enablement does not backfill earlier changes. The host must authenticate actors and set permissions deliberately; audit access is separate from memory-read access and can expose identifiers even when values are inaccessible.

`SqliteAgentMemory` is an explicitly enabled, host-authorized SQLite store. Each memory is scoped by tenant, agent, owner kind and ID, and memory kind (`session`, `semantic`, `episodic` or `procedural`). A user association does not grant access to organization memory. The host supplies an `authorize(actor, scope, action, memoryId)` callback and must derive the actor from authenticated context, enforce tenant and owner policy, and validate writes. Reads, writes, deletes, listing and expiration cleanup are separately authorized. Listing also checks read authorization for each returned record; paginated listing can be used to export authorized records.

Each bounded JSON value carries an explicit `run`, `human` or `system` provenance reference, an expiration time, and an optimistic revision. The host configures maximum retention (up to 365 days) and a live-entry limit per scope. Expired records are not returned. `purgeExpired` clears expired values and provenance after separate host authorization. Delete also clears the value and provenance; both retain a revision tombstone to reject stale writes, and a recreated ID receives a higher revision. History is bounded to ten times the configured live-entry limit per scope; after reaching it, new IDs are rejected until the host performs a separately designed maintenance process.

The database and backups are not encrypted, and SQLite pages, journals or backups may retain deleted data. Clearing a value is not cryptographic erasure. The host must secure storage, control backup retention, authorize all callers, validate provenance and choose a consistent clock and policy across instances. This store provides structured records for all four kinds. Production identity, comprehensive audit coverage and distributed adapters remain open.

SQLite memory listings and audit history recheck scope permission before returning after asynchronous per-record authorization; policy changes and records are not read from a consistent snapshot.

## Semantic retrieval

`AgentSemanticMemory` wraps the store with exact cosine search for a bounded semantic scope. The host supplies an embedding function, a stable model/version ID and dimensions. `put` checks write permission before sending text to the embedding provider and rechecks it before storing the text, normalized vector, provenance and expiration. `search` checks list permission before embedding the query, scans authorized records for the same model ID, ranks them, rechecks record permission and revision, and rechecks scope list permission after the final record checks before returning hits. Hybrid search applies the same final scope check; access and records are not held in a single consistent snapshot. Invalid vectors, mismatched models and expired or inaccessible records are excluded or rejected. The current local store is limited to 1,000 live entries per scope; search is a linear scan, not a production vector index. Changing embedding models requires an explicit re-embedding plan.

`registerSemanticMemorySearch` registers a read-only capability with a fixed host-selected scope and result limit. It uses the normal capability registry for authorization, input validation and dispatch; the memory store applies its own per-record checks. A configured agent must be explicitly allowed that capability. The model cannot select another tenant, agent or owner through the tool input. Returned text and provenance are tool data, not trusted instructions; the host must retain capability authorization and evaluate prompt-injection and retrieval quality for its deployment.

`registerSemanticMemoryWrite` optionally exposes a separate write capability for configured agents. The host fixes the semantic scope, operation and path, and supplies `authorize(actor)`, `authorizeWrite(actor, input)` and `metadata(actor, input)`. The model supplies exactly `{query: {memoryId, text, expectedRevision}}`, using revision `0` to create or a positive revision to update. The host-derived metadata supplies the expiration and provenance; callers cannot select the tenant, owner, provenance or retention. A successful write returns only the ID, revision and expiration. `AgentSemanticMemory.put` also returns this metadata. The registry applies its audit, input validation and both policies; the store separately authorizes the write before embedding and again before committing. Policy callbacks receive copies, and authorization is rechecked after metadata resolution.

Only enable writes for trusted, explicitly allowed agent operations. A model's proposed memory is untrusted content and can persist prompt-injection or sensitive information; host policy must decide what may be stored and which IDs can be overwritten, verify provenance, approve the embedding provider and enforce retention and consent. Capability policy cannot be atomic with a later asynchronous embedding call; the store's final write policy must enforce current access independently. An audit failure or interrupted response after commit can leave the outcome unknown. Revision checks prevent a stale update but do not prove whether a prior write succeeded; inspect and reconcile before retrying, especially when using action journals or external effects. The local store is not a distributed transaction or a production memory service.

`registerSemanticMemoryDelete` optionally exposes a separate fixed-scope removal capability. A caller supplies exactly `{query: {memoryId, expectedRevision}}` with the positive revision obtained from an authorized read; the host supplies separate `authorize` and input-aware `authorizeDelete` policies. The store independently authorizes deletion and atomically checks the revision. A successful response contains only the ID and `deleted: true`; the normal capability audit applies. An agent must be explicitly allowed this operation, and hosts should require user approval where deletion is sensitive. A model cannot change scope, but its requested ID is untrusted; authorization must restrict which records it may remove.

Deletion clears the current value and provenance and retains the revision tombstone; SQLite pages, journals and backups can retain old content, so this is not cryptographic erasure. Capability authorization and the store's delete policy are separate asynchronous checks; configure the store to enforce current policy at commit time. A lost response or failed success audit after deletion leaves an ambiguous result: inspect authorized state before retrying.

For a bounded hybrid search, a trusted host may call `searchHybrid(actor, scope, query, limit)` or configure the capability with `mode: 'hybrid'`. The default remains semantic-only. Hybrid search fuses the cosine ranking with a ranking by the fraction of distinct query words found in a memory, using equal-weight reciprocal ranks with a constant of 60. Words are Unicode letters and numbers after NFKC normalization and lowercasing; each side is limited to its first 256 words. Punctuation separates words, and there is no stemming or language-specific segmentation. A query without words uses only the semantic rank. Only authorized, unexpired records from the selected embedding model participate, and access and revision are rechecked before returning results. Hybrid scores are rank-based and must not be compared with cosine scores or used as calibrated confidence. This bounded scan is not an indexed full-text search; hosts should evaluate retrieval on representative data and languages.

Hosts may opt into a cosine cutoff by passing `{minSimilarity}` as the final argument to `search` or `searchHybrid`, or configuring `minSimilarity` on `registerSemanticMemorySearch`. It must be a finite number from -1 to 1; omitted preserves the existing behavior. The cutoff is applied to authorized candidate cosine scores before semantic ordering or hybrid rank fusion. In hybrid mode this can exclude an exact word match with a low cosine score, so choose it only after measuring representative queries. The model cannot override a capability's host-selected cutoff. This is a relevance filter, not an authorization check, calibrated confidence or prompt-injection defense.

Trusted hosts can use `evaluateAgentMemoryRetrieval({memory, actor, scope, mode, limit, cases})` to evaluate a labeled set of 1–100 cases. Each case has a unique ID, query and 1–100 distinct relevant memory IDs. Pass the same optional `minSimilarity` to evaluate a cutoff; the report includes the configured cutoff when supplied. The helper runs the selected search sequentially using that actor and scope, then reports retrieved IDs, recall, precision at the configured limit, reciprocal rank, average precision and binary-relevance nDCG at the limit per case, plus their unweighted means. nDCG discounts each relevant hit by log2(rank + 1) and divides by the ideal ordering of the first min(relevant count, limit) positions, so it rewards placing relevant memories higher, not only retrieving them. Average precision sums precision at each retrieved relevant rank and divides by the total number of labeled relevant IDs, including those not retrieved; it is zero when no relevant item is retrieved. Precision divides by the configured limit even when fewer results are returned. Relevant IDs that are inaccessible, expired, missing or associated with another embedding model remain in the recall denominator; labels should be curated for the intended actor and corpus. The report excludes query and memory text, but retrieved IDs can be sensitive. Search or authorization errors reject the entire evaluation; no partial report is returned.

Evaluation queries are sent to the configured embedder and can incur cost or disclose data to that provider. The host must authorize the evaluator and protect labels and reports. Results do not use a consistent database snapshot across searches: changes in records, access policy, clocks or models can affect comparison. Use a representative, reviewed dataset and controlled corpus, repeat runs for the target deployment, and assess safety and language coverage separately; these metrics do not establish production quality.

The embedding provider receives text and queries, so the host must approve that provider and its data handling and control credentials, costs and retention. Stored vectors and text are not encrypted. Search quality depends on the selected model and data; the deterministic tests verify ranking and access boundaries, not real-world recall or safety. Automatic context injection, production reranking, distributed indexes and production evaluation remain open.

`registerSemanticMemoryRead` optionally exposes a fixed-scope lookup for a known ID, using `{query: {memoryId}}`. The host must provide both `authorize` and input-aware `authorizeRead` policies; the store independently checks read access. It returns the text, revision, provenance and expiry, or `null` for a missing, expired, invalid or different-model record. It does not call the embedding provider or expose vectors. Memory text remains untrusted.


## Shared PostgreSQL adapter

`PostgresAgentMemory` is an opt-in shared store for multiple host processes. Supply `enabled`, `maxEntries`, `maxTtlMs`, `authorize`, `query`, and `transaction`, then call `initialize()` before use. The transaction callback must start a real PostgreSQL transaction on one dedicated connection, invoke its operation with a query function bound to that connection, commit on success and roll back on failure. Use READ COMMITTED isolation. Every writer, delete and purge using this adapter locks a row for the full scope, making revision checks and live/history quotas atomic across participating processes. Deploy the same limits, clock policy, authorization and adapter version to every writer. Do not write directly to the tables or use a transaction callback backed by a connection pool without pinning a connection; doing so invalidates these guarantees.

The same tenant, agent, owner and kind isolation, optimistic revisions, expiration, tombstones, per-record listing authorization, bounded values and host-supplied provenance apply. `AgentSemanticMemory` accepts this adapter, but remains a bounded linear scan rather than an indexed vector service. Authorization is rechecked after acquiring a write lock and after database reads; listings, indexed searches and audit pages recheck access to each returned record or event and then scope access before returning; if a final check fails, the whole response fails closed. After final authorization, reads, listings and indexed searches check returned revisions and expiration in a bounded database query and fail if records changed. This query does not lock records or make external policy atomic with data; external policy or data can still change after the last check; the host owns policy consistency. Clock skew can change expiration outcomes. A lost commit response leaves the result uncertain; inspect authorized state before retrying.

Set `audit: true` on every PostgreSQL writer to record writes, deletes and nonempty expiration purges atomically with their mutations. `auditHistory(actor, scope, {after?, limit?})` checks `audit` permission at scope and record level and returns bounded pages, including possibly empty filtered pages with a continuation cursor. Events contain actor, action, ID, revision, count and host clock time, but not values or provenance. Denied attempts, reads and earlier non-audited writes are not recorded. The audit table has update, delete and truncate rejection triggers, but privileged database administrators can alter the schema or bypass protections; this is not independently tamper-proof storage. Hosts need to secure and retain audit data and monitor storage growth. It does not encrypt content or erase database pages, replicas, logs or backups. Hosts must configure TLS, database roles, availability, backups, retention, monitoring and migrations. Scope-lock rows and revision tombstones persist; the history quota can eventually reject new IDs and requires a separately designed maintenance strategy. Production indexes and representative deployment evaluation remain open.

The PostgreSQL CI integration includes worker termination during expired-memory purges after mutation, before commit and after commit, verifying atomic audit, retry behavior and tenant isolation. It also includes worker termination immediately before and immediately after a transaction commit. A new connection checks that uncommitted values and audit events disappear together, while committed values and audit events remain together and tenant scope remains isolated. A single-node kind test also force-deletes worker pods on both sides of a semantic-memory commit and checks the shared database, scoped pgvector search and audit from a separate pod. These tests use one test database and do not establish database failover, node-loss durability, production deployment, or backup recovery.


## Retention worker

`AgentMemoryRetentionWorker` optionally schedules cleanup of an explicit host-supplied list of up to 1,000 scopes belonging to a fixed authenticated actor. Set `maxScopesPerPass` (1–100), `pollMs`, a per-scope host `authorize` callback and `onError`. It visits at most that many scopes per pass in round-robin order; denied or failing scopes do not stop later scopes from being visited. `runOnce()` performs one pass, while `start()` runs passes without overlap. `stop()` prevents a cleanup from starting after a pending host authorization returns, whether the pass was manual or polled, and waits for store operations already in flight. The interrupted scope is retried on a later pass. The worker passes a cancellation signal into the store: stopping while store authorization or a PostgreSQL update is pending prevents the purge from completing when cancellation is observed, and a PostgreSQL transaction rolls back. Direct callers may also pass an optional signal to `purgeExpired`. Stop still waits for pending callbacks and database operations, and cannot interrupt synchronous SQLite work or guarantee cancellation after a PostgreSQL commit has begun. The store independently authorizes each purge and retains tombstones, and enabled mutation audit records nonempty purges in the same transaction. PostgreSQL scope locks serialize overlapping workers.

The worker passes an `AbortSignal` as the third argument to its scope authorization callback. Optionally set both `authorizationTimeoutMs` (100 to 30000) and `maxPendingAuthorizations` (1 to 100) to bound these host callbacks per worker instance. Timeout or stop aborts the signal and prevents a late approval from starting a purge. An unfinished callback retains its slot until it settles, and a later pass reports saturation until capacity is available. With these limits, stop can finish without waiting for a callback that ignores cancellation. The limits do not cover the memory store's own authorization or database operations, and cannot interrupt synchronous work or reverse callback side effects. Without them, stop waits for the host callback.

The list and actor are fixed at construction; rebuilding the worker is required when scopes change. This worker does not discover new scopes, guarantee purge timing, coordinate a production scheduler, remove tombstones or erase database backups. Callbacks and database operations must return promptly; the host owns scheduler health, retries, storage protection and alerting.


Local SQLite listing and audit pages recheck each returned item and then scope authorization before returning. Listings also verify that returned records still have the same revision and have not expired. Semantic and hybrid searches, including exact/indexed comparisons, recheck access, revision and expiration for all selected hits after other asynchronous checks. A comparison rejects conflicting revisions for the same record. A failed final check rejects the response rather than returning a partially stale page. Policy may still change after the final check; hosts requiring atomic authorization must coordinate it with data access.

## Indexed PostgreSQL keyword search

Set `textIndex: true` on `PostgresAgentMemory` and call `initialize()` to create a PostgreSQL GIN full-text index on live semantic records. `AgentSemanticMemory.searchLexical(actor, scope, query, limit?, maxCandidates?)` uses it to find the current embedding model's records without calling the embedding provider. PostgreSQL's `simple` text configuration tokenizes and lowercases the query; all query tokens must match. Its tokenizer and rank differ from hybrid search's NFKC word matching. Results carry PostgreSQL text-rank scores, not cosine similarity or confidence.

The store first checks scope-list authorization, scans at most `maxCandidates` matches (default 100, maximum 1,000), then checks read access and revision for each candidate and rechecks scope authorization. It returns at most `limit` (default 5, maximum 20) valid records. Inaccessible, invalid, changed or expired records consume candidate slots, so a result can be short even when more authorized matches exist; increase the bound only within the documented limit. No denied record IDs are returned. Changes and policy decisions are not a database-wide snapshot, and host policy must remain current. Empty or punctuation-only queries can yield no matches. The host must evaluate relevance on representative languages and queries and must not treat retrieved text as trusted instructions.

The index is optional and maintained by PostgreSQL on writes and deletes; creating it may lock a populated table and consume time and storage. Plan production migration, privileges and monitoring before enabling it. It is a keyword index, not a vector index, and existing semantic and hybrid searches still use bounded linear scans.


## Indexed PostgreSQL vector search

A host can install pgvector 0.8.7 or newer in PostgreSQL's `public` schema, then configure `vectorIndex: {modelId, dimensions}` on `PostgresAgentMemory` and call `initialize()`. Dimensions must be 1–2,000 and must match that embedding model everywhere. Initialization creates a model-specific HNSW cosine index; hosts must coordinate initialization and migrations, provision sufficient database privileges and capacity, and schedule index creation because it can block writes. Existing and future `semantic-v1` records for that model must contain valid vectors of exactly that dimension; incompatible records can make index creation or writes fail. Treat model IDs as immutable versions and plan re-embedding and index retirement explicitly.

`AgentSemanticMemory.searchIndexed(actor, scope, query, limit?, maxCandidates?, options?)` checks scope access before embedding, uses a bounded pgvector search, and independently rechecks each candidate's read authorization and revision. It returns up to 20 authorized, valid records with cosine-based scores; `maxCandidates` defaults to 100 and is capped at 1,000. An optional host-selected `minSimilarity` from -1 to 1 filters the returned cosine scores inclusively after the bounded approximate search. A cutoff can return fewer results and does not improve index recall. The search uses pgvector's strict iterative scans and a bounded candidate list. It is approximate: expired or unauthorized records, filtering, index scan limits and index recall can yield fewer or different results than exact `search()`. A shared HNSW index can make one scope's vectors affect another scope's recall and timing, even though record authorization filters returned data. Hosts needing stronger performance or timing isolation should use separate databases or separately isolated indexes. Evaluate recall, latency, permissions and language coverage on representative deployment data; do not treat similarity as confidence or retrieved text as trusted instructions.

The index is maintained by PostgreSQL for writes and deletion, but this does not erase old data from pages, replicas or backups. Index construction, maintenance, database failover and monitoring are the host's responsibility. The existing exact and hybrid search methods remain available and do not use this index.


The host may configure `registerSemanticMemorySearch` with `mode: 'indexed'` or `mode: 'lexical'` and a fixed `maxCandidates`; the model supplies only query text and cannot change mode, limits or scope. The default remains exact semantic search. Indexed vector mode accepts a host-fixed `minSimilarity`; lexical mode does not, because text ranks are not cosine similarity. Both modes require their corresponding PostgreSQL indexes.

`evaluateAgentMemoryRetrieval` accepts `indexed` and `lexical` modes with the same candidate bound. For indexed vector search, `compareExact: true` also runs the exact semantic search for each query and reports its authorized IDs and the fraction found in the indexed results. Cases with no exact hits report `exactRecall: null` and are excluded from the mean; if all are empty, the mean is null. This overlap measures agreement with the exact top results, not relevance or safety. Both searches use the same query embedding and apply the same optional similarity cutoff, avoiding extra provider calls and differences caused by a changing embedding response. PostgreSQL vector precision and JavaScript arithmetic can still differ near a cutoff. They still execute sequentially without a shared database snapshot, so changing records, permissions or clocks can change the comparison. After the exact scan, the comparison rechecks indexed hits and drops records that are no longer readable, have disappeared, or have a different revision; it also rechecks scope access before returning. Use stable, representative labeled data and a controlled corpus for deployment evaluation.


To isolate the HNSW candidate graph for one tenant, agent, owner and semantic-memory kind, configure `vectorIndex: {modelId, dimensions, scope}` with that exact scope. The scoped index contains only records in that scope, and indexed searches through that adapter reject other scopes before sending query text to the embedder. The scoped query uses a distinct indexed expression so an existing global vector index cannot supply its candidates. Host authorization and per-record checks remain mandatory. Expired or unauthorized records within that scope can still affect recall and timing, and shared database resources can still create cross-tenant timing effects. Manage index count, database privileges and separate deployment boundaries according to the isolation required. A scoped index is not a replacement for database tenant isolation or a representative retrieval evaluation.

### Measured: shared versus scoped vector indexes

`node scripts/bench-memory-isolation.mjs [tenants] [memoriesPerTenant] [queriesPerTenant]` (needs `APP_MIXER_TEST_POSTGRES_URL` and `npm run build`) loads the same synthetic corpus into PostgreSQL with pgvector under each strategy and, for every query, compares the approximate index's top 5 with exact search. Every tenant draws from one shared vocabulary, so a query's nearest neighbours belong to many tenants. The deterministic reference embedder is used, so the figures show index behaviour, not the quality of an embedding model. Measured on one developer machine (pgvector 0.8.7, PostgreSQL 16, candidate limit 40):

| Tenants x memories | Strategy | Recall against exact search | Queries below full recall | Median and 99th percentile per query |
| --- | --- | --- | --- | --- |
| 20 x 500 | one shared index | 0.899 | 157 of 400 | 77 ms, 117 ms |
| 20 x 500 | one index per tenant | 0.998 | 3 of 400 | 80 ms, 113 ms |
| 50 x 300 | one shared index | 0.914 | 176 of 500 | 63 ms, 89 ms |
| 50 x 300 | one index per tenant | 0.998 | 6 of 500 | 60 ms, 86 ms |
| 100 x 200 | one shared index | 0.907 | 192 of 500 | 58 ms, 82 ms |
| 100 x 200 | one index per tenant | 0.998 | 4 of 500 | 54 ms, 79 ms |

The likely cause (not isolated by a separate experiment) is that the tenant filter is applied to the nearest candidates of the whole index, so a query can see a candidate list that belongs mostly to other tenants. A scoped index holds only one scope's memories and keeps recall near exact search at the same latency. The per-query time includes the exact comparison query, so it is not an index-only latency. The cost of scoped indexes is one index per tenant, agent, owner and kind to create, store and maintain, and a store object per scope. The cost showed up in loading: at 100 tenants of 200 memories (20,000 memories) writing the corpus took 329 s with per-tenant indexes and 165 s with one shared index. Creating the indexes is not the cost: setting up 100 scoped indexes on empty tables took 0.5 s. The loading ratio (per-tenant time over shared time) grew with the number of scopes in the three runs, about 1.1 times at 20 tenants (95 s against 85 s), 1.35 times at 50 (196 s against 145 s) and 2.0 times at 100, which fits each write paying for every scope's index on the same table. That reading is an inference from three points and was not tested separately, and the shared table holds one partial index per scope, so a deployment with thousands of tenants should expect write cost to keep growing and should measure it (or split scopes across tables or databases) before relying on one index per tenant. The choice (and the index-count limit that is acceptable for the deployment) still belongs to the owner. Production sizes, a production embedder and concurrent writes are not measured here.

### Decision: per-tenant indexes

On 2026-11-07 the product owner chose scoped indexes (`vectorIndex.scope`, one HNSW index per tenant, agent, owner and kind) for deployments that need recall close to exact search. The deployment owns the index count: create indexes when a scope is first used, monitor storage and write cost as scopes grow, and repeat the benchmark above at production sizes with the production embedder before relying on the figures.

## Erasing a scope

`SqliteAgentMemory.eraseScope(actor, scope)` tombstones every live or expired memory in one tenant, agent, owner and kind scope, for example when an owner asks for their data to be erased. It needs the host `authorize` callback to allow a separate `erase` action, so a cleanup worker that may only `purge` expired entries cannot erase live data. It returns the number erased, is idempotent, and with auditing enabled records one value-free `erase` event with the count. Revisions keep increasing, so a later write cannot reuse an old revision. The PostgreSQL adapter offers the same operation, taking the scope lock and writing the audit record in one transaction. Both adapters accept an optional `AbortSignal` as the third argument. SQLite checks it before and after authorization; its synchronous transaction cannot be interrupted. PostgreSQL also checks it after acquiring the scope lock and after the update and audit write, causing the transaction to roll back if cancellation is observed before the transaction callback returns. Cancellation does not forcibly interrupt a pending policy or database query, and a cancellation or lost response near commit can leave the outcome uncertain; inspect authorized state and audit before retrying. The host transaction implementation must roll back when its callback throws. PostgreSQL process-kill tests exercise termination between record clearing and the audit insert, before commit, and after commit; they verify atomic recovery, retry behavior and tenant isolation. These tests do not simulate a database server or node failure.

`registerAgentMemoryScopeErase(registry, {memory, scope, operationId, path, authorize, authorizeErase})` optionally exposes a POST capability for a host-fixed tenant, agent, owner and memory kind. Invoke with `{query: {confirm: true}}`; callers cannot select or broaden the scope. The capability requires the authenticated tenant, general capability permission and a separate erase policy, and rechecks both policies immediately before the store independently authorizes `erase`. Enable store audit on every writer to retain actor-attributed erasure evidence. Configure this powerful operation only for trusted administrators, protect the endpoint, and ensure policies and database availability are managed by the host. Optionally include a host-generated `requestId` in the query: `{query: {confirm: true, requestId: "request-1"}}`. The store atomically commits a durable scope- and principal-bound request marker with the erasure and any enabled audit, returning `{erased, replayed}`. A retry with the same ID and principal returns the original count without erasing subsequent writes; a different principal using the same scoped ID is rejected. Allocate a fresh unpredictable ID for each intended erasure and retain it through uncertain responses. The host may also call `eraseScopeOnce(actor, scope, requestId, signal?)` directly. Markers persist with a limit of 10,000 per scope and cannot be updated or deleted through ordinary database operations; privileged administrators can alter them, and restoring an older database snapshot can lose the fence. Plan storage, backups and migration before enabling this path. An initial or retried call still requires current authorization. Calls without `requestId` remain available but have no replay fence: do not automatically retry after a lost response or failed final audit, since later memories could be erased. Inspect authorized state and audit and explicitly decide whether a new erasure is intended. External policy changes are not atomic with the database transaction; callback timeouts and request limits must be supplied by the host.

`registerAgentMemoryErasureEvidence(registry, {memory, scope, operationId, path, authorize, authorizeEvidence})` optionally exposes a separately authorized GET capability with `{query: {requestId}}`. The host fixes the full scope and authorizes both the caller and the requested ID; the store independently requires `erase-audit` permission for that request ID, before and after reading. It returns the retained request ID, original principal and erased count, or `null` if absent. This evidence exists even for a zero-count keyed erasure and does not contain memory values or a timestamp. It is distinct from the optional mutation audit and cannot prove that a later write did not occur. Scope and request IDs and principals may be sensitive. Optional paired `timeoutMs` and `maxPending` limit concurrent pending capability callbacks and bound the response wait; a timed-out callback or query that ignores cancellation retains its slot until it settles. The signal prevents late results from being returned, but does not forcibly cancel database queries or store authorization callbacks. Host policies, database permissions, transport and identity remain the host responsibility. Direct hosts can use `getErasureRequest(actor, scope, requestId, signal?)`; both APIs require current authorization even for missing or previously completed requests.

Generated apps can opt in to `mountAgentMemoryErasure(root, {eraseOperation, evidenceOperation, scopeLabel})` from `offline-runtime.mjs`. The host must bind both capabilities to the same fixed scope, provide a clear scope label, authenticate and authorize the operator, and protect the page. The view requires an operator-supplied request ID and explicit confirmation. If the response is uncertain, it locks the request ID and prevents another erasure until the operator loads matching evidence and acknowledges it. Missing evidence does not establish that a request will not commit later; investigate before proceeding. The view does not persist the request ID or review state across reloads, so hosts and operators must retain the ID and protect access to evidence. It cannot verify whether memories were written after the recorded erasure. A generated-proxy integration test exercises a lost response, evidence review and owner isolation; DOM tests cover missing or malformed evidence and disposal. A headless browser acceptance test also exercises a lost response, evidence review, PostgreSQL persistence, the authenticated generated-app proxy and owner isolation.




At the maximum safe revision, expiry cleanup and scope erasure still clear values and provenance. The tombstone retains that maximum revision, so the same memory ID cannot be written again; hosts must choose another ID.

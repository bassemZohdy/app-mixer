# Persistent-agent definitions

`@app-mixer/agent` exports `validateAgentManifest` and `SqliteAgentDefinitions`. A version 1 manifest identifies a tenant and agent independently of any human user. It includes a name, an owner (`organization`, `team`, `application`, `service` or `user`), one or more administrator IDs, an optional user association, a service-principal ID, model provider and model IDs, an optional credential reference, an explicit capability allowlist, lifecycle settings and quotas. An empty capability list grants nothing. User association is metadata; it does not grant impersonation or delegated authority. Store a reference to a host-managed secret, never a credential itself, in `credentialRef`. The strict validator rejects unknown fields, duplicate administrators or capabilities, malformed identifiers, unsupported manifest versions and out-of-range limits.

`save(tenantId, manifest, expectedVersion)` creates an agent with expected version 0 or appends a new immutable version using optimistic concurrency. `get(tenantId, agentId, version?)` retrieves a specific or latest version; `list(tenantId, {after, limit})` returns up to 100 latest definitions in agent-ID order. The SQLite store isolates records by tenant and agent, persists versions across restart, and prevents updates, deletion and replacement of version rows. It rejects a manifest whose tenant differs from the requested scope. Versions are configuration snapshots, not execution checkpoints.

The repository is a local primitive: it does not authenticate callers or enforce ownership, administrators, service identities, permissions, lifecycle settings, quotas or credential access. A trusted host must authorize every read and write, derive tenant scope from authenticated context, validate referenced identities and capabilities against its policy, and protect the database and backups. Model provider identifiers and credential references are not resolved here. The definition repository itself is separate from run lifecycle, triggers, delegated authority and audit enforcement.

## Configured ephemeral runtime

`createConfiguredAgentRun` loads the current version from a trusted definition repository, requires an enabled manifest and an exact expected version, and calls host-supplied `authorizeRun`. It supplies the host model factory with the saved model configuration and only the manifest-allowlisted, host-bound tools. Every tool call rechecks the current definition and `authorizeCapability`, then invokes the normal capability registry as the configured service principal. The registry independently applies its own authorization, validation and audit. The optional user association is never used as delegated authority. A run handle is single-use; run authorization is checked again at execution, and a changed definition or revoked capability prevents later calls.

The host must provide authenticated tenant and agent scope, trusted authorization callbacks, a trusted model factory, credential resolution and capability bindings. The runtime does not authenticate callers, enforce owner/admin membership itself, or create an implicit user delegation. Timeouts and cancellation use abort signals and require cooperative model and capability implementations; an external call already dispatched may still complete. By default this is an ephemeral invocation; an explicitly configured LangGraph saver can persist state as described in [durable agent runs](durable-agent-runs.md). It is not a scheduler. The ephemeral runtime does not enforce manifest concurrency, token or daily quotas, retries or automatic recovery. The host-driven durable worker enforces local concurrency and daily run limits as described in [durable agent runs](durable-agent-runs.md).

Configured agents can optionally journal tool calls using the [agent action journal](agent-action-journal.md). Hosts must enforce authorization for cached results and ensure the target capability honors its idempotency key.

## Delegated user authority

A host may pass `delegation` to `createConfiguredAgentRun` with an authenticated, host-issued grant containing `tenantId`, `agentId`, `runId`, `principalId`, `grantId`, `permissionVersion` and an absolute `expiresAt` timestamp in milliseconds. Supply `authorize(identity, grant, operationId, input)` to revalidate the service principal, grant and user authority for each operation, including revocation and permission version. The runtime snapshots the grant, checks its scope and expiry around authorization and invokes the capability registry as the delegated user. The registry still applies its own user authorization. Service-principal capability policy is also required; a user association in the manifest never creates delegation.

For journaled actions, an authority binding to the service and user is durable alongside the action and any approval request. A retry or cached result cannot switch users or switch between service and delegated authority. The review page displays this binding. Renewed grants for the same service and user must pass current host authorization; their new expiry and policy version are checked on every invocation. Existing unbound action and approval records cannot be adopted by delegated runs.

This is a host-integrated local primitive: it does not authenticate users, provide renewal notifications, or enforce a distributed revocation transaction. A local durable grant registry is described below. An expired or revoked grant stops the affected call. Expiry before dispatch produces a distinct event that a journaled worker can use to wait for renewal; revocation and ambiguous dispatches still report a generic error. The host must stop the worker, inspect and reconcile any uncertain action, obtain renewed authority, and explicitly resume the run. The journal may conservatively mark an action uncertain if authority changes immediately before dispatch. Expiry cannot undo an already-dispatched effect; the downstream system must enforce its own authorization and idempotency. Input, grant metadata and audit data require protected storage.

### Durable local grants

`SqliteAgentDelegations` stores grants for one tenant, agent and run in the same SQLite database as `SqliteAgentRuns`. A trusted host authenticates actors and supplies an authorization callback for issuance, read, renewal, revocation, verification and history. `issue(actor, grant)` creates a grant only for a nonterminal, unarchived run, with expiry no later than its deadline and at most 24 hours away. `renew(actor, grantId, revision, permissionVersion, expiresAt)` keeps the same user, advances the revision and permits renewal after expiry. `revoke(actor, grantId, revision)` permanently revokes that grant. Concurrent updates use revision checks. Immutable events record the actor, user, permission version, expiry and revision. A revoked grant cannot be renewed; the authorized host may issue a new grant when policy permits.

The returned `record.grant` includes a revision. Pass that exact snapshot into the configured runtime, and call `store.verify(serviceActor, grant)` inside its `delegation.authorize` callback along with any operation-specific policy. Verification re-reads current state after authorization and rejects expired, revoked, stale or mismatched snapshots and terminal runs. The revision prevents an old snapshot becoming valid again if later renewal restores the same version and expiry. The host must construct a new runtime with the renewed grant after stopping and reconciling the prior attempt. Grant storage does not itself authenticate people or enforce policy at the downstream service. A host-integrated worker can persist a renewal wait as described in [durable agent runs](durable-agent-runs.md). Host authorization must validate user consent and the delegated permissions; grant records are not credentials. Protect the database, audit denied operations separately, and enforce downstream authorization because verification and an external effect cannot be one atomic transaction.

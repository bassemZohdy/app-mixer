# Persistent-agent definitions

`@app-mixer/agent` exports `validateAgentManifest` and `SqliteAgentDefinitions`. A version 1 manifest identifies a tenant and agent independently of any human user. It includes a name, an owner (`organization`, `team`, `application`, `service` or `user`), one or more administrator IDs, an optional user association, a service-principal ID, model provider and model IDs, an optional credential reference, an explicit capability allowlist, lifecycle settings and quotas. An empty capability list grants nothing. User association is metadata; it does not grant impersonation or delegated authority. Store a reference to a host-managed secret, never a credential itself, in `credentialRef`. The strict validator rejects unknown fields, duplicate administrators or capabilities, malformed identifiers, unsupported manifest versions and out-of-range limits.

`save(tenantId, manifest, expectedVersion)` creates an agent with expected version 0 or appends a new immutable version using optimistic concurrency. `get(tenantId, agentId, version?)` retrieves a specific or latest version; `list(tenantId, {after, limit})` returns up to 100 latest definitions in agent-ID order. The SQLite store isolates records by tenant and agent, persists versions across restart, and prevents updates, deletion and replacement of version rows. It rejects a manifest whose tenant differs from the requested scope. Versions are configuration snapshots, not execution checkpoints.

The repository is a local primitive: it does not authenticate callers or enforce ownership, administrators, service identities, permissions, lifecycle settings, quotas or credential access. A trusted host must authorize every read and write, derive tenant scope from authenticated context, validate referenced identities and capabilities against its policy, and protect the database and backups. Model provider identifiers and credential references are not resolved here. There is no administration API, trigger, durable run, delegated identity or agent-level audit trail yet; those remain separate persistent-agent tasks.

## Configured ephemeral runtime

`createConfiguredAgentRun` loads the current version from a trusted definition repository, requires an enabled manifest and an exact expected version, and calls host-supplied `authorizeRun`. It supplies the host model factory with the saved model configuration and only the manifest-allowlisted, host-bound tools. Every tool call rechecks the current definition and `authorizeCapability`, then invokes the normal capability registry as the configured service principal. The registry independently applies its own authorization, validation and audit. The optional user association is never used as delegated authority. A run handle is single-use; run authorization is checked again at execution, and a changed definition or revoked capability prevents later calls.

The host must provide authenticated tenant and agent scope, trusted authorization callbacks, a trusted model factory, credential resolution and capability bindings. The runtime does not authenticate callers, enforce owner/admin membership itself, or create an implicit user delegation. Timeouts and cancellation use abort signals and require cooperative model and capability implementations; an external call already dispatched may still complete. This is an ephemeral invocation, not a durable run or scheduler. Manifest concurrency, token and daily quotas, retries, checkpoints and recovery are not enforced by this runtime and remain open work.

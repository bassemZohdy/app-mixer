# Environment promotion

The local control plane can transfer a published definition between separate repositories. `POST /promotion/export` with `{ "sourceEnvironment": "development", "version": 1 }` returns a versioned package containing the definition, source environment and version, and a SHA-256 digest of those fields. `POST /promotion/import` with `{ "package": ..., "targetEnvironment": "production", "expectedVersion": 0 }` checks the package, its digest, the target application ID, schema, target compatibility guard and current target version before appending a new immutable publication. Both routes require the control token. `expectedVersion` is zero for an empty target; otherwise it is the latest target version. A stale request returns 409. The target draft and historical publications are not changed.

Promotion provenance records the claimed source and target environments, source version, package digest, and preceding target version. SQLite writes the publication and both provenance records in one transaction. After a lost response, inspect target provenance and latest version before retrying; a retry with the original precondition cannot publish twice. Older publications without provenance remain unknown. The existing SQLite provenance table stores promotion base records as `publish`, with a separate immutable promotion table; readers must use the current repository API to distinguish them.

## Authenticated remote client

`createRemotePromotionClient` in `@app-mixer/core` connects two explicitly configured origins. It requires HTTPS with normal certificate verification; HTTP is available only for loopback origins when `allowLoopbackHttp` is explicitly enabled for development. Redirects are rejected. The host supplies separate bearer tokens, an authenticated actor, an authorization callback and an audit callback. Configure origins, credentials and actor identity from trusted host configuration, not from an untrusted request or model. Use an authenticated TLS termination layer in front of each control plane; the control-token API itself remains a development prototype and does not implement production identity. The trusted host must bind each configured origin and credential to its intended environment and tenant, and enforce its own network access policy.

Call `promote` with `{actor: {tenantId, principalId}, applicationId, sourceEnvironment, sourceVersion, targetEnvironment, expectedVersion}`. The client asks the host to authorize export and import separately, verifies the package digest, application, source environment and version, and sends the target's optimistic version precondition. Authorization receives a copy of the request details and origins, never the tokens. The audit callback receives attempt, verification, authorization and completion events; it must durably record events if the host requires an audit trail. Pre-import callback failures prevent import. A completed event is not transactional with the target's publication, and permission changes after the import authorization cannot be coordinated atomically with the remote target.

An import error, malformed response, timeout, or failure to record the completed event raises `RemotePromotionUncertainError`: the target may already have committed. The client does not retry. Inspect the target's latest publication and durable provenance before deciding what to do; the original expected version prevents a duplicate publication. Source errors are reported without including endpoint responses or credentials.

The unsigned package digest checks consistency, not a digital signature. HTTPS and the host's trusted endpoint configuration establish transport identity. The host's publication guard must verify target runtime and extension compatibility. Do not put credentials or environment secrets in definitions. Promotion does not migrate business data or submit transactions. General schema evolution and production authorization remain open.


## Signed promotion packages

A trusted release service can call `signPromotionPackage(package, targetEnvironment, keyId, privateKey, expectedVersion)` with an Ed25519 private `KeyObject` and the expected target publication version. The version-bound signature prevents that envelope from being imported at a different target version. Omitting the final argument creates the older unbound signature format. The signed envelope binds the package digest, signer key ID and target environment. Configure the target with `createSignedPromotionVerifier([{sourceEnvironment, keyId, publicKey}], targetEnvironment, {requireVersionBound: true})` and pass `{verify}` as the sixth argument to `createControlPlane` (or `createDevelopmentPlanes`). The target rejects unsigned, altered, untrusted, wrong-application or wrong-target packages before calling the repository. Supply trusted public Ed25519 keys and source-environment bindings; replace the verifier to rotate or revoke keys. The control token, compatibility guard and optimistic version precondition still apply.

For remote promotion, supply `signPackage(package, details)` to `createRemotePromotionClient`, returning the signed envelope and using `details.expectedVersion` when signing. The client verifies that the signed envelope still contains the exported package and target before sending it. Signing failure occurs before import. The target must independently enforce the verifier; the client alone cannot ensure that. Existing unsigned endpoints and direct repository calls do not enforce signatures unless the host configures the policy or wraps those paths.

To retain signature evidence, pass `{verifyWithEvidence: verify.verifyWithEvidence}` as the target policy instead. The in-memory and SQLite repositories atomically store the Ed25519 signature, key ID, DER public key and SHA-256 public-key fingerprint alongside promotion provenance. SQLite protects the evidence with append-only triggers and verifies it against the stored publication when reading provenance. If a repository does not implement `promoteVerified`, the control plane rejects this policy's imports rather than silently omitting evidence. Existing unsigned promotions and the basic `{verify}` policy continue to have no signature evidence. Direct repository callers are trusted and can supply their own valid evidence; only the configured target verifier establishes that the key was trusted at import time. The saved proof does not independently prove past trust or actor identity, and revoking a key does not invalidate historical signatures.

For a signed release-principal assertion, call `signPromotionPackage(package, targetEnvironment, keyId, privateKey, expectedVersion, signerPrincipal)`. This creates a version-3 envelope that cryptographically binds the principal and target version. Configure the target key entry with that exact `signerPrincipal` and set `requireSignerIdentity: true` on `createSignedPromotionVerifier`; this rejects older envelopes and any principal that does not match the trusted key binding. Use `verifyWithEvidence` to store the signed principal atomically alongside the publication and signature; reads reverify the signature, including the principal. Principal IDs use 1–128 ASCII letters, digits, dots, underscores or hyphens and start with a letter or digit. Version-3 envelopes are also supported by signed remote export and the remote promotion client.

The configured binding identifies the principal authorized by the host to use the key; it does not prove which human or process actually used that key, nor prove that the key was trusted or the principal authorized at a later audit time. Protect signing keys, use distinct keys for distinct principals, retain historical trust and authorization records, and independently audit signing and import. A compromised or shared key can assert its configured principal. Direct repository writes can bypass the trusted verifier, so restrict them. Older unsigned or version-1/2 promotions do not have a signed principal and remain readable; enable the strict option before accepting new imports if identity is required.

A signature proves possession of a trusted key, not the signer's identity, authorization or the correctness of the source publication. The host must bind keys and endpoints to the appropriate tenant and release authority, protect private keys, audit signing and import, and enforce its own approval and replay policies. The basic `{verify}` policy stores the package digest and environments, but not the signer ID or signature. Signatures do not expire. Version-bound signatures prevent reuse with a different target version, but hosts must prevent database rollback and enforce time-based or other release-freshness rules externally. Older unbound signatures can be reused with a new expected version and are rejected when `requireVersionBound` is enabled. This does not provide production identity or protect against a compromised trusted signing key.

## Signing audit

`SqlitePromotionSigningAudit(path)` is an optional append-only signing log kept by the release service, separate from every target. `createAuditedPromotionSigner({audit, actor, keyId, privateKey, signerPrincipal?})` returns a function usable as the control plane's export signer: it signs, then records the tenant, actor, application, source environment and version, package digest, target environment, key ID, target version, signer principal and signature, and only returns the envelope after the record commits. A failed record releases nothing. A configured signer principal requires a target version.

Each entry includes the previous entry's SHA-256 hash. `verify(checkpoint?)` recomputes the chain and reports a missing sequence, broken link or altered entry; `head()` returns the latest sequence and hash. Retain heads outside the log, for example in a ticket, a separate service or a transparency system, and pass one to `verify` to detect truncation after that point. Database triggers reject ordinary updates and deletes, but a database administrator can drop them; the chain detects such edits only when compared with an independently retained head.

`findUnaudited(imports)` compares a target's imported signature evidence, such as `getPublicationProvenance` records, with the log. It reports imports whose signature was never recorded (`missing`) and imports whose signature was recorded for a different application, version, digest, environment, key, target version or principal (`mismatch`). A missing signature indicates the key was used outside the audited service. Ed25519 signatures are deterministic, so signing identical content outside the service produces an already-recorded signature and is not detected; that content was already approved for that target. The log cannot detect use of a key it never sees, and it does not prove which human approved a release. Protect the signing key and the log separately, and reconcile every target regularly.

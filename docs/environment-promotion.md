# Environment promotion

The local control plane can transfer a published definition between separate repositories. `POST /promotion/export` with `{ "sourceEnvironment": "development", "version": 1 }` returns a versioned package containing the definition, source environment and version, and a SHA-256 digest of those fields. `POST /promotion/import` with `{ "package": ..., "targetEnvironment": "production", "expectedVersion": 0 }` checks the package, its digest, the target application ID, schema, target compatibility guard and current target version before appending a new immutable publication. Both routes require the control token. `expectedVersion` is zero for an empty target; otherwise it is the latest target version. A stale request returns 409. The target draft and historical publications are not changed.

Promotion provenance records the claimed source and target environments, source version, package digest, and preceding target version. SQLite writes the publication and both provenance records in one transaction. After a lost response, inspect target provenance and latest version before retrying; a retry with the original precondition cannot publish twice. Older publications without provenance remain unknown. The existing SQLite provenance table stores promotion base records as `publish`, with a separate immutable promotion table; readers must use the current repository API to distinguish them.

## Authenticated remote client

`createRemotePromotionClient` in `@app-mixer/core` connects two explicitly configured origins. It requires HTTPS with normal certificate verification; HTTP is available only for loopback origins when `allowLoopbackHttp` is explicitly enabled for development. Redirects are rejected. The host supplies separate bearer tokens, an authenticated actor, an authorization callback and an audit callback. Configure origins, credentials and actor identity from trusted host configuration, not from an untrusted request or model. Use an authenticated TLS termination layer in front of each control plane; the control-token API itself remains a development prototype and does not implement production identity. The trusted host must bind each configured origin and credential to its intended environment and tenant, and enforce its own network access policy.

Call `promote` with `{actor: {tenantId, principalId}, applicationId, sourceEnvironment, sourceVersion, targetEnvironment, expectedVersion}`. The client asks the host to authorize export and import separately, verifies the package digest, application, source environment and version, and sends the target's optimistic version precondition. Authorization receives a copy of the request details and origins, never the tokens. The audit callback receives attempt, verification, authorization and completion events; it must durably record events if the host requires an audit trail. Pre-import callback failures prevent import. A completed event is not transactional with the target's publication, and permission changes after the import authorization cannot be coordinated atomically with the remote target.

An import error, malformed response, timeout, or failure to record the completed event raises `RemotePromotionUncertainError`: the target may already have committed. The client does not retry. Inspect the target's latest publication and durable provenance before deciding what to do; the original expected version prevents a duplicate publication. Source errors are reported without including endpoint responses or credentials.

The digest checks consistency, not a digital signature. HTTPS and the host's trusted endpoint configuration establish transport identity; a package does not independently prove its origin. The host's publication guard must verify target runtime and extension compatibility. Do not put credentials or environment secrets in definitions. Promotion does not migrate business data or submit transactions. General schema evolution, signed artifacts and production authorization remain open.
